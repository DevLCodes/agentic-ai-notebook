Agent Architecture Patterns

Six common shapes for an agent: RAG, ReAct, Planner–Executor, DAG, Multi-agent and Self-critique. Each one is the same agentic loop, arranged differently. The question is always: who decides the next step, and how much does that cost?

0 · The autonomy dial

  • Workflows: code fixes the path, and the model fills in each step. They are predictable, cheap and easy to test.
  • Agents: the model picks the next step at run time. They are flexible, but cost more and are harder to test.
  • Most real systems mix the two: a fixed outer shape with small autonomous pieces inside.
Rule of thumb
Start with the simplest shape that passes your evals. Move one notch towards "model decides" only when an eval shows you need to.

1 · RAG agent

Core idea: ground the answer in retrieved documents. Classic RAG always retrieves once before answering. A RAG agent treats retrieval as a tool, so the model decides whether to search, what to search for, and when it has enough.

tools = [{"name": "search_docs",
          "description": "Search the policy handbook. Returns the top 5 passages with doc ids. "
                         "Call it again with a narrower query if the passages don't answer the question.",
          "input_schema": {"type": "object", "properties": {"query": {"type": "string"},
                           "year": {"type": "integer"}}, "required": ["query"]}}]
system = "Answer only from search results and cite doc ids. If nothing relevant comes back, say you don't know."
# ...then the normal agentic loop: the model calls search_docs as often as it needs

Where RAG agents break
  • Bad chunks: no agent can fix retrieval that never returns the right passage. Measure recall first.
  • Search loops: the model keeps rephrasing forever. Cap the searches and return "no results" clearly.
  • Ungrounded answers: check faithfulness (is every claim in a cited passage?) as on the Testing & Evals page.

2 · ReAct (Reason + Act)

Core idea: interleave thinking and tool calls. Thought → Action → Observation, repeated until the model can answer. Each observation can change the plan, which makes ReAct good for problems where you can't know step 2 until you've seen step 1.

✎ Try it: step through a ReAct trace

Question: "Which is older, the Eiffel Tower or the Statue of Liberty, and by how many years?"

2022 ReAct papertoday, with native tool use
Thought: … (free text)a text or thinking block
Action: search[Eiffel]a tool_use block with JSON input
Observation: …a tool_result in the next user turn
Finish[answer]stop_reason: "end_turn"
ReAct = the agentic loop
  • The loop on the Agentic Loop page is ReAct, just with structured tool calls.
  • Don't parse "Action:" out of text any more. Use real tools.
  • Weak spot: it is greedy. It thinks one step ahead, so long tasks drift. That's why planners exist.

3 · Planner–Executor

Core idea: think once, then act many times. A strong model writes the whole plan up front. A cheaper executor (often a small ReAct agent) runs each step. A replanner revises what's left when a step fails or the facts change.

plan = planner(goal)                          # structured output: ["get dates", "get forecast", ...]
done = []
while plan:
    step = plan.pop(0)
    result = executor(step, context=done)     # small ReAct agent, cheaper model
    done.append((step, result))
    if result.failed or result.surprising:
        plan = replanner(goal, done, plan)    # rewrite only the remaining steps
return writer(goal, done)
✎ Try it: break a step

Goal: "Write a one-page brief for a Paris trip next weekend."

    Why bother?
    • Cost: the expensive model runs once or twice, not on every step.
    • Focus: the whole plan stays visible, so long tasks drift less than with pure ReAct.
    • Review: a human can approve the plan before anything runs.
    • Trap: a stale plan. No replanner means a failed step silently poisons the rest.

    4 · DAG agents

    Core idea: make the plan a dependency graph, not a list. Steps that don't depend on each other run in parallel. The total time is the critical path (the longest chain of dependencies), not the sum of all steps. The graph can be written by hand (a workflow) or produced by a planner model (the LLMCompiler idea).

    ✎ Try it: list vs graph
    DAG checklist
    • Every node declares its inputs. The edges are data, not vibes.
    • Nodes must be safe to run concurrently: no shared mutable state, and watch rate limits.
    • Speed up the critical path. Making an off-path node faster saves nothing.
    • A failed node blocks everything downstream, so give each node a retry and a timeout.

    5 · Multi-agent systems

    Core idea: split the work across agents with their own prompts, tools and context windows. The win is context isolation: each agent sees only what it needs. The cost is tokens, which is often several times a single agent. Details of orchestration, subagents and handoffs are on the Domain 1 page.

    ✎ Pick a topology
    Before you add a second agent
    • Could one agent with better tools do it? That's usually cheaper and easier to debug.
    • Split by context (each piece of work needs different information), not by job titles.
    • Pass summaries between agents, not whole transcripts.
    • Trace across agents, or you will never find which one went wrong.

    6 · Self-critique agents

    Core idea: generate, critique, revise. The same model (or a second one) reviews the draft against a rubric and the generator fixes it. Reflexion goes further: it stores the lessons as memory for the next attempt.

    draft = generate(task)
for round in range(MAX_ROUNDS):                   # always cap it
    feedback = critique(task, draft, rubric,      # best: grounded in an external signal
                        signal=run_tests(draft))
    if feedback.passes:
        break
    draft = revise(task, draft, feedback)
    ✎ Try it: how many rounds?

    The numbers are illustrative. They show the shape of the curve that published results report, not a benchmark.

    Self-critique rules
    • A model grading its own work with no new information mostly agrees with itself, so gains plateau fast.
    • Give the critic something the generator didn't have: test results, a schema validator, retrieved sources, a different model.
    • Stop on pass, on no improvement, or at the cap. Each round costs two more calls.

    Remember
    • RAG = what the agent knows. ReAct = how it acts step by step.
    • Planner and DAG = structure decided up front. Multi-agent = who does it. Self-critique = quality control.
    • They are layers, not rivals. Pick the least autonomy that passes your evals.
    Anti-patterns
    • Multi-agent for a task one agent with good tools can do.
    • ReAct for a fixed pipeline you could write as five lines of code.
    • Self-critique with no external signal and no round cap.
    • A plan with no replanner, or a DAG with hidden shared state.
