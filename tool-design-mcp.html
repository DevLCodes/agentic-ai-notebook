2.1 Tool interface design

The tool description is the primary mechanism Claude uses to choose a tool. When it picks the wrong tool, fix the description first: it's the lowest-effort, highest-leverage change.

the five parts of a production-grade description

Wrong tool picked? Try the fixes in this order
  • ✓ Expand the descriptions (root cause, low effort)
  • Few-shot examples treats the symptom and costs tokens
  • Routing classifier over-engineered for a first step
  • Consolidate tools valid later, but more effort

2.2 Structured error responses

A failure is only useful if the agent can tell what kind of failure it was, because that decides whether to retry, fix the input, or escalate.

Four categories, four recoveries
⏱ Transient
timeout, rate limit, service down		retryable → wait, retry
✏️ Validation
bad format, missing field, out of range		fix the input, resubmit
📜 Business
policy or limit exceeded		escalate / other workflow
🔒 Permission
access denied		escalate / other credentials
Empty ≠ broken
Access failure: the tool couldn't reach the data.
Valid empty result: it did reach the data and found nothing. 
// found nothing: accept the answer
{ "isError": false, "resultCount": 0 }

// couldn't look: retry
{ "isError": true,
  "errorCategory": "transient",
  "isRetryable": true }
errorCategory / isRetryable / description are app conventions, carried in structuredContent

✎ Try it: sort the failure

Multi-agent rule: a subagent retries transient errors itself. Only unresolved errors go up to the coordinator, together with partial results and what was attempted, so the coordinator isn't deciding blind.

2.3 Tool distribution & tool_choice

4–5 tools per agent, scoped to its role. Every extra tool adds a decision, and selection errors rise with the size of the toolkit. And remember: server boundaries are invisible to the model. Twenty-two tools split across two servers is still a 22-tool problem.

    2.4 MCP server integration

    MCP (Model Context Protocol) gives any host one standard way to plug in outside tools and data.

    Core components: host, client, server

    componentwhat it isits jobexamples
    MCP hostThe app the user talks to. It owns the model. Creates one client per server, asks the user for consent, decides which tools the model sees, and merges results into context. Claude Desktop, Claude Code, an IDE, your own agent app
    MCP clientA connector inside the host, one per server (1 : 1). Opens the connection, negotiates the protocol version and capabilities, and passes JSON-RPC messages both ways. Built into the host, or the client class in an MCP SDK
    MCP serverA program that exposes capabilities. Offers tools, resources and prompts. It knows nothing about the model or the other servers. GitHub, filesystem, Postgres, your internal API
    server primitivewho controls itmethods
    🔧 tools: actionsthe model decides to call themtools/list, tools/call
    📚 resources: read-only data by URIthe app decides what to attachresources/list, resources/read
    💬 prompts: reusable templatesthe user picks one (for example as a slash command)prompts/list, prompts/get
    client featurelets the server…
    samplingask the host's model for a completion. The server needs no API key of its own, and the user stays in control.
    rootslearn which folders or URIs it is allowed to work in.
    elicitationask the user for missing input mid-call ("which repo?").

    Creating MCP servers

    An MCP server is a small program. The SDK handles the protocol, and you write plain functions. The function's name, type hints and docstring become the tool definition the model reads, so the description rules from 2.1 apply here too.

    # weather_server.py · Python SDK (FastMCP)
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("weather")

@mcp.tool(annotations={"readOnlyHint": True})
async def get_forecast(city: str, days: int = 1) -> dict:
    """Hourly forecast for a city, up to 7 days ahead. Returns rain probability per hour.
    Use it for 'will it rain' questions. For past weather, use get_history instead."""
    return await fetch_forecast(city, days)          # returning a dict gives structured output

@mcp.resource("weather://cities")
def cities() -> str:
    """Supported city names, one per line."""
    return "\n".join(CITIES)

@mcp.prompt()
def packing_list(city: str) -> str:
    return f"Check the forecast for {city} and write a packing list."

if __name__ == "__main__":
    mcp.run()      # stdio by default; transport="streamable-http" to serve over HTTP
    // the same tool in TypeScript
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer({ name: "weather", version: "1.0.0" });
server.registerTool("get_forecast", {
  description: "Hourly forecast for a city, up to 7 days ahead. ...",
  inputSchema: { city: z.string(), days: z.number().int().max(7).default(1) },
  annotations: { readOnlyHint: true },
}, async ({ city, days }) => ({
  content: [{ type: "text", text: JSON.stringify(await fetchForecast(city, days)) }],
}));

await server.connect(new StdioServerTransport());
    Build → test → install
    1. Write the server, then describe each tool with 3–5 sentences.
    2. Try it in the MCP Inspector: npx @modelcontextprotocol/inspector uv run weather_server.py. List the tools, call them, and check the errors.
    3. Add it to a host: claude mcp add weather -- uv run weather_server.py, or commit it to .mcp.json for the team.
    4. Ask the agent a real question and read the trace: did it pick your tool?
    Server-building gotchas
    • stdio: never print to stdout. stdout carries the protocol, so one stray print() corrupts it. Log to stderr.
    • Report tool failures as a result with isError: true and a helpful message (see 2.2). Don't crash the server.
    • Add annotations (readOnlyHint, destructiveHint, idempotentHint) so hosts know what to ask approval for. They are hints, not security.
    • Keep tools few and focused. 40 thin API wrappers crowd the model's context.

    Deployment modes

    🖥 local desktop (stdio)☁️ remote (Streamable HTTP)
    how it runsThe host starts the server as a child process on the user's machine and talks through stdin/stdout. The server runs as a web service. Hosts connect to one URL, such as https://…/mcp.
    who uses itOne user, one process per hostMany users and hosts share one deployment
    authRuns with the user's own OS permissions. Secrets come from env vars.OAuth 2.1: each user signs in and the server checks tokens
    can reachlocal files, local apps, localhost, VPNonly what the server's network can reach
    updatesEach user upgrades their own copyDeploy once and everyone gets it
    configcommand + args in .mcp.json / claude_desktop_config.json, or a one-click desktop extension (.mcpb) "type": "http" + url, or claude mcp add --transport http name URL, or a "connector" in claude.ai
    watch out forversion drift across laptops, and the stdout ruleauth, rate limits, multi-tenant data isolation, and DNS rebinding (check Origin)

    Streamable HTTP replaced the older HTTP+SSE transport in the 2025 spec. Older servers and docs may still say "SSE".

    2.5 Built-in tools

    Grep finds what's INSIDE files. Glob finds files by their NAMES.

    Editing
    Edit = swap one unique old_string for a new_string. Precise and cheap on context.
    It fails when the text appears more than once (that's a safety feature).
    Exam fallback: Read + Write the whole file. (In real Claude Code, widening old_string or using replace_all is cheaper, but the exam expects Read + Write.)
    Don't read the whole repo
    Grep for the entry point → Read only the files that matter → Grep again for wrapper/barrel names → Read what those turn up. Reading everything first fills the context with irrelevant files.
