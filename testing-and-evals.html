Testing & Evals in Agentic AI

Everything on one page. If an improvement was "obviously better" by eye, it wasn't measured. Evals turn vibes into one number you can regress against.

0 · Why agents are hard to test

  • Non-deterministic: the same input can take a different path each run.
  • Multi-step: small per-step error rates compound into large end-to-end ones.
  • Many right answers: exact-match assertions break on valid variations.
  • Side effects: tools send emails and move money, so tests need mocks or sandboxes.
  • Cost & latency: every eval run costs tokens and time.

Offline vs online
  • Offline: a fixed golden set run before you ship (in CI). It catches regressions.
  • Online: score a sample of live traffic. It catches drift and real-world inputs your set never imagined.
You need both. Production failures become new offline cases.

Part A · Evaluation & testing

A1 · Metrics to track

Pick one north-star metric (usually task success) plus a few guardrail metrics that must not get worse (cost, latency, safety). A single average hides regressions, so slice it by task type.

familymetrics
🎯 Outcometask success / completion rate, correctness, faithfulness (groundedness), answer relevancy
🔧 Agent behaviourtool-selection accuracy, argument correctness, trajectory match, steps per task, redundant calls, loop / stuck rate, error-recovery rate
⚙ Operationallatency p50/p95, tokens and cost per task, tool error rate, timeouts
🛡 Safetypolicy violations, PII leaks, prompt-injection success, correct refusals
🙋 Userthumbs up/down, escalation-to-human rate, retries, abandonment
Measure the path, not just the answer
Two agents can both give the right final answer. One took 3 steps. The other took 14 steps, called process_refund twice, and got lucky. Final-answer metrics alone would score them the same.

A2 · Unit testing for individual tools

Tools are ordinary code, so test them like ordinary code: no LLM, deterministic, fast. Most agent failures that look like the model's fault are really a tool returning something confusing.

# test_lookup_order.py (plain pytest, fake API, no model)
def test_happy_path():
    r = lookup_order("#48213", api=FakeOrders({"48213": "shipped"}))
    assert r["status"] == "shipped"

def test_bad_format_is_validation_error():
    r = lookup_order("abc", api=FakeOrders({}))
    assert r["isError"] and r["errorCategory"] == "validation"
    assert r["isRetryable"] is False

def test_timeout_is_retryable():
    r = lookup_order("#48213", api=TimeoutAPI())
    assert r["errorCategory"] == "transient" and r["isRetryable"]

def test_no_rows_is_not_an_error():
    r = lookup_order("#99999", api=FakeOrders({}))
    assert r["isError"] is False and r["resultCount"] == 0

def test_refund_is_idempotent():
    api = FakePayments()
    process_refund("#48213", key="k1", api=api)
    process_refund("#48213", key="k1", api=api)
    assert api.refund_count == 1

A3 · Integration testing for flows

Run the loop plus the tools together on scripted scenarios and check three things: ① the final answer, ② the trajectory (which tools were called, in what order), and ③ the end state (was exactly one refund row written?). Mock or sandbox anything with side effects, and run each case several times.

✎ Try it: trajectory matching

Expected for a refund: get_customer → lookup_order → process_refund. Choose how strictly to match. The last column is a hard invariant: never refund before verifying.

Integration-test toolkit
  • Record/replay model responses for fast, deterministic CI runs. Use live runs nightly.
  • Simulated users (an LLM playing the customer) for multi-turn flows.
  • Invariants in code: max steps, no duplicate side effects, gate order held.
  • State checks on the fake database, not just on the text.
pass@k vs pass^k
pass@k = at least one of k tries succeeds. That's fine when a human picks the best attempt.
pass^k = all k tries succeed. That's what an unattended agent needs. It falls fast: 90% per try becomes about 66% over 4 tries. (Try the slider in section 0.)

A4 · Human-in-the-loop evaluation

Humans do what code and judges can't: find the failure modes in the first place, set the ground truth, and check that your LLM judge agrees with them. (That's different from runtime HITL, where a human approves risky actions.)

1 · Error analysis
Read 50–100 real traces. Note what went wrong in free text, then group the notes into failure categories and count them. Fix the biggest category first.
2 · Golden set
Experts label 20–50+ real cases, including edge cases and past failures. That set becomes your offline regression suite.
3 · Judge calibration
Humans and the judge label the same sample. If they agree less than ~80–90% of the time, rewrite the rubric before trusting the judge.

Part B · Evaluation types

B1 · Deterministic evals

Plain code assertions: exact match, regex, JSON-schema validation, contains / not-contains, tool name == expected, number within tolerance, latency < budget.

✓ free, instant, 100% reproducible, easy to put in CI.
✗ brittle on free text ("Paris" vs "It's Paris.").

Rule: if code can check it, use code. Save judges for the things code can't check.

# deterministic checks on one agent run
assert json_schema_valid(out, RefundDecision)
calls = run.tools_called
assert calls.count("process_refund") <= 1
assert calls.index("get_customer") \
     < calls.index("process_refund")
assert "ssn" not in out.lower()
assert run.steps <= 8 and run.latency_s < 20

B2 · Model-based evals (LLM-as-judge)

A second model grades the output against a rubric. It scales like code and handles nuance the way a person does, but only after you've calibrated it against human labels.

# a judge prompt that holds up
You are grading a support reply.

Policy: {policy}
Customer: {question}
Reply: {answer}

Criteria (each is PASS or FAIL):
1. States refunds end at 30 days.
2. Offers store credit if 31–60 days.
3. Promises nothing the policy forbids.

Think step by step, then output JSON:
{"reasoning": "...", "c1": "PASS", ...,
 "verdict": "PASS"}   # PASS only if all pass
choiceoptions
what it seespointwise (score one answer) · pairwise (A vs B, better for comparing versions)
reference?reference-based (compare to a gold answer) · reference-free (judge against criteria only)
scalebinary per criterion beats 1–10. Unanchored scales drift.
G-Evalthe judge writes its own evaluation steps from the criteria, then fills in a score
Judge failure modes → fixes
  • Position bias (prefers the first answer) → run both orders and count only consistent wins
  • Verbosity bias (long = good) → specific criteria, "length is not a criterion"
  • Self-preference (likes its own model's style) → use a judge from a different model family
  • Leniency → binary checks, and ask for reasoning before the verdict

B3 · Human evals

The gold standard, but slow, expensive and inconsistent between people. Use experts where the stakes are high, write a rubric so reviewers agree, and measure inter-annotator agreement (e.g. Cohen's κ). If two humans can't agree, no judge will either. Use humans to create ground truth and calibrate judges, not for every CI run. Side-by-side (A/B) comparisons are easier and more reliable than absolute scores.

B5 · Evaluation tools: DeepEval & RAGAS

🧪 DeepEval "pytest for LLMs"

Test cases plus metrics, run with deepeval test run in CI. Metrics include G-Eval (a custom rubric), answer relevancy, faithfulness, hallucination, and agent metrics like tool correctness and task completion.

from deepeval import assert_test
from deepeval.test_case import LLMTestCase, ToolCall
from deepeval.metrics import GEval, ToolCorrectnessMetric
from deepeval.test_case import LLMTestCaseParams as P

correct = GEval(name="Policy-correct",
  criteria="Mentions 30-day refund limit and "
           "store credit up to 60 days.",
  evaluation_params=[P.INPUT, P.ACTUAL_OUTPUT],
  threshold=0.7)

def test_return_45_days():
    case = LLMTestCase(
        input="Return shoes after 45 days?",
        actual_output=agent("Return shoes after 45 days?"),
        tools_called=[ToolCall(name="get_policy")],
        expected_tools=[ToolCall(name="get_policy")])
    assert_test(case, [correct, ToolCorrectnessMetric()])

📐 RAGAS "RAG assessment"

Built for RAG: faithfulness, context precision and recall, response relevancy. It can generate synthetic test sets from your documents, and it has agent metrics (tool-call accuracy, agent goal accuracy, topic adherence).

from ragas import evaluate, EvaluationDataset
from ragas.dataset_schema import SingleTurnSample
from ragas.metrics import (Faithfulness,
    LLMContextRecall, ResponseRelevancy)

ds = EvaluationDataset(samples=[SingleTurnSample(
    user_input="When was the Eiffel Tower done?",
    retrieved_contexts=["Completed in 1889 ..."],
    response="It was completed in 1889.",
    reference="1889")])

result = evaluate(ds,
    metrics=[Faithfulness(), LLMContextRecall(),
             ResponseRelevancy()],
    llm=judge_llm, embeddings=judge_emb)
print(result)   # per-metric scores 0–1

Part C · Putting it together

C · The eval-driven development loop

Anti-patterns
  • judging by eye ("looks better to me")
  • happy path only: no edge cases or past failures
  • final answer only: no trajectory or state checks
  • an uncalibrated judge treated as ground truth
  • 1–10 scores with no anchors
  • one run per case for a non-deterministic agent
  • tests hitting real payment APIs
  • tuning prompts on the test set (it stops being a test)
Minimum viable eval (start today)
  1. 30 labelled real examples in a JSONL file
  2. deterministic checks for everything code can check
  3. one binary-rubric judge for the rest, checked against your own labels
  4. one number (the pass rate) printed on every change, and run in CI
  5. every production failure → a new row
