Open-Weight Models

A model you can download is a file of numbers. Whoever holds that file can run it on their own hardware, inside their own network, for as long as they like. You gain control, and you take on the work an API provider used to do.

See it in 3D: running a model inside your own fence

1 · What “the weights” actually are

Training a model means adjusting billions of numbers until it predicts text well. Those numbers are the weights (or parameters). “Llama 3.1 8B” means about 8 billion of them. Stored at 2 bytes each, that is roughly a 16 GB file. The file does nothing on its own. A runtime such as vLLM or llama.cpp reads it, together with the architecture config and the tokenizer, and does the maths.

“Open” gets used for three different things. The difference matters when legal or security ask what you are allowed to do.

The OSI Open Source AI Definition (v1.0, 2024) requires the parameters, the training code and enough information about the training data to rebuild the model. By that bar, most models called “open” are open-weight, not open source.

2 · Will it fit? The memory maths

Three things share the GPU’s memory:

  • Weights: the number of parameters × the bytes per parameter.
  • The KV cache: the attention keys and values kept for every token in every active request.
  • Overhead: the runtime and activations.
weights_GB ≈ params_B × bytes_per_param           (BF16 2 · FP8/INT8 1 · 4-bit ≈ 0.55)
kv_GB      ≈ 2 × layers × kv_heads × head_dim × 2 bytes × context × batch / 1e9
total      ≈ weights × 1.1 + kv + ~1 GB

weights KV cache overhead

Mixture of experts (MoE): total vs active
gpt-oss-120b has about 117B parameters in total, but routes each token through only about 5B of them. Speed follows the active count. Memory follows the total, because every expert has to be loaded. It ships natively in 4-bit (MXFP4), which is why it fits on one 80 GB GPU.

Quantization and serving

Quantization stores each weight in fewer bits, accepting a small quality loss in exchange for a model that is 2–4× smaller and usually faster. Measure that loss on your own eval set, not on a leaderboard; see Testing & Evals.

For a laptop or a single developer machine, use Ollama or llama.cpp. To serve many users, use vLLM or SGLang: they batch requests continuously and manage the KV cache in pages, so one GPU serves dozens of users at once.

3 · API, hosted open-weight, or your own GPUs?

There are three routes, not two. Many providers (Amazon Bedrock, Vertex AI Model Garden, Together, Fireworks, Groq) run open-weight models for you and charge per token. Tick what is true for your project.

recommended route

    Why teams choose open weights
    • Data residency and privacy: prompts never leave the network
    • Cost at steady, high volume, once GPUs stay busy
    • Latency and offline or air-gapped use
    • Fine-tuning and LoRA on your own data
    • No surprise deprecations: the version you tested is the one you run, so results are reproducible
    What it costs
    • GPUs, and paying for them even when idle
    • Serving, scaling, upgrades and on-call
    • Safety tuning and guardrails become yours
    • Your own evals before every model swap
    • Usually a capability gap to the best closed models on the hardest tasks

    4 · Where open weights already win: embeddings, rerankers, small jobs

    The most common production use isn’t a chat model at all. It is the small, quiet models in the retrieval pipeline:

    • Embedding models such as bge, e5 and nomic-embed, a few hundred MB each.
    • Cross-encoder rerankers such as bge-reranker; see Reranking.
    • Small classifiers or routers; see Routing.

    They run on a CPU, every document passes through them, and per-token API pricing adds up quickly at that volume. FinSight, the running example in this notebook, embeds 50,000 10-K chunks with bge-small-en-v1.5 (33M parameters, 384 dimensions) through FastEmbed on a laptop CPU. Its numbers planner runs on a local model through Ollama. See Embeddings.

    Safety is now your job
    • Once weights are released, they can’t be recalled or patched. If a jailbreak is found, the fix is your guardrails, not a provider update.
    • Read the model card: intended use, known limits, the safety evals the vendor ran.
    • Load .safetensors, not pickled .bin or .pt files from strangers. Unpickling can run arbitrary code.
    • Add input and output guardrails and log usage, exactly as you would for an API. See AI Governance.
    Remember
    • Weights are the model: a file of learned numbers, plus a config and a tokenizer.
    • Open-weight ≠ open source ≠ “do anything”. The licence decides.
    • Memory ≈ params × bytes, plus a KV cache that grows with context × users.
    • Hosted open-weight is a middle route: open models, no GPUs.
    Common mistakes
    1. “Apache on one size, so all sizes”: check each checkpoint
    2. sizing for weights only: 32 users × 32k context can outgrow the weights
    3. counting MoE active params for memory
    4. trusting leaderboard deltas after quantizing: run your evals
