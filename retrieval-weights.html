Weights in Retrieval

Every search engine turns a query into one number per document and sorts. That number is almost always a weighted sum of signals: keyword match, meaning match, freshness, field, business rules. The weights decide what “relevant” means, so they deserve the same care as the model.

See it in 3D: two retrievers, one scale

1 · A score is a weighted sum

score(d) = w₁·bm25 + w₂·dense + w₃·recency + w₄·field + w₅·business

Each signal is a number per document. The w’s are the only thing you tune. In hybrid search the first two are usually written as one knob: alpha·dense + (1 − alpha)·bm25, so alpha = 1 is pure vector search and alpha = 0 is pure keyword search.

The catch: you can’t add numbers on different scales. A BM25 score of 18 next to a cosine of 0.84 means BM25 wins every sum unless you normalise first. Two common fixes: min-max (rescale each list to 0–1) and z-score (subtract the mean, divide by the standard deviation).

2 · Fuse ranks, not scores: RRF

Reciprocal Rank Fusion ignores raw scores and uses only each document’s rank in each list:

RRF(d) = Σ wᵢ / (k + rankᵢ(d))

No normalisation is needed, which is why most engines ship it as the default hybrid mode. k = 60 comes from the original paper (Cormack et al., 2009). A small k makes the #1 slot in either list dominate. A large k flattens the curve, so documents that do well in both lists win. Weighted RRF adds a weight per list, the same idea as alpha but applied to ranks.

3 · Boosts, decay and filters

Field boosts

A match in the title or a section header says more than a match in a footnote. Keyword engines let you weight fields: title^3 section^2 body. For 10-Ks, a hit in the heading “Item 7. Management’s Discussion and Analysis” is worth more than one in the exhibit index.

Business boosts

“Promote our own research notes”, “prefer the help-centre article over the forum post”. They’re legitimate, but they quietly overrule relevance. Keep them small and named, log them on every result, and measure them with the same eval as everything else. Otherwise nobody can explain why result #1 is #1.

Recency decay

Exponential decay with a half-life: recency = 0.5^(age / half_life). With a 90-day half-life, a 90-day-old filing gets 0.5 and a 180-day-old one gets 0.25.

Filter or boost?

Filters are hard: WHERE fiscal_year = 2023 removes documents entirely. Use them when the question pins a value (ticker, year, permissions). Boosts are soft: they reorder but never remove. Use them for preferences (“newer is usually better”). Never use a boost for access control (access control).

4 · Choosing the weights

Weights are hyperparameters. Picking alpha by trying three queries and eyeballing the results is how teams ship a search that’s great on the demo and worse everywhere else. The repeatable way is a grid search on a labelled set: queries with graded relevance (2 = answers it, 1 = related, 0 = not), a metric such as NDCG@k or recall@k, and one run per weight value (evals, testing & evals).

Three habits follow from that lab:

  • Re-tune after any change to a signal. A new embedding model, a new chunker or a new BM25 analyser shifts score distributions, and yesterday’s best alpha may now be wrong.
  • Tune per query type if they differ. ID lookups want low alpha; open questions want high alpha. A router can pick the profile.
  • Hold out a test split. Tune on one half of the labelled set and report on the other, or the score flatters you.

When there are more than a handful of signals, hand-tuned weights stop scaling. Learning to rank (LTR) trains a model, often LambdaMART gradient-boosted trees, on the same labelled pairs to learn the weights and their interactions. A cross-encoder reranker, the next page, goes one step further and reads the query and document together.

Remember
  • A retrieval score is a weighted sum. The weights define relevance.
  • Normalise before you add scores, or use RRF and fuse ranks.
  • RRF: 1/(k + rank), k = 60 by default.
  • Filters remove, boosts reorder. Permissions are always filters.
  • Choose weights with a labelled set and NDCG/recall, and re-tune after any model change.
Pitfalls
  1. raw BM25 + cosine: BM25 silently wins every query
  2. alpha tuned on five demo queries
  3. recency as a filter: last year’s 10-K vanishes when it’s the only answer
  4. unlogged business boosts: nobody can explain the ranking
  5. the same weights after swapping the embedding model
