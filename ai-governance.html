AI Governance

Security, compliance and guardrails on one page. Governance = who decides what the AI may do, how that's enforced, and how you prove it afterwards.

0 · Three pillars, one job

🔐 Security
Keep attackers from making the system do harm: injection, data theft, runaway spend, abused tools.
"Can someone break it?"
📜 Compliance
Meet laws, standards and contracts (EU AI Act, GDPR, NIST, ISO 42001), and keep the evidence.
"Can we prove it's allowed?"
🚧 Guardrails
Runtime controls on inputs, outputs and actions that enforce the other two, request by request.
"What stops it right now?"

The governance loop

  1. Inventory: every AI system, model, vendor, owner and data source
  2. Classify risk: by use case (a hiring tool ≠ a menu recommender)
  3. Apply controls: guardrails, access, human oversight in proportion to the risk
  4. Test: evals and red teaming before launch (see Testing & Evals)
  5. Monitor: logs, incidents, drift, abuse
  6. Audit & report: evidence for regulators, customers and the board, then back to 1
Who owns what
  • Product / eng build and run the controls (the first line)
  • Risk, legal, security, privacy set policy and review high-risk launches (the second line)
  • Internal audit checks that it actually works (the third line)
  • Often an AI governance council approves high-risk use cases and keeps the acceptable-use policy

A2 · Prompt injection: the #1 risk

Direct: the user types "ignore previous instructions…".
Indirect: the instructions hide in content the agent reads, such as web pages, emails, PDFs, tool results and MCP tool descriptions. For agents this is the dangerous kind, because the user isn't the attacker.

The core problem is that an LLM can't reliably tell instructions from data, since both are just tokens. So no prompt or classifier gets you to 0%. Design as if injection will succeed, and limit what it can do when it does.

A3 · Securing agents, tools & MCP

Agent hardening checklist
  • Least privilege: the fewest tools, the narrowest scopes, read-only by default
  • The model never holds credentials: tools keep scoped, short-lived tokens server-side, and act as the user rather than as an admin
  • Authorise in the tool: check that this user may see order #123 in code, never by asking the model
  • Sandbox code execution: containers, no network by default, CPU and time limits
  • Caps: max steps, tokens and dollars per session; rate limits per user
  • Log everything: prompts, tool calls, args and approvals, while keeping PII out of the logs
MCP-specific riskdefence
Tool poisoning: hidden instructions in a tool's descriptionreview descriptions, and install only trusted servers
Rug pull: the server changes its tools after you approved thempin versions, and re-approve when the definitions change
Tool shadowing: a malicious server redefines another server's toolnamespace tools, and limit servers per agent
Confused deputy / token passthroughthe server gets tokens issued for itself (OAuth audience), not passed through
Local servers run as youtreat them like any package you run: least-privilege environment

Red teaming

Before launch, and again on every major change, attack your own system: jailbreaks, direct and indirect injection, PII extraction, harmful content, tool abuse, spend attacks. Automate the known attacks as a regression suite (tools: garak, PyRIT, promptfoo red-team) and add humans for creative ones. Map findings to OWASP and MITRE ATLAS (an ATT&CK-style knowledge base of AI attacks). Every successful attack becomes a test case, just like production failures in evals.

Part B · AI compliance

B1 · EU AI Act: risk-based rules

tierexamples → duties
Unacceptablesocial scoring, manipulative AI, workplace/school emotion recognition, untargeted face scraping → banned
High-riskhiring, credit, education, critical infrastructure, law enforcement, medical devices → risk management, data governance, logging, technical docs, human oversight, accuracy and robustness, conformity assessment, registration
Limitedchatbots, deepfakes, generated content → tell people it's AI, label synthetic media
Minimalspam filters, recommendations, games → voluntary codes

Providers (who build a system or put their name on it) carry most duties. Deployers (who use it) must follow the instructions, assign human oversight, and keep logs. General-purpose model providers have their own duties (docs, copyright policy, training-data summary). It applies to anyone whose AI output is used in the EU.

datewhat applies
1 Aug 2024enters into force
2 Feb 2025prohibitions and AI-literacy duty

2 Aug 2026most of the rest, including Annex III high-risk systems (the EU "digital omnibus" proposal may push high-risk dates back, so check the current status)
2 Aug 2027high-risk AI embedded in regulated products (Annex I)

Fines: up to €35M or 7% of global turnover for prohibited practices, and €15M or 3% for most other breaches.

GDPR and US rules that bite AI

rulewhat it means for an AI system
GDPR: lawful basis, minimisation, purpose limitationyou need a reason to send personal data to a model. Send the minimum, and don't reuse support chats for training without a basis.
GDPR Art. 22people can object to solely automated decisions with legal or similarly significant effects, and get human review and an explanation
GDPR DPIA, rights of access and erasureassess high-risk processing before launch. Erasure is hard once data is in fine-tuned weights, so prefer RAG over training on personal data.
US: no single federal AI lawa patchwork: NYC Local Law 144 (bias audits for hiring tools), the Colorado AI Act (high-risk "consequential decisions"), California transparency laws, plus FTC rules on unfair or deceptive practices
Sector rulescredit (ECOA/FCRA adverse-action reasons), health (HIPAA), finance (model risk management, SR 11-7). Existing law still applies when AI is involved.

B2 · Frameworks: NIST AI RMF & ISO/IEC 42001

NIST AI RMF 1.0 (voluntary, US) has 4 functions, plus a Generative AI Profile (NIST AI 600-1) listing GenAI-specific risks:

Governculture, policy, roles, risk tolerance, inventory (it spans the other three)
Mapcontext: intended use, users, who could be harmed, legal setting
Measureevals, bias tests, red teaming, tracking metrics over time
Manageprioritise and treat risks, respond to incidents, decommission
ISO/IEC 42001:2023
The first certifiable AI management-system standard, the "ISO 27001 for AI". It requires an AI policy, roles, risk and impact assessments, controls (Annex A), internal audit and continual improvement. Enterprise customers increasingly ask vendors for it, alongside SOC 2. Related: ISO/IEC 23894 (AI risk management guidance).

Part C · AI guardrails

C1 · Guardrail layers

deterministic (code)model-based (classifier / LLM)
forregex PII, schemas, allowlists, amount limits, rate capsinjection, toxicity, topic, grounding, subtle PII
profast, predictable, testable, can't be talked aroundhandles meaning and paraphrase
conbrittle: misses paraphrases, blocks innocent wordslatency, cost, false positives, can be fooled
Prompt ≠ guardrail
"Never refund more than $500" in the system prompt is a request. if amount > 500: ask_human() in the tool or a PreToolUse hook is a guarantee. This is Domain 1's lesson again: prompts are probabilistic, hooks are deterministic.

C2 · Guardrail pipeline lab

Nine real-world requests to a restaurant support agent. Switch guardrails on and aim for 0 harms, 0 false positives, while watching latency.

C3 · Thresholds: every guardrail trades misses for false alarms

A classifier gives each message a risk score. You choose where to cut. ✗ = actually harmful, ○ = benign.

block if score ≥
Pick the threshold by cost
A missed harm in a kids' app costs more than a blocked question, so use a low threshold. On an internal developer tool, false positives kill adoption, so use a higher threshold with logging. Measure it on a labelled set (see the evals page), don't guess.
Soft actions beat hard blocks
Between allow and block there's a middle ground: redact, rewrite, add a disclaimer, ask a clarifying question, route to a human, or log and review later. A refusal with no way forward frustrates users and drives them to less safe tools.

C4 · Guardrail tools & code

# a guardrail sandwich around one model call
def answer(user_msg, ctx):
    msg = redact_pii(user_msg)            # input · code
    if injection_score(msg) > 0.8:        # input · model
        return REFUSAL
    out = llm(system=POLICY, user=msg, context=ctx)
    if not ReplySchema.is_valid(out):     # output · code
        out = retry_once(msg, ctx)
    if not is_grounded(out, ctx):         # output · model
        return handoff_to_human(msg)
    if moderation(out).flagged:
        return REFUSAL
    return out

# action rail: enforced in code, never by the prompt
def pre_tool_use(tool, args, user):
    if tool not in ALLOWED[user.role]:
        return deny("tool not permitted")
    if tool == "process_refund" and args["amount"] > 500:
        return ask_human("refund over $500")
    return allow()

Part D · Putting it together

D · Defence in depth (the Swiss-cheese model)

Every layer has holes. Harm needs holes that line up, so stack layers of different kinds.

Anti-patterns
  • security by system prompt ("never reveal…")
  • secrets or API keys in the prompt
  • an agent with admin credentials "to keep it simple"
  • authorisation decided by the model
  • model output piped straight to SQL, HTML or a shell
  • no inventory: shadow AI nobody approved
  • logs full of raw PII "for debugging"
  • compliance as a launch-week checkbox
Minimum viable governance
  1. An AI inventory: system, owner, model, vendor, data, risk tier
  2. An acceptable-use policy plus a vendor DPA with no training on your data
  3. Least-privilege tools and code-level gates on high-impact actions
  4. Input and output rails matched to the risk, measured on a labelled set
  5. Audit logs (with PII redacted) and an incident runbook
  6. A red-team suite in CI, and every incident becomes a test
