What vector search is

Vector search finds the stored items whose embeddings point in nearly the same direction as the query's embedding. It matches on meaning, not on shared words.

This page follows one query through that path. The vector databases page covers how the index is built and stored; here the focus is what happens at query time and how to tune and judge it.

A query, step by step

  1. Prepare the text. Some embedding models are trained with different instructions for questions and documents, for example a query: prefix, or a separate query_embed call. Use the query form for questions and the passage form for chunks, or similarity drops for no visible reason.
  2. Embed with the exact model and version used for the index. Vectors from two different models live in unrelated spaces, so comparing them gives meaningless scores rather than an error. Store the model name beside every vector and check it at query time.
  3. Normalise. Most text models return unit-length vectors. If yours does not, normalise both sides so cosine similarity and dot product agree (the lab below shows why).
  4. Probe the index. The ANN index returns a candidate set, usually larger than k, by walking a graph or scanning a few clusters.
  5. Apply filters. Tenant, permissions, date or document type. Done inside the traversal when the engine supports it; see filtering.
  6. Return the top k with ids, scores and metadata, ready for fusion with keyword results, a reranker, or the prompt.

Exact k-NN, worked by hand

Exact k-nearest-neighbour search compares the query with every stored vector and keeps the k best. With unit vectors, similarity is just the dot product: multiply matching numbers and add them up.

exact cost per query = N vectors × d dimensions multiply-adds
CorpusWork per queryRough time, one CPU core
30k chunks × 384 dims11.5Mabout 1 ms
1M chunks × 768 dims768Mtens of ms
50M chunks × 768 dims38Bseconds

Exact search is the right answer more often than people expect:

  • Small corpora, up to roughly 100k to 1M vectors, where it is fast enough and has perfect recall.
  • Very selective filters: if a filter leaves 2,000 rows, scanning them exactly beats walking a graph built for all 50M.
  • Ground truth: exact results are what you measure an ANN index against (see two different recalls).

How an HNSW search walks

The HNSW index is a layered graph. Finding neighbours in it is a search with two phases.

entry = the top layer's entry point
for layer in top .. 1:                       # phase 1: greedy descent
    entry = move to any neighbour closer to q, until none is closer

candidates = {entry}   results = {entry}     # phase 2: beam search on layer 0
while candidates:
    c = closest candidate
    if c is farther than the worst result and len(results) == ef: stop
    for n in neighbours(c) not yet visited:
        if len(results) < ef or n is closer than the worst result:
            add n to candidates and results; keep only the ef best results
return the k closest results

The beam width ef (efSearch) is what stops the walk from getting stuck. A purely greedy walk stops at the first node with no closer neighbour, which may be a local dead end. Keeping ef candidates open lets the search back out and try another route.

Two practical consequences: ef must be at least k, and in pgvector a query returns at most hnsw.ef_search rows unless iterative scans are enabled, so asking for 100 results with the default ef of 40 quietly gives you 40.

Two different recalls

"Recall" means two different things in vector search, and mixing them up leads to fixing the wrong component.

Index recallRetrieval recall
Compares againstExact k-NN over the same vectorsLabelled relevant chunks (a golden set)
MeasuresHow much the ANN index approximates awayWhether search finds what answers the question
Typical value0.95–0.99Often 0.5–0.9 at first
Fix when lowRaise ef_search or nprobeBetter chunks, embedding model, hybrid search, filters, query rewriting
index recall@k = |ANN top-k ∩ exact top-k| / k

An index can score 0.99 index recall while retrieval recall is 0.6. That means the index faithfully returns the nearest vectors, and the nearest vectors are the wrong passages. Raising ef_search will not help; the problem is upstream. See recall@k, step by step.

Making vectors smaller

At scale, memory is the cost. Compression stores each vector in fewer bytes, searches the small form, then re-scores a shortlist with the full vectors.

Raw vector sizes only; the index graph adds more. Re-scoring recovers most of the lost accuracy because the compressed form only needs to get the right items onto the shortlist, not to order them perfectly. pgvector offers halfvec for float16 and binary_quantize for bits; dedicated engines offer int8, binary and PQ with built-in re-scoring.

k, thresholds and diversity

How many to retrieve

Retrieve wide, pass narrow. A common shape is 50 to 100 candidates from vector search, a reranker to order them, and 5 to 10 chunks into the prompt. Without a reranker, retrieve 10 to 20 and pass most of them.

Why a fixed score threshold is fragile

Similarity scores are not probabilities. Each model spreads them differently: some put nearly every pair between 0.7 and 0.9, others use the whole range. A cut-off tuned for one model breaks when you change models, and even with one model a score of 0.8 means "close" for one query and "the best of a bad lot" for another. Compare scores within a query, calibrate any threshold on labelled data, or let a reranker decide whether anything is good enough to answer.

Near-duplicates and MMR

Annual reports repeat whole paragraphs year after year, and wikis keep old copies. Plain top-k can then fill every slot with the same passage. Maximal marginal relevance (MMR) picks results one at a time, rewarding similarity to the query and penalising similarity to what is already picked:

next = argmax over candidates [ λ × sim(q, d) − (1 − λ) × max sim(d, already picked) ]

      λ = 1 is plain top-k; λ = 0 ignores the query and only spreads out. Values around 0.5 to 0.8 usually work. Removing exact duplicates at ingestion, or filtering to the latest document version, is cheaper still when you can do it.

      Most of these are not index problems, so raising recall knobs does nothing. They show up as low retrieval recall on specific slices of a golden set, which is why the golden set needs exact-ID, numeric and negation questions.

      Saying it in an interview

      "At query time I embed the question with the same pinned model as the index, run filtered ANN search to get about 50 candidates, then rerank down to the handful that go into the prompt. I tune ef_search with a sweep against exact search until index recall is around 0.95 inside the latency budget, and I track retrieval recall separately on a golden set, because a perfect index can still return the wrong passages. Where vector search is weak, on IDs, numbers, years and negation, I add BM25, metadata filters and a reranker. At large scale I quantize and re-score the shortlist with full vectors."
