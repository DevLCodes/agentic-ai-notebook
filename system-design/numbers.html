Numbers cheat sheet: tokens, cost and latency

Back-of-the-envelope numbers for AI system design: how many tokens a page, file, prompt or chat turn is, input and output prices by model tier, monthly cost estimates, classifier vs LLM cost, latency, and self-hosted GPU serving.

Memorise these first

  1. 1 token ≈ 4 characters ≈ ¾ of an English word. 1,000 words ≈ 1,300 tokens; one page ≈ 600 tokens.
  2. Output costs 4 to 8 times more than input per token, so long answers are expensive and short labels are cheap.
  3. Three price tiers per 1M tokens (input / output): small about $0.10 / $0.40, mid about $0.30 / $2.50, large about $1.25 / $10.
  4. A chat turn is about 5K tokens in and 250 out. The prompt is mostly system prompt, history and retrieved chunks, not the question.
  5. An agent task is 30K to 100K tokens in, because every step re-sends the context.
  6. Cost = input tokens × input price + output tokens × output price. Per day × 30 = per month.
  7. A classifier is 10 to 100 times cheaper and faster than an LLM on high-volume fixed-label work: a few dollars vs $100+ per million items, 10 ms vs 1 s.
  8. Batch is about half price; cached input is 75 to 90% off.

Prices are illustrative list prices for Flash-Lite, Flash and Pro class models at the time of writing. They change often, so say "roughly" in an interview and show the method, not the exact number.

Self-hosted GPU serving

When you run open weights on your own NVIDIA GPUs, the numbers that matter are memory, batching and parallelism. The stack has three layers, each with one job. NIM packages the model, Triton schedules requests, and TensorRT-LLM runs the maths on the GPUs.

LayerJobWhat you tune
NIMA container with the model, an optimized engine for your GPU and an OpenAI-compatible APIWhich model and profile (precision, GPU count); mostly picked for you
Triton Inference ServerTakes requests, queues and batches them, runs model instances, exposes metricsBatching delay and sizes, instance count, ensembles
TensorRT-LLMCompiles and runs the LLM with fused GPU kernelsPrecision, parallelism, max batch and sequence length, KV cache size
CUDANVIDIA's GPU programming model; everything above runs on itRarely touched directly in an agent system

NIM is the deployable unit, so an agent team usually picks a NIM rather than building this stack by hand. You still need to know the layers, because each failure mode lives in one of them.

Where GPU memory goes

Two things fill the GPU: the model weights, which are fixed, and the KV cache, which grows with every token of every active request.

weights ≈ parameters × bytes per parameter

An 8B model takes about 16 GB in BF16 and 8 GB in FP8, before any KV cache.

A mixture-of-experts model like the 120B one above keeps all 120B parameters in memory but uses only about 12B per token. MoE saves compute per token, not memory.

FP8 quantization

FP8 stores each weight in 8 bits instead of 16. Weights take half the memory and the GPU's FP8 tensor cores do more operations per second, so you serve the same model on fewer GPUs or with more room for the KV cache.

  • Hardware: FP8 tensor cores exist on Hopper (H100, H200), Ada (L4, L40S) and Blackwell. A100 has none, so FP8 there gives no speed-up.
  • Quality: the loss is usually small but not zero. Run your eval set on the quantized model before rollout; never assume.
  • KV cache too: the cache can also be stored in FP8, which doubles the tokens that fit.
  • Lower still: INT4 methods such as AWQ cut memory further at a larger, task-dependent quality cost.

Exam pattern: quantization cuts cost, but the right answer always pairs it with an evaluation before rollout, and keeps redundancy so savings never come out of availability.

KV cache

To generate token 101, attention needs the keys and values of tokens 1 to 100. The KV cache keeps them, so each new token costs one step instead of reprocessing the whole prefix. The price is memory that grows with every token.

KV bytes per token = 2 × layers × KV heads × head dim × bytes per value

Worked example, Llama 3.1 8B in FP16: 2 × 32 layers × 8 KV heads × 128 × 2 bytes = 128 KiB per token. One 8,000-token conversation holds about 1 GiB, and 40 of them hold more than the model's own 16 GB of weights.

Paged KV cache

Paging removes the waste of reserving the longest possible sequence for every request, so more requests fit at once. Requests that share a prefix, such as a common system prompt, can reuse its blocks instead of computing them again.

Batching

A GPU running one request at a time is mostly idle. Batching runs many requests together; the question is when a request may join.

KindWhereHow it worksFits
StaticOffline jobsA fixed group runs to the end togetherBatch scoring where latency doesn't matter
DynamicTriton schedulerWaits up to a short delay to group arriving requests, then runs them as one batchFixed-size work: embeddings, rerankers, classifiers
In-flight (continuous)TensorRT-LLMBatches per generation step; finished requests leave and new ones join between stepsLLM generation, where output lengths vary widely
# Triton config.pbtxt for an embedding model
dynamic_batching {
  preferred_batch_size: [ 8, 16 ]
  max_queue_delay_microseconds: 200
}
instance_group [ { count: 2, kind: KIND_GPU } ]

The delay is a trade: a longer wait forms bigger batches and more throughput, but adds that wait to every request's latency. For LLMs, Triton hands batching to the TensorRT-LLM backend (batching_strategy: inflight_fused_batching).

Exam pattern: bursty, variable-length LLM traffic → in-flight batching plus paged KV cache. Together they keep the GPU busy and raise throughput without inflating tail latency.

Concurrency and CUDA

CUDA is NVIDIA's platform for running code on the GPU. Work is written as kernels, many-threaded functions, and queued on CUDA streams. Work in one stream runs in order; work in different streams can overlap, for example copying the next batch to the GPU while the current one computes.

Concurrent execution in Triton means running several instances of a model, or several models, on the same GPU at once. Each instance gets its own stream, so a small model doesn't leave the GPU idle while it waits on input. It helps models too small to fill the GPU alone; a large LLM already saturates it.

To use more GPUs for one modelHow it splitsCost
Tensor parallelismEvery layer split across GPUs; all GPUs work on every tokenLots of GPU-to-GPU traffic, so keep it inside one NVLink node
Pipeline parallelismDifferent layers on different GPUs, like an assembly lineLess traffic, but stages can idle; spans nodes
ReplicasWhole copies of the model behind a load balancerSimplest scaling for throughput, if one copy fits

TensorRT-LLM engine

TensorRT-LLM is NVIDIA's open-source library for running LLMs fast on its GPUs. You build an engine for a specific GPU type, precision, parallelism and maximum batch and sequence length; that engine is what runs.

  • Fused kernels: several operations in one GPU pass, cutting memory reads.
  • Quantization: FP8, INT8 and INT4 (AWQ) weights, and FP8 KV cache.
  • Scheduling: in-flight batching and the paged KV cache.
  • Parallelism: tensor and pipeline parallelism across GPUs.
  • Speculative decoding: a small draft model proposes several tokens and the big model checks them in one pass, cutting latency.

Engines are tied to a GPU architecture, so an H100 engine won't run on an L40S. NIM hides this by shipping prebuilt engines and picking one for the GPUs it finds.

NeMo Evaluator and Curator

These sit around serving, not in it. Curator prepares the data a model is trained or fine-tuned on; Evaluator checks the model before and after you change how it's served.

ToolJobUse it when
NeMo EvaluatorRuns academic benchmarks, LLM-as-judge and custom evaluations against a model or endpointBefore rolling out a quantized or fine-tuned model; comparing two models on your task
NeMo CuratorGPU-accelerated data curation: exact, fuzzy and semantic deduplication, quality and safety filters, PII removalBuilding a pre-training or fine-tuning dataset at scale

Neighbours that exams use as distractors: NeMo Retriever provides embedding, reranking and extraction models for RAG. NeMo Guardrails adds input, dialog, retrieval, execution and output rails. Morpheus is for real-time cybersecurity pipelines.

Cutting the bill, biggest lever first

  1. Use a smaller model where evals allow (routing, cascade): often 5 to 10 × cheaper.
  2. Send fewer input tokens: RAG instead of whole documents, top 3 to 5 chunks, summarise old turns, load only the tools needed.
  3. Prompt caching for the fixed system prompt, tools and shared documents: 75 to 90% off those tokens.
  4. Cap output: short answers, JSON labels instead of explanations.
  5. Batch mode for anything that can wait: about 50% off.
  6. Response or semantic cache for repeated questions (check correctness and per-user data).
  7. Replace the LLM with a classifier on high-volume, fixed-label paths.

Saying it in an interview

"Let me estimate. 50K conversations a day, about 6 turns, and each turn sends roughly 5K tokens: 2K system prompt, 2K of retrieved chunks and some history, with about 250 tokens out. That's 1.5 billion input and 75 million output tokens a day. On a Flash-class model at roughly 30 cents in and $2.50 out per million, that's about $640 a day, or around $19K a month; on a Pro-class model, about four times that. To cut it, I'd cache the system prompt, route easy turns to a smaller model, and keep only the top chunks. If part of the traffic is fixed-label tagging at high volume, a small fine-tuned classifier does it for a few percent of the LLM cost."
