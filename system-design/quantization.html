Quantization

Storing a model's numbers with fewer bits, so it fits on fewer GPUs and answers faster, at a quality cost you measure.

The idea in one picture

A model is billions of numbers called weights. Quantization rounds each weight to the nearest mark on a coarser ruler, so each one takes fewer bits.

Two things make this work. Neural networks tolerate small errors in individual weights, because each output adds up thousands of them and the errors partly cancel. And most weights are small, so a well-chosen ruler covers nearly all of them finely.

Scale

Three lessons usually jump out:

  • 8-bit is nearly free: the error is a fraction of a percent.
  • 4-bit is where care starts: the error is visible, so how you choose the scale matters.
  • One outlier ruins a shared scale: it stretches the ruler, so every small weight in the row lands on zero. A separate scale per small group keeps the damage inside one group, which is why real 4-bit methods scale in groups of 64 to 128 weights.

How a weight becomes an integer

The common recipe, called symmetric round-to-nearest, takes three steps for each group of weights:

  1. Find the scale. Take the largest absolute weight in the group and divide it by the largest integer the format holds: 127 for 8-bit, 7 for 4-bit.
  2. Divide and round. Each weight ÷ scale, rounded to the nearest integer, is what gets stored.
  3. Multiply back when used. At run time, integer × scale gives an approximate weight.
scale = max|w| / 127  ·  q = round(w / scale)  ·  w′ = q × scale

Worked example in 8-bit: the group's largest weight is 0.98, so the scale is 0.98 / 127 = 0.00772. A weight of 0.4371 becomes round(56.6) = 57, stored in one byte, and comes back as 57 × 0.00772 = 0.440. The error is 0.003.

The scale itself is stored once per group, usually in 16 bits. With groups of 128, that adds about 0.13 bits per weight, so a "4-bit" model really uses about 4.1 to 4.5 bits per weight.

Why it makes models faster

When an LLM writes an answer, it produces one token at a time, and for each token the GPU reads every weight from memory. Reading memory, not doing arithmetic, is the slow part.

An 8B model inWeights to read per tokenFits on
16-bit16 GBA 24 GB GPU, with little room left for users
8-bit8 GBA 24 GB GPU, with room for the KV cache
4-bit≈ 4.5 GBA laptop GPU or a 16 GB card

Halve the bytes and each token needs half the reading, so single-user generation gets close to twice as fast. The memory you save also holds more KV cache, which lets the server batch more requests at once.

Formats

FormatBitsWhat it isTypical use
FP3232Full precision floating pointTraining maths, rarely serving
BF16 / FP1616Half precision; BF16 keeps FP32's rangeThe default serving format
FP8 (E4M3)8A tiny floating point number: 4 exponent bits, 3 mantissa bitsFast serving on GPUs with FP8 support; weights, activations and KV cache
INT88An integer plus a scaleWeights, and activations with SmoothQuant
INT44An integer from −8 to 7 plus a group scaleWeight-only, with GPTQ or AWQ; laptops and single GPUs
FP44A 4-bit floating point with block scalesNewest GPUs only

Floating-point formats like FP8 spend some bits on an exponent, so their marks are dense near zero and sparse far out, which suits weights that cluster near zero. Integer formats space marks evenly and rely on the scale. Which formats run fast depends on the GPU; see GPU generations.

What gets quantized

ChoiceSavesRisk
Weights only (W4A16, W8A16)Model memory and memory readsLowest; the maths still runs in 16-bit
Weights and activations (W8A8, FP8)Memory and compute, using low-precision tensor coresActivations have outliers, so it needs careful scaling
KV cache (FP8 or INT8 KV)Memory per token of context, so more users or longer contexts fitSmall; check long-context tasks

The shorthand W4A16 means 4-bit weights, 16-bit activations.

Methods

MethodHow it worksWhen
Round-to-nearest (RTN)The recipe above, with no data needed8-bit, where it's usually enough
GPTQQuantizes weights one at a time and adjusts the rest to cancel the error, using a small calibration set4-bit weight-only
AWQFinds the weights that matter most, from activations on calibration data, and protects them with per-channel scaling4-bit weight-only; robust across tasks
SmoothQuantMoves outliers from activations into weights so both fit 8-bitW8A8
Quantization-aware training (QAT)Simulates rounding during training or fine-tuning so the model learns to copeWhen post-training methods lose too much quality

Everything except QAT is post-training quantization (PTQ): it runs on a finished model in minutes to hours, with a few hundred calibration examples at most.

Checking quality

  • Measure on your own tasks. Run the same eval set on the 16-bit and the quantized model. Leaderboard averages hide task-specific drops.
  • Watch the fragile cases: maths and multi-step reasoning, long contexts, code, non-English text and strict output formats break first.
  • Check perplexity too. A jump in perplexity on held-out text is a quick early warning, though not proof that quality held.
  • Roll out like any model change: shadow traffic, then a canary, with a rollback ready.

Rule of thumb: 8-bit (FP8 or INT8) is close to lossless for most tasks. 4-bit with GPTQ or AWQ loses a little, more on small models. Below 4 bits, quality drops quickly.

Saying it in an interview

"Decoding is memory-bound: every token reads all the weights. Quantizing a 70B model from BF16 to FP8 halves that from 140 GB to 70 GB, so it fits on fewer GPUs, generates faster and leaves room for KV cache. I'd use FP8 on hardware that supports it, or 4-bit AWQ with group scaling when memory is tight, quantize the KV cache for long contexts, and only roll out after the eval set shows no regression on the tasks we care about."
