Three-Way Match Agent

Matches each invoice against its purchase order and goods receipt, holds anything that doesn't line up, and lets an agent investigate only the exceptions. Rules decide money, a person approves every outcome, and every component below links to its code and its low-level design.

The problem

Accounts payable pays an invoice only when three documents agree: what was ordered (purchase order), what arrived (goods receipt) and what was billed (invoice). Design a system that reads all three from PDFs, matches them, catches duplicates, fraud and prompt injection, and asks a person before anything is posted.

Functional: read POs, receipts and invoices from a document source; extract line items; match quantity, price and totals; flag duplicates and fake invoices; investigate exceptions with evidence; let a person approve, reject or escalate; record the outcome in the ERP.

NFRs: no LLM output can approve a payment; documents are untrusted data; every step is safe to run twice; every state change is logged and append-only; vendors (source, parser, LLM) are swappable; runs at close to $0 on free tiers.

Out of scope for v1: releasing payments, multi-currency, tax rules, credit notes, approval without a person.

Case lifecycle

One invoice is one case. Its state is a row in Postgres, and every move is a transaction that also writes an audit event and queues the next job, so a crash never loses or doubles a step.

Reading documents

PDF to typed data in four steps, each cached so a page is paid for once.

  1. Fetch: download the PO, receipt and invoice PDFs for an order from the Hugging Face Northwind datasets. A missing PO or receipt is None, not an error.
  2. Render: each page becomes a PNG inside 1664 × 2048, the parser's recommended size.
  3. Parse: Nemotron 3.5 Parse reads one page image per request and returns text with LaTeX tables. Picture blocks and layout tags are stripped.
  4. Extract: an LLM maps the text to a Document (order id, date, party, lines, total) at temperature 0. Pydantic validates it, and code checks it has as many lines as the parsed tables have rows. On either failure the problem goes back once, then the case goes to investigation.

Why two models: the parser has no structured output, so a second call does the mapping. The prompt says never calculate or guess a value, because a guessed total would hide the exact mismatch the matcher exists to catch. See chunking for parsing trade-offs.

Cross-check: every amount in the PDF's own text layer must also appear in the parsed text. On invoice 11077 Nemotron dropped the $1,374.60 total; the check reports it, and extraction correctly leaves the total empty rather than inventing it (step 01.8).

Matching rules

The matcher is plain code. Lines are joined by a normalised product name, prices compare with a 0.01 tolerance, and any exception means the case is not approved.

CodeFires when
missing_po · missing_receiptThe document isn't found
not_on_poInvoiced but not ordered
quantity_vs_poInvoiced quantity differs from ordered
price_missing · price_vs_poA unit price is absent, or differs from the PO by more than 0.01
not_received · quantity_vs_receiptInvoiced but not received, or more invoiced than received
total_mismatchThe invoice total is missing, or lines don't add up to it

The resolution agent

Planned. It runs only in INVESTIGATING, for one case, with at most 8 tool calls and a fixed token budget. Hitting a limit hands the case to a person with what it found so far.

Tool (read-only)Purpose
get_case · get_document_text · get_pdf_text_layerLook at the evidence
get_po · get_receipts · get_vendorFetch current ERP records
reread_pageRepeat a read at higher resolution
search_past_casesSimilar resolved cases from pgvector memory
rerun_matchRerun the matcher on a correction that comes from a second source

Output is a validated Proposal: root cause, cited evidence, recommended action, confidence. An evidence check rejects any proposal whose cited values aren't in the case data. Built on LangGraph for this one loop only; step 7.1 first checks the NVIDIA model can call tools. Memory is written only when a person closes a case, so a malicious invoice can't teach a bad precedent (agent memory).

Queue, retries and scale to zero

The queue lives in the same Postgres as the cases (pgmq), so a state change and its next job commit together. Nothing runs when there is no work.

  1. Supabase Cron runs each minute and checks in SQL whether a job is visible or a due_at timer has passed.
  2. Only then does it POST to /internal/drain through pg_net, with the bearer token from Supabase Vault.
  3. Cloud Run starts. drain() first turns due timers into jobs, then reads batches of 10 with a 60 s visibility timeout.
  4. Each job names the state it was queued for. The handler locks the case row and runs the step only if the case is still in that state, so a repeat delivery does nothing.
  5. A failed job becomes visible again after 2n × 10 s. After 5 attempts it moves to jobs_dlq.
  6. The drain stops when the queue is empty or after DRAIN_SECONDS (50 s in production), and the instance scales to zero.

See message queues for delivery guarantees and the outbox pattern.

Approval and execution

Planned. A person reviews every case in v1. The agent proposes; a separate executor acts, and only with a valid approval.

  1. The review page (FastAPI, Jinja2, HTMX, same service) shows the invoice, evidence, signals, the agent's reasoning and the exact action.
  2. The approval stores a hash of the action, the approver and an expiry, and commits with an outbox row.
  3. The executor recomputes the hash, re-reads the PO and invoice, and stops if either changed.
  4. It writes erp_postings with idempotency key case_id:action, reads it back, and closes the case.

Approvers have amount limits and can't approve a case they raised. Unanswered cases escalate and never approve themselves.

Saying it in an interview

"It's a workflow, not an agent, because the steps are known: read, screen, extract, check, match, approve, post. A Postgres state machine runs it, with the queue in the same database so a state change and its next job commit together, and every step is idempotent. Rules decide money; the LLM only reads documents and, for exceptions, investigates with read-only tools and proposes. A person approves an action hash, and a separate executor writes to the ERP with an idempotency key and reads it back. It scales to zero: a cron checks for due work in SQL before waking Cloud Run."
