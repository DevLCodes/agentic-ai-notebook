At a glance

A single agent is one loop with one context window. A multi-agent system is several loops, each with its own prompt, tools and context, plus rules for who runs next and how results come back.

Think of a research desk. One researcher reading 300 pages ends up with a desk buried in paper and forgets what was on page 12. A lead who sends three researchers off with clear questions, and gets back one page from each, can think clearly about the answer. That is the whole idea: workers absorb the reading, the lead sees only the summaries. The cost is that every researcher is paid, and every summary loses some detail.

Why and when to go multi-agent

Start with one agent and good tools. Add agents only when you can name the problem they solve. There are four good reasons:

  • Context isolation. Each worker reads hundreds of pages or files in its own context window and returns a short report, so no single context overflows or rots with stale detail.
  • Parallelism. Independent parts run at once: three searches that each take 40 seconds finish in about 40 seconds, not 120.
  • Different tools or permissions. Only the billing agent holds the refund tool; the research agent is read-only. Least privilege per agent is easier to audit than one agent with every tool.
  • Independent checking. A reviewer that did not write the draft, ideally with different context or a different model, catches errors the author repeats.

And three costs that are easy to underrate:

  • Tokens. Anthropic reported that agents use about 4× the tokens of a chat, and its multi-agent research system about 15×. The task must be worth that. See Numbers for prices.
  • Lost detail and compounding errors. Every brief and every report is a summary. One misleading brief sends a worker down the wrong path, and the lead may never notice.
  • Debugging. A wrong answer can come from any agent or any hand-off. Without traces that span agents (one trace ID, a span per agent and tool call), you can't tell which.

Rule of thumb: split by context, not by job title. Multi-agent pays off for broad, parallel, read-heavy work (research, reviewing many files, comparing many options). It hurts tightly coupled work where each step needs everything the last step saw, such as most edits inside one codebase.

The supervisor / orchestrator-worker pattern

One lead agent (the supervisor or orchestrator) owns the task. It plans, writes a brief for each worker, starts workers (often in parallel), reads their reports, decides whether more work is needed, and writes the answer. Workers never talk to each other or to the user: every message goes through the supervisor, which gives one place to log, retry, enforce budgets and decide what each worker sees.

plan    = lead.plan(question)                    # how many parts, how much effort
reports = parallel(worker.run, [lead.brief(p) for p in plan.parts])
while lead.gaps(reports) and rounds < MAX_ROUNDS:   # follow-up round, capped
    reports += parallel(worker.run, lead.follow_ups(reports))
answer  = lead.merge(question, reports)          # see "merge the findings"

The brief is the interface

A worker starts with an empty context: it knows only its brief. The most common failure is a vague brief, which makes workers duplicate each other, drift off topic or stop too early. A good brief has five parts:

PartExampleMissing it causes
ObjectiveMonthly cost of 50M 1,536-dim vectors with p95 search under 100 msThe worker guesses what "cost" means
Output formatClaims with source, date and confidence, plus a "not found" listEssays that are hard to merge
Tools and sourcesVendor pricing pages; ignore forum posts before 2025Old or weak sources quoted as fact
BoundariesSearch quality and migration are other workers' jobsOverlap, and a topic nobody covers
Effort budgetAbout 10 tool calls; stop when three sources agreeOne search, or sixty

Scale effort to the question

Supervisors tend to over-spawn. Anthropic's research agent puts explicit rules in the lead's prompt: a simple fact needs one agent and 3 to 10 tool calls; a direct comparison needs 2 to 4 workers with 10 to 15 calls each; complex research may use more than 10 workers with clearly divided responsibilities.

Parallel or sequential: run workers in parallel when their parts are independent; run them in order when one needs another's result ("find the top three vendors", then "price each vendor"). A supervisor often does one parallel round, reads the reports, then a smaller follow-up round. This is plan-and-execute with agents as the executors.

Network, hierarchical and handoff patterns

Every topology answers the same question differently: who decides which agent runs next?

Network (peer to peer)

Agents call each other directly and each decides who goes next, often through a shared message channel (AutoGen-style group chats are close to this). It suits open-ended work where the order can't be planned, such as a writer, critic and fact-checker passing a draft around. Costs: no single owner of the answer, conversations that loop, and traces that are hard to follow. Add a hop or turn limit, a termination condition (a "done" message or a judge), and one agent responsible for the final output.

Hierarchical

A top supervisor manages team leads, and each lead runs its own workers. It is how you scale past the point where one supervisor's context fills with too many reports, and it mirrors real team boundaries (legal review, financial review, technical review). Costs: each layer summarises, so detail fades like a game of telephone, and latency and tokens add up per layer. Use it only when the sub-teams are genuinely separate, and let leads return structured reports so the director's merge stays mechanical.

Handoff (transfer of control)

The active agent passes the conversation to a specialist, usually by calling a tool such as transfer_to_billing. Only one agent works at a time, and the specialist talks to the user directly; there is no boss waiting for a report. It is the natural shape for support and service desks: a triage agent routes, specialists act. The OpenAI Agents SDK calls these handoffs; LangGraph builds the same thing with a router node and Command transfers.

transfer_to_billing({
  "customer_id": "C-2291",
  "goal": "refund a duplicate charge of $49 on 3 Nov",
  "verified": true,                      # identity already checked by triage
  "tried": ["confirmed both charges in the ledger"],
  "reason": "refunds need the billing tool"
})

Pass a structured handoff note like this, not just the raw transcript, so the specialist doesn't re-ask the customer. Give the specialist a way to hand back, and cap the number of transfers per conversation to stop ping-pong. Unlike routing, which picks a model or path for one request, a handoff moves the whole conversation and its ownership.

Shared state, memory and message passing

Agents need to know what other agents found. There are two basic designs, and most systems mix them.

Message passingShared state (blackboard)
How it worksAgents send explicit messages: a brief down, a report backAll agents read and write one shared object, such as a graph state or a scratchpad
Each agent seesOnly what it was sentEverything on the board
Good atContext isolation, clear ownership, easy tracingAdding agents without rewiring; agents reacting to each other's progress
RiskThe sender decides what the receiver missesLost updates, context bloat, everyone reading everything
ExamplesSupervisor and worker reports; handoff notesLangGraph state with reducers; a shared task list or plan file

Three layers of memory

  • Short-term: one agent's messages list, sent in full on every call and bounded by its context window. It is private to that agent. The window is a token limit, not storage, and is not the same as the GPU's KV cache; see where the context window lives.
  • Shared working memory: the plan, open questions and findings for one job, kept outside any single context so the supervisor can reload it if its own context fills or the job restarts. Checkpoint it, as described in agent memory.
  • Long-term: facts that outlive the job (user preferences, past decisions), in a database or vector store, read and written through explicit tools. See Agent memory.

Concurrent writes

Two parallel workers that each read a shared list, add an item and write the whole list back will lose one item: the second write replaces the first. Pick one of these fixes. Try each below.

Write strategy

Pass references, not contents. A worker that produced a 20-page result saves it to a file or object store and returns the path or ID with a short summary. The supervisor's context stays small, and the full result is one tool call away. Anthropic describes workers writing to a filesystem and passing lightweight references for this reason.

Case: merge the findings

Three workers have reported on "should we move search from Elasticsearch to a vector database?". The merge decides whether the team was worth its tokens.

WorkerReported
CostManaged vector DB about $3,000/month for 50M vectors (vendor pricing page, 2026). Self-hosted about $1,800/month plus ops time. Not found: egress costs.
QualityHybrid search beat keyword-only on our test set. Managed vector DB about $5,000/month (blog post, 2023). Recall depends on index settings.
MigrationRe-embedding 50M documents takes about 2 days of batch jobs. Both options support hybrid search. Not found: rollback plan.

The reports overlap (hybrid search twice), disagree ($3,000 against $5,000) and leave gaps (egress, rollback). Pick a merge strategy:

Merge by

  1. Deduplicate claims, keeping every source that supports each one.
  2. Resolve conflicts on evidence: a primary source over a secondary one, newer over older, a number with its conditions over a bare number. If you can't resolve a conflict, show both and say why.
  3. Carry citations from worker to final answer. A separate citation or verification pass checks each claim against its source; see Citations.
  4. Name the gaps, then send a capped follow-up round or tell the user what is unknown.
  5. Answer the question asked, not "here is everything we found".

Merging is far easier when the brief fixes the report format: a list of claims, each with source, date and confidence, plus a "not found" list. Then deduplication and conflict detection are mostly code, and the model only judges the conflicts.

Saying it in an interview

"I'd start with one agent and only split when the work is broad and parallel, because multi-agent costs several times the tokens. For research I'd use a supervisor: it plans, writes each worker a brief with an objective, an output format, sources, boundaries and a budget, runs the workers in parallel with their own contexts, and merges structured reports: dedupe, resolve conflicts on source quality and date, keep citations, and name the gaps for a capped follow-up round. For support I'd use handoffs from a triage agent to specialists, with a structured handoff note and a transfer cap. Shared state goes in a checkpointed store with append-only reducers so parallel writes can't overwrite each other, big results are passed by reference, and every agent shares one trace ID so I can debug the whole team."
