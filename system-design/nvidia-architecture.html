The stack

Three layers, each with one job. NIM packages the model, Triton schedules requests, and TensorRT-LLM runs the maths on the GPUs. Then follow one request through them in 3D.

That is the stack at rest. Below, follow one request as it moves through it.

LayerJobWhat you tune
NIMA container with the model, an optimized engine for your GPU and an OpenAI-compatible APIWhich model and profile (precision, GPU count)
Triton Inference ServerTakes requests, queues and batches them, runs model instances, exposes metricsBatching delay and sizes, instance count, ensembles
TensorRT-LLMCompiles and runs the LLM with fused GPU kernelsPrecision, parallelism, max batch and sequence length, KV cache size
CUDANVIDIA's GPU programming model; everything above runs on itRarely touched directly in an agent system

NIM

NVIDIA Inference Microservices (NIM) put a model behind a stable HTTP address, so an agent calls a model the same way it calls any other service.

Each NIM is a container holding a model, an inference engine tuned for NVIDIA GPUs and an API server. At start-up it detects the GPUs and picks a matching profile, such as FP8 with tensor parallelism of 4 on four H100s.

NIM versionInference backend
1.xSeveral backends bundled in one container, with TensorRT-LLM as the optimized default. Most course and exam material describes this.
2.x"One container, one backend": each image ships a single engine, so images stay small and predictable. 2.0 uses vLLM; 2.1 offers vLLM or SGLang images, with NVIDIA optimizations.
3.xRuns alongside 2.x, for distributed inference built on NVIDIA Dynamo.

The levers below, paged KV cache, in-flight batching, FP8 and tensor parallelism, exist in all of these engines. Check the NIM documentation for the version you deploy.

OpenAI-compatible: change the base URL, keep your code

A NIM speaks the same request and response format as the OpenAI API. Code written with the OpenAI Python SDK only needs a different base_url, an NVIDIA API key and a model name:

from openai import OpenAI
import os

client = OpenAI(
    base_url="https://integrate.api.nvidia.com/v1",   # NVIDIA-hosted NIMs
    api_key=os.environ["NVIDIA_API_KEY"],
)
resp = client.chat.completions.create(
    model="meta/llama-3.1-8b-instruct",               # pick per latency or accuracy need
    messages=[{"role": "user", "content": "Classify this support ticket."}],
)
  • Routes: the usual OpenAI ones, /v1/chat/completions to run a turn and /v1/models to list what's available.
  • Self-hosted: run the same NIM container on your own GPUs and point base_url at it. Moving a model from hosted to self-hosted is a configuration change, not a rewrite.
  • Two sizes, one interface: a small model (about 8B) for routing, classification and high-volume tool calls where latency matters; a large one (about 70B) for hard reasoning and final answers. Only the model string changes.
>

The hosted catalog changes often. On 19 November 2026 neither of these two Llama models was listed on integrate.api.nvidia.com/v1/models, so list the models before you hard-code one. The pattern, not the model name, is what exams test.

Triton Inference Server

Triton is NVIDIA's general model server. It serves many frameworks through backends (TensorRT, TensorRT-LLM, PyTorch, ONNX Runtime, Python) over HTTP and gRPC, with Prometheus metrics.

Dynamic batching

Triton's scheduler waits up to a set delay to group requests that arrive together, then runs them as one batch. Use it for models whose work has a fixed size, such as embedders, rerankers and classifiers. Batching compares it with static and in-flight batching.

# config.pbtxt for an embedding model
dynamic_batching {
  preferred_batch_size: [ 8, 16 ]
  max_queue_delay_microseconds: 200
}
instance_group [ { count: 2, kind: KIND_GPU } ]

For LLMs, Triton hands batching to the TensorRT-LLM backend, set with batching_strategy: inflight_fused_batching, because output lengths vary too much for request-level batches.

Concurrent model execution

instance_group runs several instances of a model, or several models, on the same GPU at once. Each instance gets its own CUDA stream, so their work can overlap. It helps small models that can't fill the GPU alone; a large LLM already saturates it.

Ensembles and BLS

An ensemble chains models into one server-side pipeline, such as tokenizer, then model, then detokenizer, with no client round trips between steps. Business Logic Scripting (BLS) does the same with Python control flow.

TensorRT-LLM engine

TensorRT-LLM is NVIDIA's open-source library for running LLMs fast on its GPUs. It produces an engine for a specific GPU type, precision, parallelism and maximum batch and sequence length.

  • Fused kernels: several operations in one GPU pass, cutting memory reads.
  • Quantization: FP8, INT8 and INT4 (AWQ) weights, and an FP8 KV cache.
  • Scheduling: in-flight batching and a paged KV cache with block reuse.
  • Parallelism: tensor, pipeline and expert parallelism across GPUs over NVLink.
  • Speculative decoding: draft-model, Medusa and EAGLE methods to cut latency per token.

Engines are tied to a GPU architecture, so an H100 engine won't run on an L40S. NIM hides this by shipping several engines and choosing one at start-up.

Serving levers on one GPU pool

Most of what makes self-hosted serving affordable comes from four levers inside the inference engine, whether that is TensorRT-LLM, vLLM or SGLang. Turn them on and off for a 70B model on 80 GB H100s.

  • PagedAttention (paged KV cache): the KV cache lives in small fixed-size blocks instead of one big reserved buffer, so memory isn't stranded and more conversations fit. More
  • In-flight (continuous) batching: a finished request frees its slot at the next token step, and a waiting one fills it at once. More
  • FP8 on Hopper: roughly halves weight and activation memory compared with FP16, with little accuracy loss. Lower-bit methods (AWQ, GPTQ, INT8, INT4) shrink further. FP64 is for scientific computing, never for serving. More
  • Tensor parallelism: shards every layer across GPUs in one server over NVLink, so a model too big for one card fits. Pipeline parallelism instead places groups of layers on different GPUs and can span servers. More
>

Illustrative numbers: 140 GB of FP16 weights, a KV cache of 24 GB reserved without paging or about 6 GB with it for the same conversations, and 3 GB of activations and overhead. The throughput multipliers show direction, not a benchmark.

Worked example: one agent, two model tiers

A support agent where most turns are simple lookups and a minority need real reasoning:

  1. Cheap tier, hosted. Send simple turns to a small model on a hosted NIM endpoint. Per-token pricing suits a bursty long tail, and you run no GPUs.
  2. Hard tier, self-hosted. Run a 70B model on your own H100s. FP16 overflows one 80 GB card, so turn on FP8 and it fits on one. PagedAttention and in-flight batching then let that card serve many conversations at once.
  3. One interface. Both tiers speak the OpenAI-compatible NIM API, so the agent code is the same and a router only picks base_url and model.
  4. Durable conversations. Give the agent a shared checkpoint store, such as Postgres, and a thread_id per user, so a pod restart on the GPU tier resumes the conversation instead of losing it. See Agent memory: surviving restarts.

If the small model really handles 70 to 80% of turns, total inference cost drops sharply, often quoted as 60 to 80%. Measure your own split and quality before you count on it.

CUDA and streams

CUDA is NVIDIA's way of running code on its GPUs. A CUDA stream is a queue of GPU work. Work in one queue runs in order; work in different queues can run at the same time.

Serving one request on a GPU takes three kinds of work: copy the input from the server's memory to the GPU, run the model (the GPU's compute units, through functions called kernels), and copy the result back. The GPU has separate hardware for copying and for computing, so they could run at the same time, but only if the work sits in different streams.

  • One stream: request 2 can't start copying until request 1 has finished everything. The compute units sit idle during every copy.
  • Several streams: request 2 copies in while request 1 computes. Copy and compute overlap, and the GPU stays busy.
  • Small models: one model's kernel may use only part of the GPU. With several streams, two instances' kernels can run side by side. This is what Triton's instance_group count does: each model instance gets its own stream.
>

NCCL is the library that moves data between GPUs for tensor parallelism: over NVLink inside a server, and over InfiniBand or Ethernet between servers. TensorRT-LLM runs that communication on its own streams so it overlaps with compute.

Sharing a GPU: MIG, MPS and time-slicing

When each model or team needs much less than a whole GPU, give them a share of one instead of a GPU each. The three ways differ in how well one tenant is protected from another.

MethodHow it sharesMemory isolationUse it when
MIG (Multi-Instance GPU)Splits the GPU in hardware into up to 7 instances, each with its own memory and computeYes: one tenant's out-of-memory error can't touch anotherDifferent teams or customers need guaranteed, isolated shares (A100, H100, H200 and newer)
MPS (Multi-Process Service)Lets several processes run kernels on the GPU at the same timePartial: memory limits can be set, but a crash can affect every clientSeveral trusted processes of one team that each underuse the GPU
Time-slicingTakes turns on the whole GPUNo: everyone shares one memory spaceDev and test, or low-traffic jobs where isolation doesn't matter

In Kubernetes, the NVIDIA device plugin exposes each MIG instance as a schedulable resource, such as nvidia.com/mig-3g.40gb, and resource quotas per namespace guarantee each team its slices.

>

The rule of thumb: much smaller than a GPU and needs isolation → MIG. Fits one GPU → one GPU per replica. Bigger than one GPU → quantize or split it. MIG never joins GPUs together; a model that needs more than 80 GB can't use it.

GPU generations and FP8

ArchitectureExample GPUsLowest tensor-core precision
AmpereA100, A10INT8 (no FP8)
Ada LovelaceL4, L40SFP8
HopperH100, H200FP8
BlackwellB200, GB200FP4

FP8 halves weight memory compared with BF16 on any GPU, but only GPUs with FP8 tensor cores run it faster (see Quantization for how the formats work). On an A100, an FP8 checkpoint saves memory without the speed-up.

Validate the quantized model with your eval set before rollout, for example with NeMo Evaluator, and keep a second replica so cost savings never come out of availability.

NeMo tools

These sit around serving. Exams test which tool does which job, and use the others as wrong answers.

ToolJobUse it when
NeMo EvaluatorRuns academic benchmarks, LLM-as-judge and custom evaluations against a model or endpointBefore rolling out a quantized or fine-tuned model; comparing two models on your task
NeMo CuratorGPU-accelerated data curation: exact, fuzzy and semantic deduplication, quality and safety filters, PII removalBuilding a pre-training or fine-tuning dataset
NeMo RetrieverEmbedding, reranking and extraction models for RAG, served as NIMsBuilding the retrieval side of an agent
NeMo GuardrailsInput, dialog, retrieval, execution and output rails, written in ColangKeeping an agent on topic and its tool calls safe
NeMo Agent ToolkitBuilds, profiles and evaluates agent workflows from config; exports traces to OpenTelemetry backendsInstrumenting and comparing agent workflows
MorpheusReal-time cybersecurity pipelines, such as phishing and PII-leak detectionSecurity streams, not agent serving

Check yourself

Your agent uses the OpenAI Python SDK against OpenAI. What is the minimal change to call an NVIDIA-hosted NIM model?

Override base_url to https://integrate.api.nvidia.com/v1, authenticate with NVIDIA_API_KEY, and set the model string. Everything else stays the same, because NIM is OpenAI-compatible. You don't need a NIM-specific client or route.

A 70B model in FP16 won't fit on one 80 GB H100, and the sharding traffic must stay on the fast local link. What fits, and what shrinks the footprint first?

FP8 on H100 first roughly halves the memory, to about 70 GB of weights. If you still need to split, use tensor parallelism inside one server over NVLink. Pipeline parallelism is for crossing servers. MIG only divides a GPU; it never combines GPUs into a bigger one.

Three teams' small models share H100s, and one team's job crashes another with out-of-memory errors. What isolates them without a GPU each?

MIG instances, which give each team its own memory and compute in hardware, plus per-namespace resource quotas in Kubernetes that guarantee each team its slices. Time-slicing shares one memory space, so it doesn't stop the crashes.

Why would two CUDA streams finish four requests sooner than one stream?

The GPU has separate hardware for copying data and for computing. With one stream, every copy waits for the previous request's compute to finish. With two streams, one request copies while another computes, so the compute units stay busy.

Exam patterns

  • Bursty, variable-length LLM traffic → in-flight batching plus paged KV cache in TensorRT-LLM.
  • Fixed-size models such as embedders → Triton dynamic batching.
  • Small model, idle GPU → more Triton instances (concurrent execution).
  • Cut serving cost → FP8 on Hopper, Ada or Blackwell, validated with an eval and with redundancy kept.
  • Deduplicate training data → Curator. Score a model → Evaluator. Retrieval models → Retriever. Rails → Guardrails.
