NVIDIA inference architecture

The stack

Three layers, each with one job. NIM packages the model, Triton schedules requests, and TensorRT-LLM runs the maths on the GPUs.

LayerJobWhat you tune
NIMA container with the model, an optimized engine for your GPU and an OpenAI-compatible APIWhich model and profile (precision, GPU count)
Triton Inference ServerTakes requests, queues and batches them, runs model instances, exposes metricsBatching delay and sizes, instance count, ensembles
TensorRT-LLMCompiles and runs the LLM with fused GPU kernelsPrecision, parallelism, max batch and sequence length, KV cache size
CUDANVIDIA's GPU programming model; everything above runs on itRarely touched directly in an agent system

NIM

NVIDIA Inference Microservices are prebuilt containers. Each holds a model, engines prebuilt for several GPU types and precisions, and an OpenAI-compatible HTTP API. At start-up NIM detects the GPUs and picks a matching profile, such as FP8 with tensor parallelism of 4 on four H100s.

  • Agents call a NIM like any OpenAI-style endpoint, so swapping a hosted model for a self-hosted one changes a base URL, not code.
  • The same NIM runs on NVIDIA's hosted API catalog for prototyping and on your own GPUs for production.
  • NIMs exist for LLMs and also for embedding, reranking, speech and safety models such as the NemoGuard content-safety, topic-control and jailbreak-detection models.

Triton Inference Server

Triton is NVIDIA's general model server. It serves many frameworks through backends (TensorRT, TensorRT-LLM, PyTorch, ONNX Runtime, Python) over HTTP and gRPC, with Prometheus metrics.

Dynamic batching

Triton's scheduler waits up to a set delay to group requests that arrive together, then runs them as one batch. Use it for models whose work has a fixed size, such as embedders, rerankers and classifiers. Batching compares it with static and in-flight batching.

# config.pbtxt for an embedding model
dynamic_batching {
  preferred_batch_size: [ 8, 16 ]
  max_queue_delay_microseconds: 200
}
instance_group [ { count: 2, kind: KIND_GPU } ]

For LLMs, Triton hands batching to the TensorRT-LLM backend, set with batching_strategy: inflight_fused_batching, because output lengths vary too much for request-level batches.

Concurrent model execution

instance_group runs several instances of a model, or several models, on the same GPU at once. Each instance gets its own CUDA stream, so their work can overlap. It helps small models that can't fill the GPU alone; a large LLM already saturates it.

Ensembles and BLS

An ensemble chains models into one server-side pipeline, such as tokenizer, then model, then detokenizer, with no client round trips between steps. Business Logic Scripting (BLS) does the same with Python control flow.

TensorRT-LLM engine

TensorRT-LLM is NVIDIA's open-source library for running LLMs fast on its GPUs. It produces an engine for a specific GPU type, precision, parallelism and maximum batch and sequence length.

  • Fused kernels: several operations in one GPU pass, cutting memory reads.
  • Quantization: FP8, INT8 and INT4 (AWQ) weights, and an FP8 KV cache.
  • Scheduling: in-flight batching and a paged KV cache with block reuse.
  • Parallelism: tensor, pipeline and expert parallelism across GPUs over NVLink.
  • Speculative decoding: draft-model, Medusa and EAGLE methods to cut latency per token.

Engines are tied to a GPU architecture, so an H100 engine won't run on an L40S. NIM hides this by shipping several engines and choosing one at start-up.

CUDA and streams

CUDA is NVIDIA's platform for running code on its GPUs. Work is written as kernels, functions run by thousands of threads at once, and launched onto CUDA streams.

  • Work in one stream runs in order.
  • Work in different streams can overlap, such as copying the next batch to the GPU while the current one computes.
  • Triton's concurrent instances and TensorRT-LLM's overlapping of compute and communication both rely on multiple streams.

NCCL handles GPU-to-GPU communication for tensor parallelism, over NVLink inside a node and InfiniBand or Ethernet between nodes.

GPU generations and FP8

ArchitectureExample GPUsLowest tensor-core precision
AmpereA100, A10INT8 (no FP8)
Ada LovelaceL4, L40SFP8
HopperH100, H200FP8
BlackwellB200, GB200FP4

FP8 halves weight memory compared with BF16 on any GPU, but only GPUs with FP8 tensor cores run it faster (see Quantization for how the formats work). On an A100, an FP8 checkpoint saves memory without the speed-up.

Validate the quantized model with your eval set before rollout, for example with NeMo Evaluator, and keep a second replica so cost savings never come out of availability.

NeMo tools

These sit around serving. Exams test which tool does which job, and use the others as wrong answers.

ToolJobUse it when
NeMo EvaluatorRuns academic benchmarks, LLM-as-judge and custom evaluations against a model or endpointBefore rolling out a quantized or fine-tuned model; comparing two models on your task
NeMo CuratorGPU-accelerated data curation: exact, fuzzy and semantic deduplication, quality and safety filters, PII removalBuilding a pre-training or fine-tuning dataset
NeMo RetrieverEmbedding, reranking and extraction models for RAG, served as NIMsBuilding the retrieval side of an agent
NeMo GuardrailsInput, dialog, retrieval, execution and output rails, written in ColangKeeping an agent on topic and its tool calls safe
NeMo Agent ToolkitBuilds, profiles and evaluates agent workflows from config; exports traces to OpenTelemetry backendsInstrumenting and comparing agent workflows
MorpheusReal-time cybersecurity pipelines, such as phishing and PII-leak detectionSecurity streams, not agent serving

Exam patterns

  • Bursty, variable-length LLM traffic → in-flight batching plus paged KV cache in TensorRT-LLM.
  • Fixed-size models such as embedders → Triton dynamic batching.
  • Small model, idle GPU → more Triton instances (concurrent execution).
  • Cut serving cost → FP8 on Hopper, Ada or Blackwell, validated with an eval and with redundancy kept.
  • Deduplicate training data → Curator. Score a model → Evaluator. Retrieval models → Retriever. Rails → Guardrails.
