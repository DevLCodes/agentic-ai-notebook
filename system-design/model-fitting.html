Fitting a model on GPUs: shrink, split or share

A model either fits on one GPU, is too big for one, or is much smaller than one. Each case has its own answer: quantize it, split it with tensor or pipeline parallelism, or share the GPU.

Three situations

First work out how much memory the model needs, then compare it with one GPU.

memory ≈ parameters × bytes per weight + KV cache for all active users + activations and overhead (~2 GB)

A 70B model in BF16 needs 70 billion × 2 bytes = 140 GB for its weights alone. An 80 GB GPU can't hold it. Then there are three situations:

SituationExampleAnswer
Too big for one GPU70B in BF16 on 80 GB GPUsShrink it with quantization if quality allows; otherwise split it across GPUs with tensor or pipeline parallelism
Fits on one GPU8B in BF16 (16 GB) on an 80 GB GPURun one copy per GPU and add copies (replicas) for more users. Splitting would only add communication
Much smaller than one GPUThree teams each need 15 GB on one 80 GB GPUShare the GPU: cut it into isolated slices so one tenant can't run another out of memory (GPU partitioning)

Try it: fit the model

Pick a model, a precision and a GPU, then add GPUs and choose how to split. The layers fly out of the model into the GPUs, and each glass card fills with what it holds. The line under the scene says what you'd recommend in a design review.

Things to try:

  • 70B, BF16, 1 GPU: red spills out of the card, about 67 GB too much. Click FP8 and watch the stripes shrink until it fits. Then click Show me the recommendation.
  • Tensor vs pipeline at 4 GPUs: the fill height is the same, but look inside. Tensor parallel gives every GPU a thin slice of every colour, and the purple pulse never stops. Pipeline parallel gives each GPU two whole colours, and a single gold token leaves three GPUs dark. Raise users and the dark GPUs light up.
  • 405B, BF16, 16 GPUs: a second server appears. With tensor parallel the pulse turns red and slows as it crosses the network cable. Switch to pipeline parallel between servers.
  • 8B, INT4, 141 GB GPU: a sliver of colour at the bottom of a huge card. That's the case for sharing the GPU, not splitting the model.

Tensor parallelism

Every layer is cut into N slices, one per GPU. For each token, all GPUs compute their slice of layer 1 at the same time, combine the partial results (an all-reduce), then move to layer 2.

  • Use it when: the model doesn't fit on one GPU and you want low latency per request. It's the default way to split a model inside one server.
  • Limit: keep it inside one server (usually up to 8 GPUs). Between servers the network is far slower than the GPU-to-GPU link, and the per-layer traffic stalls everything.

Pipeline parallelism

The layers are cut into N consecutive stages, one per GPU, like an assembly line. GPU 1 runs layers 1–20 and hands its result to GPU 2 for layers 21–40, and so on.

  • Use it when: the model needs more GPUs than one server has, or the GPUs only have a slow link between them.
  • Limit: it doesn't speed up a single request, because each token still passes through every stage in turn. It needs many concurrent requests to fill the pipeline.
  • Combined: very large models use both, tensor parallel inside each server and pipeline parallel between servers.

What to try first

  1. Does it fit on one GPU with room for the KV cache your users need? Then don't split it. Add replicas for more users.
  2. Would 8-bit make it fit? Quantize to FP8 or INT8 and check your eval set. One GPU at FP8 is usually cheaper and simpler than two at BF16.
  3. Still too big, or quality must not move? Use tensor parallelism inside one server, with the smallest GPU count that leaves enough KV cache.
  4. Bigger than one server? Add pipeline parallelism between servers.
  5. Much smaller than one GPU? Share the GPU between several models or tenants with isolated slices, or use a smaller GPU.

Saying it in an interview

"70B in BF16 is 140 GB of weights, so it can't sit on one 80 GB GPU. If an FP8 checkpoint passes our eval set, it's 70 GB and fits on one GPU, which is the cheapest option. If quality must stay at BF16, I'd use tensor parallelism of 4 inside one 8-GPU server: about 35 GB of weights per GPU and plenty of room for KV cache. I'd only add pipeline parallelism if the model outgrew one server. And for several small models from different teams, I'd partition GPUs into isolated slices rather than give each team a whole GPU."
