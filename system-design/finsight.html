FinSight: a Research Assistant over SEC Filings

Analysts ask questions about public companies: exact figures, calculations such as margins and ratios, and summaries of risks and management’s discussion. Design a system that answers from SEC filings, with every number correct and every claim cited.

Requirements

  • Clarify

Ask what the answers look like before anything else. A number, a calculation and a summary need different machinery, and the mix decides where the effort goes.

Architecture

  • Whole system

Two sources from the same SEC system feed two paths: filing documents become chunks for retrieval, and XBRL facts become rows for exact numbers. A filings ledger drives ingestion, and evals sit behind everything.

ComponentJobWhy this way
Filings ledger (Postgres)One row per filing: status, retries, raw locationThe queue between stages; compare-and-set makes every stage safe to rerun
Raw storeImmutable copy of each filingRe-parse or re-chunk without going back to a rate-limited upstream
Parser and chunkerSections, tables with units and periods, chunks with metadataFiling structure (Items, tables) is what retrieval filters and citations need
pgvector (HNSW)Chunk text, metadata and a 384-number vector per chunkOne database for ledger, facts and vectors; SQL filters and joins
financial_factsEvery XBRL-tagged number with period, unit and filingExact values with free citations; no retrieval needed for most numeric questions
Planner (local LLM)Turns a question into company, line items, years, formulaThe only model call on the numbers path; everything after it is code
EvalsIngestion, numbers and retrieval scores per runEach design change is judged against the last run, not by eye

Ingestion and the ledger

  • Pull-only upstream
  • Idempotent

Discover first, then fetch

Discovery asks EDGAR for a company’s filing list and writes one ledger row per filing, keyed by its accession number. Fetching then works through rows in DISCOVERED. Listing 100k filings takes seconds; downloading them at 10 requests per second takes hours, so the slow part has to be resumable and countable.

Every move is a compare-and-set

update filings set status = 'FETCHED', raw_uri = …, content_sha256 = …
where accession = '0000320193-25-000079' and status = 'DISCOVERED'

A stage only moves a filing forward if it is still where that stage expects it. A crash, a rerun or a second worker can’t process the same filing twice. A failure leaves the row in place with retry_count + 1; after three, it is skipped and shows up in the status report.

Store raw first

The downloaded HTML is written once to raw/{cik}/{accession}/{doc}, the same key layout as an S3 bucket, and never overwritten. This paid off three times during the build: each parser bug fix replayed every filing with zero EDGAR calls.

Freshness without webhooks

EDGAR has no push. The fast path polls the latest-filings feed; because that feed only shows the most recent entries, a burst can scroll filings past between polls. The daily index lists every filing for the day, so a reconcile job compares it with the ledger and adds anything missed. Accession numbers make the two paths safe to overlap.

Parsing and chunking

  • Structure
  • Metadata

From HTML to structure

The parser walks the page in reading order and emits three kinds of event: a page break, a text block or a table. PART and Item headings start sections. Tables keep their header rows, units (“in millions”) and page number, because a number without its period and unit is how “right number, wrong year” answers happen.

Problem found in real filingsFix
Words split across styled spans (“FINANCI AL”)Join inline text without separators; nested blocks are word breaks
“PART I · Item 1” printed at the top of every page created 109 fake sectionsA repeat of the current item is a running header, not a new section
$, (4, )% in separate table cellsGlue currency signs, brackets and percent signs back onto their numbers
Hidden inline-XBRL header and the table of contentsSkip hidden elements; drop tables that are mostly Item references
Some filers (a bank, two tech companies) put the Item index at the endOpen: those chunks have no section label yet, so section filters miss them

Chunks and their metadata

Text is packed per section up to 300 words, so no chunk spans two Items. Each table is its own chunk; large tables split by rows and every part repeats the header rows. Every chunk starts with a header such as Apple Inc. (AAPL) 10-K FY2025 | Item 7. MD&A, which puts the context into the vector.

GroupFieldsUsed for
Filtercik, ticker, form_type, fiscal_year, fiscal_period, section, content_typeNarrowing the search before similarity; FY2023 and FY2024 text embeds almost identically
Citationaccession, page, table_id, parent_idPointing every claim at a filing, page and table
Operationschunk_id, chunker_version, embedding_modelDeterministic rewrites and running two index versions side by side

Embedding and pgvector

  • The slow step
  • Atomic writes

Each chunk becomes 384 numbers from bge-small-en-v1.5, running locally on the CPU. Text, metadata and vector share one row in Postgres, with an HNSW index on the vector column.

Stage, one 10-K (390 chunks)TimeShare
Parse the HTML0.9 s3%
Chunk0.01 s0%
Embed24.3 s97%

Measured on a laptop CPU. Embedding dominates ingestion, which is why production pipelines work hard not to embed: hash each chunk and re-embed only when the hash changes, batch, use a GPU or a hosted model.

One transaction per filing

Indexing a filing deletes its previous chunks, inserts the new ones and moves the ledger to INDEXED in a single transaction. A crash halfway leaves the old chunks serving; a rerun leaves no strays. Chunk ids are deterministic (accession:section:index), so the same input always produces the same rows.

The numbers path

  • LLM plans, code computes

Companies tag every number in their financial statements with XBRL, and the SEC publishes those facts as JSON. For “what was X in year Y” and “compute this ratio”, that is better than any retriever: exact values, units, periods and the filing they came from.

{ "company": "3M (MMM)",
  "items": [{ "var": "capital_expenditure_2018", "line_item": "capital_expenditure", "fiscal_year": 2018 }],
  "formula": "capital_expenditure_2018", "unit": "usd_millions", "decimals": 2 }
  • Plan: one call to a local model (qwen3:14b) returns JSON constrained by a schema. It names company, line items and fiscal years, and a formula. It never sees or produces a number.
  • Fetch: get_metric maps each line item to the XBRL concepts filers use for it and picks the value as originally reported in that year’s 10-K.
  • Calculate: a parser that only allows + − × ÷ ** over fetched values. The formula comes from a model, so it is never passed to eval.
  • Fail loudly: each step raises a named reason (concept_not_found, bad_formula), which is what the eval counts.

The biggest jump came from one line of prompt. The schema forced line items into an allowed list, but the model never saw that list. It wrote what it meant (“total_revenue”) and decoding pushed it to the nearest allowed value (“total_assets”), so revenue was looked up as assets. Listing the allowed values in the prompt, together with allowing ** for growth rates, took accuracy from 36% to 76%. Constrained decoding needs the options in the prompt too.

Text retrieval

  • Baseline measured
  • Next milestone

Summaries and “what drove…” questions need passages, not facts. The baseline is plain vector search, measured on FinanceBench’s 127 questions about 10-K and 10-Q filings:

The rows read as a plan. The first row assumes perfect query understanding, the last assumes none; the gap is what extracting company and fiscal year from the question is worth. The first row being low with the evidence present 95% of the time says ranking is the problem.

Getting the right documents

FinanceBench names documents like 3M_2022_10K; only 9 of 72 links carry an SEC accession number. The XBRL facts already record which filing reported each fact, so the name resolves to an accession with one query. The 9 known accessions are the check: they exposed that FinanceBench names a filing by the calendar year its period ends in (a retailer’s fiscal 2022 ending January 2023 is “2023”), and that a filing’s period is the date most of its facts report, not the latest. After both fixes, 72 of 72 resolve and 9 of 9 match.

Check the scorer too

Every run saves one record per question with the plan, the fetched inputs and their citations. Reading them found a scorer bug: negative gold answers were parsed as positive. Re-scoring the saved run, with no model calls, moved accuracy from 76% to 78%. A scorer is part of the system and needs its own tests.

Risks and v2

  • Failure modes
RiskDetected byMitigation
Filing missed by the pollerDaily-index reconcile against the ledgerReconcile adds the missing accession
Amendment (10-K/A) replaces numbersForm type on discoveryMark superseded chunks; most amendments only add Part III, so check before replacing
Concept name a company uses is not mappedconcept_not_found count in evalsGrow the mapping from failures; fall back to table chunks
Sections not detected for some filersShare of chunks with no section, per companyFiler-specific heading rules; track it as an ingestion eval
Index outgrows RAMSearch latency, index sizePartition by company or year, quantize, re-score

v2: one agent with three tools (get_metric, search_filings, calculate) for questions that need both numbers and text, measured against the current workflow before splitting into several agents; a retry that shows the planner its failed formula; memory for watchlists and answer caching keyed on filing, invalidated when a new filing lands.

Presenting it in 45 minutes

  • Interview script
StepTimeWhat to cover

2. Define success3 minNumeric accuracy, evidence recall, groundedness enforced vs measured, freshness
3. Draw the whole system7 minLedger-driven ingestion, raw store, two paths (XBRL and chunks), planner, evals
4. Deep dive: ingestion10 minDiscover vs fetch, compare-and-set, raw first, poll plus reconcile, parsing problems, metadata
5. Deep dive: answering12 minLLM plans and code computes, the enum lesson, retrieval baseline and what to fix next
6. Evals and risks8 minOracle vs retrieval, gold-set resolution, scorer bugs, amendments, scale

Lead with the split. Saying early that numbers come from XBRL and text from retrieval answers the hardest follow-up (“how do you guarantee the numbers?”) before it is asked.
