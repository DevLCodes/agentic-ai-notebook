Agentic system design walkthrough

“Ask Your Data” Analytics Agent

About 2,000 non-technical sales and marketing people want to ask questions in plain English, like “What was revenue by region last quarter vs the same quarter last year?”, and get back a number, a chart and a one-line explanation. The data is in a BigQuery warehouse of about 800 tables with confusing names and a partial dbt layer. Some tables hold customer PII. Analysts answer these by hand today, with a 3-day backlog; leadership wants it live in a quarter.

The one-minute picture

  • Start here
  1. Question: the user asks in the chat; SSO identifies them.
  2. Find the tables: retrieval over a schema index (table and column descriptions from dbt, column names and types, join keys, a few example questions). No sample rows.
  3. Write SQL: the model writes BigQuery SQL for the chosen tables, using the business definitions from the semantic layer.
  4. Guards in code: SELECT only, a dry run to check bytes against a cap, a row limit, and no unaggregated PII columns.
  5. Run as the user: the query executes with the user’s own credentials, so BigQuery enforces their permissions.
  6. Answer: the model sees only the aggregated result, and writes the one-line explanation; code draws the chart.
  7. Around it: a golden set from analysts’ past answers before launch; proxies, a weekly graded sample and kill triggers after.

In one breath: “Schema retrieval over metadata, never rows; the model writes SQL; code checks it and caps its cost; it runs as the user so the warehouse enforces access; the model only sees aggregates; and analysts’ past answers are the eval set.”

Finding the right tables

  • Schema index
  • Semantic layer

Don’t put the warehouse in a vector database: 50 TB of rows is the wrong thing to search, and it would copy PII into a second system. Index the metadata instead, one card per table:

  • table name and a plain-English description (from dbt where it exists, written by analysts where it doesn’t),
  • columns with types and descriptions, and which are PII (from policy tags),
  • join keys and grain (“one row per order”),
  • a handful of example questions this table answers, taken from analysts’ past work,
  • freshness and owner.

Retrieval picks the top tables for a question; the model then chooses among them. Start with the 50–100 curated tables that most questions use, with deprecated ones (dim_cust_legacy) excluded or clearly marked. A semantic layer (dbt metrics, Looker LookML, Cube) gives the model fixed definitions of “revenue” and “signups”, so two people asking the same thing get the same number.

Run every query as the user

  • Security default

A shared service account is the most common security mistake in this design. It can read everything the agent might need, so a cleverly worded prompt from anyone can read finance data.

Shared service accountRun as the user
Who BigQuery thinks is askingThe agentThe person who asked
AccessThe union of everyone’s needsExactly that person’s existing access
Prompt injection impactCan reach any table the account canCan’t exceed the user’s own rights
Audit logEvery query looks the sameEvery query is attributed to a person

In BigQuery this means OAuth on behalf of the signed-in user (or short-lived impersonated credentials scoped to them), with dataset IAM, row-level access policies and column-level security through policy tags. The agent’s own service account holds only what it needs to read metadata.

Keep the model away from raw rows

  • Security default

Sample rows in the schema index look helpful: the model sees what values look like. They also put customer names and emails into every prompt that retrieves that table. Raising PII as a requirement and then indexing sample rows breaks your own requirement.

Instead ofUse
Sample rowsColumn profiles computed in code: type, null rate, distinct count, and value lists only for safe low-cardinality columns (regions, plan tiers)
Raw result rows to the modelAggregated results only; code formats tables and charts
Selecting PII columnsA check that rejects SQL selecting a PII-tagged column without aggregation

Guards in code

  • Before every query
#CheckHow
1Read onlyParse the SQL (for example with sqlglot); allow a single SELECT, no DML, DDL or scripting
2No unaggregated PIIPII-tagged columns may appear only inside COUNT or similar aggregates
3Cost capA BigQuery dry run returns bytes to be scanned; above the cap, ask the user to narrow it
4Row limit and timeoutEnforced by the query runner, not requested in the prompt

The same idea as every other agent that acts: the model proposes, code decides. A failed check returns a clear error the model can fix once (“column email can’t be selected; count it instead”).

Number, chart and explanation

  • Grounded output

The result comes back as a small aggregated table. Code picks the chart (a bar for categories, a line for time) and computes the headline number and any comparison, such as the percentage change. The model writes the one-line explanation from those numbers only, and the answer shows the tables used and the SQL behind a “show query” link. If the question is ambiguous (“last quarter” in fiscal or calendar terms), it asks rather than guesses.

Evals before launch

  • Source · size · per step

The data

The 3-day backlog is an asset: years of analyst tickets with the question, the SQL that answered it and the number sent back. Take about 500, stratified by team and question type (totals, comparisons, top-N, time series, funnels), plus questions that should be declined (PII lists, data that doesn’t exist).

The metric: execution accuracy

Run the agent’s SQL and the analyst’s SQL, and compare the results: same rows and values, with rounding tolerance and order ignored unless the question asks for an order. Don’t grade the SQL text with an LLM judge: two very different queries can both be right, and a query that looks right can return the wrong number.

Per-step tests

StepMetricBar
Table selectionRecall@5 of the tables the analyst used≥ 95%
SQL validityParses, passes the guards, runs without error≥ 98%
End to endExecution accuracy≥ 90%
DeclinesCorrectly declines PII and impossible questions≥ 95%
SecurityQueries outside the user’s access that succeed0

The whole set runs on every change to prompts, models or the schema index, and a change ships only if no score drops.

Production without labels

  • Proxies · graded sample · triggers

In production there are no golden labels, so correctness and recall@k can’t be measured directly on live traffic. Say so, then use three layers.

1. Live proxy signals, on every answer

SignalWhat it suggests
👍 / 👎Explicit feedback
Rephrase rate: the same user asks a similar question within 2 minutesThe first answer probably missed
SQL error and empty-result rateWrong tables, wrong filters or broken schema
Decline rateToo low: it’s guessing. Too high: it’s useless
p95 latency; LLM cost and BigQuery bytes per questionHealth against the 30-second target and the budget

2. Real accuracy, from a weekly sample

Analysts grade 50 random answers each week. That is the true accuracy number to compare with the offline 90%, and every wrong answer becomes a new golden-set case, so the eval set grows from real failures.

3. Safety, at zero tolerance

Every query is logged with the user’s identity. Alert on any access to a table outside the user’s groups and on any PII column selected unaggregated.

Rollback triggers

TriggerAction
Any access violationInstant kill switch; questions go back to analysts
👎 above 15% for 3 days, or weekly graded accuracy below 85%Pull back to the pilot group and investigate
Cost per question above 2× budgetAlert and tighten the bytes cap

Launch to one pilot team for 2 weeks before all 2,000 users.

A template for any design: proxies, a human-graded sample, safety alerts, rollback triggers with numbers, and a pilot first. Only the domain proxies change: rephrase rate here, engineer 👍 for an on-call bot, refund-reversal rate for a support agent.

Latency and cost

  • Back of the envelope
StageBudget
Schema retrieval< 1 s
SQL generation (1–2 model calls, one retry on a guard error)3–8 s
Dry run and query in BigQuery2–15 s, partitioned tables help
Chart and explanation2–4 s
Total at p95< 30 s

Illustrative. BigQuery bytes scanned usually costs more than the model; the dry-run cap and partition filters are what keep it bounded. Caching results for identical questions over unchanged data helps popular dashboards-style questions.

Strong signals worth keeping: requirements first including PII and groundedness; indexing schema metadata, not data, and saying why; the cost guard in code; a golden set from analysts’ past answers with per-step tests; and asking for a question to be rephrased when it is unclear.
