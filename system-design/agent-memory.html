Agent memory: what to remember and how to use it

How an assistant remembers across sessions: memory types, a write path with checks in code, a read path with a token budget, user control, and evals.

The whole picture

A model remembers nothing between calls. "Memory" is data your system stores and puts back into the prompt. The design is two paths: a read path that decides which memories go into each prompt, and a write path that decides what is worth keeping.

Types of memory

TypeHoldsWhere it livesHow it is readLifetime
Short-term (working)This conversation: turns, tool results, open taskSession store such as Redis / Memorystore or Firestore, keyed by session idRecent turns in full; older turns replaced by a running summary once over budgetHours
Profile (facts)Stable preferences and facts: language, tone, "prefers short answers", default accountKey-value or document store keyed by user id (Firestore, Spanner, DynamoDB)Loaded whole at session start; it is smallUntil changed or deleted
EpisodicPast issues and outcomes as short dated summaries: "Mar 3: refund for order 812, resolved"Vector store with a user id filter (Vertex AI Vector Search, AlloyDB / pgvector)Top 3 by similarity to the current question, with a recency boostMonths, set by policy
ProceduralHow to do things: playbooks, "check the plan before suggesting upgrades"Versioned prompts and tool descriptions, owned by the teamAlways in the system promptUntil the next release

Managed options exist (for example Vertex AI Agent Engine Memory Bank, LangGraph stores, Mem0), but the decisions below are the same whichever you use.

Write path: what to keep

DecisionDefault
WhenAt session end, asynchronously, not on every turn. An explicit "remember that…" writes immediately.
WhatA small model extracts stable preferences, unresolved issues and outcomes. Skip one-off chatter, secrets and anything the user did not state about themselves.
Shape{user_id, key, value, source_session, confidence, updated_at}, so each memory is traceable to where it came from.
Check in codeDrop low-confidence facts, sensitive data without consent, and duplicates. Never store permissions ("I am an admin"): those come from IAM at request time.
ConflictsNewer wins for preferences; something the user said beats something inferred. Keep the old value in history for audit.

The check matters because memory is a write path an attacker can reach: a prompt injection that gets saved keeps working in every later session.

Read path: what goes in the prompt

  • Filter in code. Every memory query carries the signed-in user id from the session, never a value the model chose.
  • Budget. About 500 tokens in total: profile first, then the top episodic hits. Loading the whole history costs tokens and distracts the model.
  • Wrap as data. <memory date="2026-03-03" source="session 41">…</memory>, with a rule that memory may be out of date and should be confirmed before acting on it.
  • Live data wins. Account facts such as plan, balance or order status are fetched from the system of record on each request. Memory holds context, not truth.

User control and privacy

  • A "what I remember" view where the user can edit or delete any item, and a switch to turn memory off.
  • Delete removes the item from every store, cache and derived summary, within the deletion policy's deadline.
  • TTL on episodic memory; consent before keeping sensitive categories; encryption and data residency as for any customer data.
  • Logs and traces store memory ids, not memory text.

Common mistakes

  • Loading every past conversation into the prompt.
  • Letting the model write memory with no checks, so injected or wrong facts persist.
  • Trusting memory for facts that live in a database, such as the user's plan or an order status.
  • No delete path, or a delete that misses the vector store and summaries.
  • Filtering by user in the prompt instead of in the query.

Saying it in an interview

"I'd split memory into three types: short-term session state, a small profile of preferences keyed by user id, and episodic summaries of past issues in a vector store. At session end a small model extracts facts, and code checks them for confidence, consent and conflicts, with newer winning, before writing with a TTL. On each turn I load the profile and the top three relevant episodes within about 500 tokens, filtered by the signed-in user id in code, and live account data always comes from the system of record. Users can see and delete what's remembered. I'd measure memory recall on multi-session test scripts, aiming for 90%, with zero cross-user leaks as a release blocker."
