Agent memory: what to remember and how to use it

The whole picture

A model remembers nothing between calls. "Memory" is data your system stores and puts back into the prompt. The design is two paths: a read path that decides which memories go into each prompt, and a write path that decides what is worth keeping.

Memory stores compared

"Memory" covers several very different data structures. Each one answers a different kind of question, so most real agents combine two or three.

Picture a support agent talking to a customer who has written in five times this year. It needs this conversation (a buffer or summary), facts about the customer (a profile or graph), and what happened last time (episodes it can search). Conversation buffer, window and summary

These three manage short-term memory inside the context window. A buffer keeps every turn and resends it all, so call 50 pays for turns 1 to 49 again. A buffer window keeps only the last k turns (say 10), which caps the cost but drops the customer's order number from turn 3. A summary asks a small model to rewrite a running summary every few turns; it holds a long session in a few hundred tokens but blurs exact values. Summary plus buffer combines them: once the buffer passes a token budget, the oldest turns are folded into the summary and the recent turns stay verbatim. Pin facts that must stay exact (IDs, amounts, decisions) in a structured "state" block instead of trusting the summary.

buffer: tokens(call n) ≈ system + n × turn grows forever window (k): tokens(call n) ≈ system + k × turn flat, forgets summary+buffer: tokens(call n) ≈ system + summary + k × turn flat, lossy for old turns

Knowledge graph memory

A model extracts entities and relations from each turn and writes them as nodes and edges: (Priya)-[manages]->(Team Atlas), (order 812)-[status]->(refunded). On a new turn, the agent finds the entities mentioned and loads their neighbourhood. Graphs shine for multi-hop questions ("which of Priya's team's open tickets mention billing?") and for facts that change, because an edge can be updated or given a validity period instead of piling up contradictory text. Temporal graph memories such as Zep's Graphiti keep when each fact was true. The cost is extraction: the model must resolve "she", "Priya" and "P. Sharma" to one node, and wrong edges are harder to spot than wrong text.

Vector memory

Each memory (a turn, a fact, a session summary) is embedded and stored in a vector database. At read time the current question is embedded and the nearest memories come back, filtered by user id. It is the most flexible store and needs no schema, but similarity is not truth: "I like Python" and "I stopped using Python" are close vectors. Add metadata (date, type, source) so you can filter and boost by recency, and dedupe before writing. See Vector search for how retrieval works.

Episodic memory

An episode is one past interaction, stored as a short dated summary with its outcome: "3 Mar: refund for order 812 approved after photo; customer happy". It is usually kept in a vector store with date and outcome fields, and read by similarity with a recency boost. The point is learning from experience: the agent sees that the last attempt failed and why. Keep episodes short, set an expiry, and never store raw transcripts with personal data you don't need.

Whatever the mix, the write path decides what is worth keeping and the read path decides what fits in the prompt. Products include LangChain and LangGraph memory classes and stores, Mem0, Letta (MemGPT), Zep and Graphiti, and Vertex AI Memory Bank.

Where short-term memory lives: the context window

"Short-term memory lives in the context window" is true, but the context window is not a place. It is a limit. The conversation itself lives in three places at different moments.

The context window is the maximum number of tokens a model can attend to in one request: system prompt, tool definitions, every message so far, every tool result, and the reply it is writing. A 200k-token window means the input plus the output of one call must fit in 200,000 tokens. Nothing is stored "in" it between calls.

What it isWhere it livesHow long
Messages listThe conversation as text and tool resultsYour app or harness (in memory, or a session store and checkpointer)As long as you keep it
Context windowThe token limit for one request, input plus outputA property of the model and API, not storageApplies per call
KV cacheAttention keys and values for every token being processedGPU memory on the serving machineOne request, unless reused
Prompt (prefix) cacheA saved KV cache for a prompt prefix you send againThe provider's or your serving stack's GPU or host memoryMinutes (Anthropic's default is 5), then evicted

So is the context window the KV cache? No, but they are tied together. The model is stateless: on every call you resend the whole messages list, the server runs it through the model, and the KV cache holds a key and value vector for every token in every layer so each new output token costs one step instead of re-reading the prompt. The KV cache is how the window is held on the GPU during a request, and it grows linearly with the tokens in the window: about 128 KiB per token for Llama 3.1 8B in FP16, so a full 128k-token window needs about 16 GiB. That is why the window has a limit at all, and why long contexts cost more. Prompt caching keeps the KV for a repeated prefix (system prompt, tools, earlier turns) so the next call skips recomputing it; it saves time and money but changes nothing about what the model can remember.

tokens per call = system + tools + all kept turns + tool results + output ≤ window KV bytes ≈ tokens × 2 × layers × KV heads × head dim × bytes per value

When the list outgrows the window, the API rejects the call, or a harness silently drops the oldest turns. Manage it on purpose: keep recent turns in full, replace older ones with a running summary, store big tool results outside the context and keep a reference, and move durable facts to profile or episodic memory. In a multi-agent system, each worker has its own window, which is the main reason to split work across agents.

Surviving restarts: checkpointers

Short-term memory has to outlive the process holding it. Save the agent's state after every step to a store outside the pod, name each conversation with a thread id, and any pod can resume it. This is called durable execution.

An agent turn can take many steps: call the model, run a tool, call the model again. If the pod crashes, is redeployed or scales down mid-turn, state kept only in memory is gone, and the user starts over. A checkpointer saves the full graph state (messages, tool results, the current step) after every step. A thread id, such as user-4471, names the conversation so any process can load its latest checkpoint.

In LangGraph

LangChain's prebuilt agent, create_agent from langchain.agents, builds a model-plus-tools agent that runs on LangGraph and takes a checkpointer directly. The older create_react_agent from langgraph.prebuilt is deprecated.

from langchain.agents import create_agent
from langgraph.checkpoint.postgres import PostgresSaver

with PostgresSaver.from_conn_string(DB_URL) as checkpointer:
    checkpointer.setup()                       # creates the checkpoint tables once
    agent = create_agent(
        model,
        tools=[lookup_order, issue_refund],
        checkpointer=checkpointer,             # state saved after every step
    )
    agent.invoke(
        {"messages": [{"role": "user", "content": "Where is my order?"}]},
        config={"configurable": {"thread_id": "user-4471"}},   # same id resumes
    )

Call it again with the same thread_id, from any process that uses the same database, and the agent sees the whole conversation so far. The same checkpoints power human-in-the-loop pauses: the graph stops before a risky tool, and resumes when a person approves.

Async serving

A high-throughput agent server is almost always async, so one process can keep many model and tool calls in flight while it waits. Use the async checkpointer classes, whose methods are aput, aget and alist instead of put, get and list, and call the agent with ainvoke or astream.

Gotcha: async tool fan-out

When one model step asks for several tool calls, LangGraph's prebuilt ToolNode runs them differently depending on how you call it:

  • Sync (invoke): runs the calls in a thread pool that respects max_concurrency from the run config.
  • Async (ainvoke): starts every call at once with asyncio.gather and ignores max_concurrency.

We confirmed this in the langgraph-prebuilt 1.1.1 source. So if a step requests ten tool calls that each hit your self-hosted model endpoint, all ten land together. That can spike the server's queue or trigger a cold scale-up. Bound the fan-out yourself:

import asyncio
gpu_slots = asyncio.Semaphore(4)               # at most 4 concurrent calls to the endpoint

async def summarize(doc: str) -> str:
    async with gpu_slots:
        return await llm.ainvoke(f"Summarize: {doc}")

Limiting how many tools the model may call in one step also helps.

Write path: what to keep

DecisionDefault
WhenAt session end, asynchronously, not on every turn. An explicit "remember that…" writes immediately.
WhatA small model extracts stable preferences, unresolved issues and outcomes. Skip one-off chatter, secrets and anything the user did not state about themselves.
Shape{user_id, key, value, source_session, confidence, updated_at}, so each memory is traceable to where it came from.
Check in codeDrop low-confidence facts, sensitive data without consent, and duplicates. Never store permissions ("I am an admin"): those come from IAM at request time.
ConflictsNewer wins for preferences; something the user said beats something inferred. Keep the old value in history for audit.

The check matters because memory is a write path an attacker can reach: a prompt injection that gets saved keeps working in every later session.

Read path: what goes in the prompt

  • Filter in code. Every memory query carries the signed-in user id from the session, never a value the model chose.
  • Budget. About 500 tokens in total: profile first, then the top episodic hits. Loading the whole history costs tokens and distracts the model.
  • Wrap as data. <memory date="2026-03-03" source="session 41">…</memory>, with a rule that memory may be out of date and should be confirmed before acting on it.
  • Live data wins. Account facts such as plan, balance or order status are fetched from the system of record on each request. Memory holds context, not truth.

User control and privacy

  • A "what I remember" view where the user can edit or delete any item, and a switch to turn memory off.
  • Delete removes the item from every store, cache and derived summary, within the deletion policy's deadline.
  • TTL on episodic memory; consent before keeping sensitive categories; encryption and data residency as for any customer data.
  • Logs and traces store memory ids, not memory text.

Common mistakes

  • Loading every past conversation into the prompt.
  • Letting the model write memory with no checks, so injected or wrong facts persist.
  • Trusting memory for facts that live in a database, such as the user's plan or an order status.
  • No delete path, or a delete that misses the vector store and summaries.
  • Filtering by user in the prompt instead of in the query.

Saying it in an interview

"I'd split memory into three types: short-term session state, a small profile of preferences keyed by user id, and episodic summaries of past issues in a vector store. At session end a small model extracts facts, and code checks them for confidence, consent and conflicts, with newer winning, before writing with a TTL. On each turn I load the profile and the top three relevant episodes within about 500 tokens, filtered by the signed-in user id in code, and live account data always comes from the system of record. Users can see and delete what's remembered. I'd measure memory recall on multi-session test scripts, aiming for 90%, with zero cross-user leaks as a release blocker."
