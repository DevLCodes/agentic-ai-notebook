What a vector database does

A vector database stores embeddings and answers one question fast: which stored vectors are nearest to this query vector, among those that pass my filters?

Everything else (storage, replication, backups, access control) is ordinary database work. The hard part is nearest-neighbour search at scale, combined with metadata filters.

Why approximate search

Exact search is fine up to roughly a million vectors. Beyond that, systems use an approximate nearest neighbour (ANN) index. You measure it by recall: how often the true nearest neighbours appear in the results.

Common index types

IndexStrengthCost
HNSW (graph)High recall and low latency; handles inserts wellMemory-hungry; the graph lives in RAM
IVF (clusters)Smaller and simpler; good for very large setsNeeds training on a sample; recall depends on probes
Product quantisation (PQ)Compresses vectors 8 to 32 timesSome accuracy lost; usually paired with a rerank on full vectors
ScaNN / tree-AHGoogle's ANN behind Vertex AI Vector Search; strong speed and recallManaged choice; fewer knobs

Filtering

Real queries need filters: this user's permissions, a region, a date range. There are three ways to combine them with ANN:

  • Post-filter: search, then drop results that fail the filter. Simple, but a selective filter can leave almost nothing.
  • Pre-filter: filter first, then search the survivors exactly. Accurate, slow when many survive.
  • Filtered ANN: the index skips non-matching vectors during traversal. This is what you want for permission filters, and what Vertex AI Vector Search restricts, pgvector with a WHERE clause, and MongoDB Atlas Vector Search pre-filters provide.

Options and when to pick them

OptionPick it when
pgvector (Postgres, AlloyDB, Cloud SQL)You already run Postgres, need transactions with your other data, and have up to tens of millions of vectors
Vertex AI Vector SearchGoogle Cloud, very large scale, low latency, managed
MongoDB Atlas Vector SearchYour documents already live in MongoDB; vectors sit beside the source record
Elasticsearch / OpenSearchYou need strong keyword search and vectors in one engine
Pinecone, Weaviate, Qdrant, MilvusA dedicated vector store with its own scaling, often with built-in hybrid search

A good default answer: "Start with the database the team already operates if it supports filtered vector search. Move to a dedicated engine when scale or latency demands it."

Sizing

memory ≈ vectors × dimensions × 4 bytes × (1.3 to 2 for index overhead)

50M chunks × 768 dims × 4 bytes ≈ 154 GB of raw vectors, roughly 200 to 300 GB with an HNSW graph. Quantising to 8-bit cuts the raw part by 4×. Shard by hash of doc_id and replicate for read throughput.
