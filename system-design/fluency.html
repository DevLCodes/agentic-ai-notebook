How to answer

Every answer in a fluency round has the same shape, in about two minutes:

  1. Answer the exact question first. Ask yourself what is actually failing or being decided.
  2. Lead with the biggest lever, then two or three more.
  3. One metric with a number, and how you would measure it.
  4. One risk and how you would catch it.

Retrieval and RAG

Getting the right evidence in front of the model.

How would you build a RAG assistant?
  • Ingest: parse by structure, chunk about 400 tokens with metadata (doc id, ACL, date), embed, index. Keep it fresh with change events and deletes.
  • Query: rewrite the question, hybrid search (vectors + BM25) with the ACL filter inside the search, top 20.
  • Rerank to 5 with a cross-encoder; if the best score is low, say "not found" instead of guessing.
  • Prompt with tagged chunks, generate {answer, citations}, check citations and numbers in code, ship with sources, log one trace.
  • Measure recall@5 ≥ 0.85 and groundedness ≥ 95% on a golden set before launch.

"Ingest with ACLs, hybrid search, rerank with a score gate, cite, check in code, and gate on recall@5 and groundedness." Deep dive

A 5 MB document (about 1M+ tokens) is too slow and costly to send. The user only needs parts of it. What do you do?
  • Chunk and retrieve: send only the relevant 5 to 10 chunks (about 4K tokens), not the whole file. Cost and latency drop by 100× or more.
  • If the task needs the whole document (summarise, compare all sections), use map-reduce: summarise sections in parallel, then combine.
  • Cache the document prefix if the same file is queried repeatedly.
  • Risk: retrieval misses the relevant part, so measure recall@k on questions about that document.

"If only parts are needed, retrieve; if the whole is needed, map-reduce; cache repeated prefixes."

How does vector search work when a user asks a question?
  • Chunks were embedded ahead of time. At query time the question is embedded into one vector with the same model and version.
  • Approximate nearest neighbour search (HNSW) finds the closest chunk vectors by cosine similarity, with filters (ACL, tenant, date) applied inside the search.
  • Run BM25 keyword search in parallel and merge with reciprocal rank fusion, so exact terms like error codes still match.
  • Use the query vs document task types where the model supports them; change the model and you must re-embed the corpus.

"Same embedding model for question and chunks, filtered ANN plus BM25, merged with RRF, then rerank." Deep dive

Bi-encoder vs cross-encoder?
  • Bi-encoder: question and chunk embedded separately; chunk vectors precomputed; millions searched in milliseconds; approximate.
  • Cross-encoder: question and chunk read together, one relevance score; accurate but one model run per pair, so only for the top 20.
  • Use the bi-encoder for millions → 20 and the cross-encoder for 20 → 5. Its score also drives the "not found" gate.

"Embeddings are fast but approximate; a cross-encoder is accurate but slow, so it only reranks the top 20." Deep dive

What happens after retrieval?
  • Rank: rerank and gate on score. Pack: dedupe, about 4K tokens, best first, keep ids.
  • Prompt: instructions, then chunks wrapped as data with ids, then the question.
  • Generate structured output {answer, citations, found}. Check in code: citations exist and are visible to the user, numbers appear in sources.
  • Ship with sources and feedback; log one trace per request.

"Rank, pack, prompt, generate, check, ship, log." Deep dive

How does semantic chunking work, and when would you use it?
  • Split into sentences, embed each, cut where similarity between neighbours drops (for example the top 5% of gaps), then enforce min and max sizes.
  • Try structure-aware chunking first (headings, tables, code). Use semantic chunking for unstructured text such as transcripts and emails.
  • Costs many more embedding calls at ingestion; keep it only if recall@k beats fixed-size on the golden set.

"Structure first; semantic for unstructured text, kept only if recall@5 improves." Deep dive

The model hallucinates. How do you reduce it?
  • Ground it: retrieve, and instruct "answer only from the documents, cite ids, say not found if missing".
  • Gate on retrieval score so the model never answers from weak evidence.
  • Check in code at runtime: every citation is a retrieved chunk, every number appears in a source; regenerate once, then fall back.
  • Measure groundedness offline on the golden set (claims supported ≥ 95%) and online on sampled traces.

"Ground, gate, check in code at runtime, and measure groundedness offline and online." Deep dive

Users ask about live data (metrics in BigQuery). Do you put tables in a vector database?
  • No. Warehouse data is queried live with tools: predefined, parameterised queries, or validated text-to-SQL.
  • A small number of table schemas (say 40) fit in the prompt and can be cached; schema retrieval is only needed for hundreds of tables.
  • The tenant filter is injected by code and enforced with row-level security, never left to the generated SQL.
  • Measure execution accuracy on a golden set of question → expected result.

"Live data through tools with code-injected tenant filters; vectors are for unstructured text." Deep dive

How do you keep a knowledge base fresh, including deletes?
  • Change events (webhooks, CDC) where sources support them; scheduled pulls otherwise.
  • Deletes for pull-only sources: compare the list of ids at the source with the index (set difference) and remove the missing ones.
  • Version every chunk by document version; replace a document's chunks atomically.
  • Metric: freshness lag p95 (for example under 15 minutes) and zero stale chunks for deleted documents.

"Events or pulls, set-diff deletes, versioned chunk replacement, and a freshness-lag SLO." Deep dive

How do you choose and change an embedding model?extra
  • Shortlist on a public benchmark (MTEB), then decide on your own golden set: recall@k on your queries and languages.
  • Weigh dimensions (index size, cost), max input length, languages, latency and data residency.
  • Changing models means re-embedding everything: build a new index in parallel, shadow-compare recall, then switch with an alias. Never mix vectors from two models.

"Pick on my own golden set, and migrate by building a parallel index and switching with an alias." Deep dive

Prompting, models and fine-tuning

Choosing how to get the behaviour you want.

Prompting vs RAG vs fine-tuning: brand tone plus a product catalogue.
  • Facts (catalogue) → RAG: facts change, need citations, and fine-tuning still invents prices and SKUs.
  • Style (tone) → prompt with examples first; fine-tune (LoRA on a few hundred to a few thousand approved examples) only if prompting plateaus. Bonus: shorter prompts, so cheaper and faster.
  • Metrics: brand-voice pass rate ≥ 90% with a calibrated judge; catalogue accuracy ≥ 98% exact match.
  • Risk: fine-tuning can weaken instruction following; re-run the general eval set.

"Prompt first, fine-tune for style only if prompting plateaus, RAG for facts; usually tone plus RAG together."

Gemini Pro vs Flash (big vs small model) for a new feature?
  • Set the bar: quality target on the golden set, p95 latency and cost per request budgets.
  • Run both on the same golden set, compare per slice. Pick the cheapest model that clears the bar.
  • Or cascade: small model by default, escalate hard or low-confidence cases to the big one.
  • Pin model versions and re-run the comparison on every new version.

"Let the eval decide: cheapest model that clears the bar, often a cascade." Deep dive

What is prompt caching and when does it help?
  • The provider reuses computation for an identical prompt prefix (tools, system prompt, long documents), so repeated tokens are billed at a large discount and start faster.
  • Order the prompt from most static to most dynamic; anything changed early in the prefix breaks the cache.
  • Helps chat agents (same system prompt every turn) and repeated questions over one long document.
  • It does not solve concurrency or state problems; it is a cost and latency tool.

"Put static content first so every turn reuses the cached prefix."

How do you get reliable structured output (JSON) from a model?extra
  • Use the provider's structured output / response schema mode so output must match a JSON schema.
  • Keep schemas small and explicit: enums, required fields, formats.
  • Validate in code anyway; on failure, retry once with the validation error, then fall back.
  • Metric: schema-valid rate ≥ 99.9% and field accuracy on a labelled set.

"Schema-constrained output, validate in code, one retry with the error."

Temperature and other decoding settings?extra
  • Low temperature (0 to 0.3) for extraction, classification, tool calls and SQL: you want consistency.
  • Higher (0.7+) for creative drafts or generating several candidates to pick from.
  • Cap max output tokens per use case; it controls cost and runaway answers.
  • Even at temperature 0 outputs can vary, so evals should run each case more than once for agents.

"Low temperature for anything a program consumes, cap output tokens, and evaluate with repeats."

Agents, tools and memory

Making agents take the right actions.

Single agent or multi-agent?
  • Start with one agent and good tools. It is simpler to debug, faster and cheaper.
  • Split only for a reason: different permission scopes (refunds vs read-only), conflicting instructions, or too many tools or context for one prompt.
  • Use a router or supervisor with clear handoff contracts; each sub-agent gets least-privilege tools.
  • Risk: handoff errors and extra latency; measure end-to-end task success, not per-agent scores.

"One agent until permissions, instructions or context size force a split." Deep dive

The agent calls the wrong tool or passes bad arguments. How do you fix it?
  • Clear, non-overlapping tool names and descriptions, with an example each.
  • Strict schemas with enums and formats; validate in code and return a clear error for one retry.
  • Inject ids (user, account, tenant) from the session; never let the model choose them.
  • Show only the tools relevant to the current intent; confirm writes before executing.
  • Metric: tool-selection accuracy ≥ 95%, argument exact-match ≥ 98% on a labelled set; invalid-call rate in production.

"Strict schemas, validate and retry, inject ids, fewer tools per turn, and measure selection and argument accuracy."

How does query understanding and routing work?
  • The model (or a small router) decides: answer from the knowledge base, call tools, both, or ask a clarifying question.
  • Resolve parameters from the session or a lookup ("my last campaign" → campaign id) before calling tools.
  • Rewrite the question for search. Tool calling means the model emits a call; your code runs it and returns the result.
  • Measure routing accuracy on a labelled set of intents.

"Route, resolve parameters from context, rewrite for search; code executes the tools." Deep dive

A user sends a second message before the first answer completes.
  • One in-flight turn per conversation: a lock or a queue partitioned by conversation id.
  • If the first turn has no side effects, cancel it and answer both messages together; if it does, queue the second.
  • Idempotency keys on every write so retries do not double-charge or double-refund.
  • Sequence numbers on history so turns cannot be saved out of order.

"One turn at a time per conversation, interrupt-and-merge or queue, idempotent writes."

How do you design memory across sessions?
  • Three types: short-term session state, a small profile of preferences keyed by user id, and episodic summaries of past issues in a vector store.
  • Write path: at session end a small model extracts facts; code checks confidence, consent and conflicts (newer wins) and writes with a TTL.
  • Read path: profile plus top 3 relevant episodes within about 500 tokens, filtered by user id in code. Live account data always comes from the system of record.
  • Users can view and delete. Metric: memory recall ≥ 90% on multi-session scripts, zero cross-user leaks.

"Three memory types, checked writes, budgeted reads filtered in code, user control." Deep dive

How do you stop an agent looping or running away?extra
  • Hard caps: max steps per task (for example 10), max tokens and max spend per task.
  • Detect repeated identical tool calls and stop.
  • Timeouts on every tool and model call; on hitting a cap, end cleanly with a message or hand off to a human.
  • Metric: steps per task p95 and the share of tasks hitting a cap.

"Caps on steps, tokens and spend, repeat detection, timeouts, and a clean exit." Deep dive

What are MCP and A2A?extra
  • MCP (Model Context Protocol): a standard way to expose tools and data to any model or agent, so one integration works across clients.
  • A2A (Agent2Agent): a protocol for agents to discover each other (agent cards) and delegate tasks across services or vendors.
  • Either way, security stays yours: authenticate, least privilege per tool, and treat tool outputs as untrusted data.

"MCP connects agents to tools, A2A connects agents to agents; neither replaces auth and least privilege."

Workflow or agent?extra
  • If the steps are known in advance, write a workflow (fixed steps, the model fills in each step). It is cheaper, faster and easier to test.
  • Use an agent loop only when the path depends on what is found along the way.
  • Common middle ground: a workflow with one agentic step.

"Workflow when the steps are known; agent only when the path is open-ended."

Evals

Proving quality before and after launch.

How do you evaluate an LLM feature? (the six-part template)
  • Define good: what a correct answer looks like for this task.
  • Golden set: 200 to 500 real cases, sliced by intent and difficulty, labelled by experts.
  • Offline metric with one target number; release gate: no slice regresses more than 1 point.
  • Online monitoring: sampled judge scores, thumbs, escalations. Rollback rule: what number triggers it.

"Good, golden set, metric with a target, gate, online monitoring, rollback." Deep dive

Which metric for which task?
  • RAG: recall@k and groundedness. Classification: per-class precision and recall, macro-F1.
  • Agents: task success on a sandbox plus tool-argument accuracy. Summaries: claim faithfulness and coverage.
  • Text-to-SQL: execution accuracy (results match), not string match.

"Match the metric to the task type, then give one target number." Deep dive

Do you check groundedness against the golden set on every request?
  • No. At runtime you check each answer against its own retrieved sources, in code and sometimes with a small judge. That protects the user.
  • The golden set is offline: it measures the system before each release.
  • Online, you also score a sample of real traces with the same judges.

"Runtime checks protect each user; the golden set measures the system."

How do you trust an LLM-as-judge?extra
  • Calibrate it on 100 to 200 expert-labelled cases; use it as a gate only if agreement is about 80% or more.
  • Known biases: favours longer answers, the first option in pairwise tests, and its own model family. Randomise order and use a rubric with specific checks.
  • Never use a judge for things code can check exactly: amounts, ids, citations, schema validity.

"Calibrate against experts, control for bias, and use code wherever an exact check exists." Deep dive

How would you evaluate an agent that takes actions?
  • Run it in a sandbox with fake APIs; check the end state (was the right refund created, once?) not just the text.
  • Measure task success, tool-selection and argument accuracy, steps and cost per task.
  • Run each case several times; report pass rate, since agents are not deterministic.

"Sandbox, check the end state, run multiple times." Deep dive

Testing and rollout

Shipping changes safely.

How would you roll out a new model or prompt?
  • Offline gate on the golden set, then shadow on live traffic, then canary 1% → 5% → 25% with automatic rollback, then A/B on the primary metric.
  • Version prompt, model, tools and index together as one release id; a feature flag rolls everything back.
  • Rollback triggers: errors over 2× baseline, p95 over SLO, thumbs-down up 30%, any safety incident.

"Golden set, shadow, canary with auto-rollback, A/B, one release id." Deep dive

What is shadow testing?
  • The new version runs on a copy of live traffic; users only see the current one.
  • Sample 5 to 10%, run asynchronously, write tools in dry-run; compare with a pairwise judge, code checks, latency and cost.
  • Zero user risk but no user feedback, so canary and A/B come next.

"Real traffic, zero user risk, writes disabled; then canary." Deep dive

Which metrics must pass before rollout?
  • Quality: golden-set task success per slice, groundedness, tool-argument accuracy.
  • Safety: red-team, permission-leak and PII suites at zero failures; over-refusal rate.
  • Human: expert rubric pass rate, blind side-by-side vs current. Operations: p95 latency, errors. Cost per request.
  • Business, during A/B: resolution rate, escalations, CSAT.

"Quality, safety, human, operations, cost, then business in the A/B." Deep dive

Safety, privacy and security

Keeping users and data safe.

What guardrails would you put on an LLM app?
  • Input: authentication, rate limits, injection and abuse classifiers, PII detection.
  • In the middle: least-privilege tools, ids from the session, limits and approvals for risky actions enforced in code.
  • Output: citation and number checks, PII scan, safety classifier, schema validation.
  • Measure: red-team suite at zero failures, plus over-refusal rate on benign questions.

"Guard input, tools and output in code, and test with a red-team suite." Deep dive

How do you handle PII going into and out of the model?
  • Detect with a DLP tool (Cloud DLP, Presidio): regex for structured ids plus a named-entity model for names and addresses.
  • Tokenise before the model, detokenise after; scan outputs for other users' data and secrets.
  • Redact logs and traces, set retention, use an enterprise endpoint (no training on your data, in-region).
  • Metric: detector recall ≥ 99% on a labelled PII test set.

"Detect, tokenise, call, detokenise, scan output, redact logs; measure detector recall." Deep dive

How do you defend against prompt injection?
  • Treat retrieved text, emails and tool outputs as data: wrap them in tags and never let them change instructions.
  • Structural defences matter most: least-privilege tools, ids from the session, human approval for risky actions, allow-listed URLs.
  • Test with a fixed injection suite in CI, including indirect injection through documents.

"Assume the model will be fooled and make sure it cannot do damage when it is." Deep dive

How do you enforce access control in RAG?
  • Copy source permissions onto each chunk at ingestion and keep them in sync.
  • Filter inside the vector search by the signed-in user's groups, in code, never in the prompt.
  • Test: plant documents only user B can see and ask as user A in many phrasings; expect zero leaks.

"ACLs on chunks, filtered in the search, tested with leak tests." Deep dive

Cost, latency and reliability

Running it in production.

Estimate the monthly cost of a support bot.
  • Per turn: system prompt and tools about 2K, retrieved chunks about 2K, history about 750, user 50 → about 5K input; reply about 250 output.
  • Per 6-turn conversation: about 30K input and 1.5K output.
  • 50K conversations a day × 30 = 1.5M a month → 45B input and 2.25B output tokens. At about $1 and $5 per million: about $56K a month, about 4 cents a conversation.
  • Input dominates because the same prefix and history are re-sent every turn.

"Tokens per turn × turns × conversations, then price; input dominates."

Cut that cost in half without hurting quality.
  • Prompt caching for the static prefix (biggest, no quality risk).
  • Route easy turns to a small model; summarise older turns in the conversation; cap output tokens; cache FAQ answers.
  • Prove quality: golden set, shadow, canary with a thumbs-down threshold, and track input tokens per conversation.

"Cache first, route, summarise, cap output; prove it with golden set, shadow and canary."

The assistant is too slow. How do you reduce latency?
  • Trace first: find which step is slow (retrieval, tools, model).
  • Stream the answer; cut model round trips; cap output tokens; use a small model for routing.
  • Run independent tools in parallel; cache prompts and frequent results.
  • Guard quality while optimising: re-run the golden set. Metric: time to first token and p95 end-to-end.

"Trace, then stream, fewer round trips, smaller router, parallel tools, caching, with a quality guard." Deep dive

At peak the provider returns 429s and timeouts. What happens?
  • Retry with exponential backoff and jitter, honour Retry-After, cap retries; avoid retry storms.
  • Timeouts and a circuit breaker; fall back to another region or a smaller model; provisioned throughput for core traffic.
  • Priority queue: in-progress conversations and paid tiers first; shed the rest with a clear message; degrade gracefully.
  • Prevent: capacity planning, quota increases before launches. Metric: 99.5% answered within 10 s; alert at 80% of quota.

"Retry with jitter, break the circuit, fall back, prioritise, degrade, and plan capacity." Deep dive

What do you log and monitor for an LLM system?extra
  • One trace per request: query, retrieved chunk ids and versions, scores, prompt version, model, tool calls with arguments, latency per step, tokens, cost, feedback.
  • Use OpenTelemetry spans so retrieval, model and tool steps line up in one view.
  • Dashboards: p95 latency, error and 429 rate, cost per conversation, sampled judge scores, thumbs-down and escalation rates, topic drift.
  • Redact PII before logging; bad traces feed the golden set.

"One trace per request with every step, quality and cost dashboards, redacted logs." Deep dive
