Agentic system design walkthrough

AI On-Call Assistant

When a production alert fires, for example “checkout-service error rate is 12%”, an AI assistant investigates. It reads the alert, recent logs, metrics, recent deploys and the team’s runbooks, then posts a likely root cause with evidence in the incident Slack channel within 3 minutes. It can suggest or take fixes such as restarting a pod or rolling back a deploy.

Requirements

  • Clarify

Ask about the non-functional requirements first: how fast, how much per investigation, and how sure it must be before it says anything. Then ask what it is allowed to change.

VolumeA few hundred alerts a day; bursts of hundreds in a minute during an outageMost alerts in a burst are the same incident, so dedup comes before any model call
DataAlerts (PagerDuty, Alertmanager, Datadog monitors), logs, metrics, traces, deploy history, runbooks, past postmortemsThe tools the agent gets, and the history evals are built from

The one-minute picture

  • Start here

One alert, end to end, before any deep dive.

  1. Intake: alerts arrive by webhook from the monitoring system.
  2. Dedup, in code: alerts for the same service and symptom within a window join one incident. No model call.
  3. Investigation: an agent queries logs, metrics, recent deploys and the runbooks in parallel, then ranks hypotheses.
  4. Evidence gate, in code: a hypothesis is posted only if its claims point to real query results and it clears a confidence bar; otherwise the post says “low confidence”.
  5. Slack post: the likely cause, the evidence links and a suggested fix, within 3 minutes.
  6. Fix with approval: an engineer approves a rollback or restart in Slack; it runs, and a monitor watches the error rate afterwards.
  7. Evals around it: past postmortems replayed offline, a shadow period, ratings in production and a kill switch.

In one breath: “Webhook intake, code dedup into incidents, a parallel investigation over logs, metrics, deploys and runbooks, an evidence gate in code, a Slack post in under three minutes, fixes only with approval and a monitor afterwards, and replayed postmortems plus shadow mode deciding whether it ships.”

Alert intake and dedup

  • No LLM

During an outage, dozens of alerts fire for one cause: error rate, latency, failed health checks, downstream services. Investigating each one would cost money, flood the channel and post contradicting causes.

  • Fingerprint each alert: service, symptom (error rate, latency, saturation), environment.
  • Group alerts with the same fingerprint within a window (say 10 minutes) into one incident; related services that share a dependency join the same incident.
  • One investigation per incident. New alerts are added to its context instead of starting another.

This is deterministic code. Monitoring tools already do much of it (PagerDuty and Opsgenie alert grouping, Alertmanager grouping); the assistant reuses their incident ID when one exists.

Investigation

  • Parallel tools
  • Runbooks as RAG
ToolQueryReal systems
LogsTop error signatures for the service in the last 30 minutes vs the hour beforeDatadog Logs, Splunk, Elasticsearch / OpenSearch, Grafana Loki
MetricsError rate, latency, saturation, and the same for direct dependenciesPrometheus, Datadog, CloudWatch
Deploys and configDeploys and flag changes for the service and its dependencies in the last 2 hoursArgo CD, Spinnaker, GitHub deployments, LaunchDarkly
TracesSlowest and failing spans across servicesJaeger, Grafana Tempo, Datadog APM
Runbooks and postmortemsRetrieval over the team’s runbooks and past incidents for this symptomThe team’s wiki, indexed for search

The queries run in parallel with timeouts, so one slow search can’t miss the 3-minute target. Runbooks retrieved for the symptom are fed in as context: they tell the model which checks this team trusts and which causes recur. The model then ranks up to three hypotheses, each listing the query results it relies on.

The investigator is an agent rather than a fixed workflow because the next query depends on what the last one showed: an error signature pointing at the payments client leads to the payments-service metrics. A step limit and a time budget keep it bounded.

The evidence gate

  • In code, not in the prompt

“Have the model say when it doesn’t know” leaves the judgement to the model. A model under pressure to answer will often answer. Put the check in code.

CheckHow
Every claim cites a queryThe hypothesis is structured output: each claim carries a query ID. The gate looks the ID up in the investigation’s own query log; an ID that was never run rejects the claim
The cited result supports the claimDeterministic checks where possible: the deploy’s timestamp is before the spike, the error signature’s count actually rose, the metric crossed its threshold
Enough supportA minimum of independent evidence (for example a deploy that lines up in time and an error signature that changed with it)
Confidence barBelow the bar, the post says “low confidence” and lists what was checked and ruled out, instead of naming a cause

The model’s own confidence is one input, not the decision. Calibrate the bar offline: on the replay set, pick the threshold that keeps precision above target.

Fixes and approval

  • Human in the loop
  • Suggest first. Each fix comes from an allow-list (restart pods of a deployment, roll back to the previous release, scale out) with its exact command shown.
  • Approval in Slack. An on-call engineer approves with one click; the approval is logged with who and when.
  • Execute through the normal deploy system (Argo CD rollback, a Kubernetes rollout restart) with the assistant’s narrow service account, never with broad cluster access.
  • Monitor after the fix. Watch the error rate for a few minutes. If it doesn’t recover, say so in the channel, revert the action if that is safe, and escalate.

Fix suggestions come after root causes in the rollout: first prove the diagnosis is right, then let it suggest, and only much later consider pre-approved automatic actions for narrow, reversible cases.

Evals: offline

  • Source · metric · number

An eval answer needs three things: where the data comes from, what is measured, and the number it must reach. “A golden set” with none of those isn’t an answer.

The data

About 300 past incidents taken from postmortems. Each is replayed against a snapshot of the logs, metrics and deploy history from that time, so the assistant sees what an engineer would have seen. The label is the root cause the postmortem settled on. Include incidents where the cause wasn’t in the data at all; those test whether it can say “low confidence”.

The metrics and the bars

MetricBarWhy
Root cause accuracy@1> 70%The first cause posted is what the engineer checks first
Root cause accuracy@3> 90%The real cause is on the list
Evidence-citation rate100%Every claim links to a real query
“Low confidence” on unexplained incidents≥ 80%It knows when it doesn’t know
Time to first post< 3 min p95The requirement
Cost per investigation< $0.50The budget

Matching a posted cause to the postmortem’s cause needs a grader: exact matches on structured fields (service, change ID, error class) where possible, and an LLM judge with a rubric for the rest, calibrated against engineers’ labels on a sample.

The incident monitor is not the bot’s monitor. The monitoring that fired the alert watches checkout. Evaluating the assistant means measuring its outputs against labelled answers.

The ship gate and production

  • Shadow
  • Ratings
  • Kill switch

Ship gate: two weeks in shadow mode

The assistant investigates every real incident but posts privately to the on-call engineers, who rate each post 👍 or 👎. It must meet the offline targets on these live incidents before it posts in the public incident channel. Fix suggestions are switched on later, after root causes have proved themselves.

In production

SignalWhat it tells you
👍 rate on postsWhether engineers found it useful, every incident
Accuracy@1 on a weekly sample, checked against new postmortemsWhether it is still right as systems change
Fix-acceptance rate and fix-reverted rateRead together: accepted and kept is good; accepted and reverted is a bad suggestion
Cost and latency per investigationBudget and the 3-minute target

Kill switch

If the 👍 rate drops below 60% for a week, or any suggested fix makes an incident worse, the assistant goes back to read-only: it can still post evidence, but suggests and takes no actions until the cause is understood. New postmortems join the replay set every week.

Metrics that mislead

  • Goodhart’s law
Tempting metricWhy it misleadsUse instead
Conversion to execution (fixes run ÷ fixes suggested)Rewards pushing fixes. A system tuned on it learns to suggest rollbacks too often, because a rollback usually “works”Fix-reverted rate and incidents made worse, next to acceptance
Number of tool callsA health metric; more queries isn’t a better diagnosisAccuracy, with tool calls as a cost guardrail
Cost and latency aloneFast and cheap and wrong scores wellAccuracy first; cost and latency as constraints
Mean time to resolve, credited to the botMoves with incident mix and team, not just the assistantA comparison against a shadow-period baseline

Latency and cost

  • Back of the envelope
StageBudget
Intake and dedup< 5 s
Parallel queries (logs, metrics, deploys, runbooks)30–60 s, each with a timeout
Follow-up queries and ranking (3–5 model calls)40–80 s
Evidence gate and post< 5 s
Total at p95< 3 min

Illustrative. Cost per investigation ≈ model calls × tokens × price, plus log-query costs. Summarise log samples in code (top signatures and counts) before they reach the model; raw log lines are the main way the budget gets blown.

Common weak answers

  • What interviewers probe
Weak answerStrong answer

Skipping a question to come back to it laterAnswer every question when it is asked, even briefly; come back to deepen it

Strong signals worth keeping: non-functional requirements first, the end-to-end picture early, dedup without a model, human approval before any production change, runbooks as retrieval context, and a monitor after every fix.

The eval shape that fits every design: data (where it comes from and what the label is), offline metrics with numbers, a ship gate (shadow mode and a bar to beat), production signals, and a kill switch.
