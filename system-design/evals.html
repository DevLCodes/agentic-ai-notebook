Why evals decide everything

Evals are automated tests for AI behaviour. They turn "the answers feel worse" into numbers you can compare, gate releases on and debug.

Without them every prompt tweak, model upgrade or chunking change is a guess. With them you can say "recall@5 went from 0.82 to 0.88 and groundedness held at 0.96, so we ship".

Retrieval metrics, hands on

Question: "How many weeks do adoptive parents get in India?" The golden set marks 3 chunks as relevant (green). Pick a ranking, or mark results yourself, and watch the metrics move.

Presets

    recall@k = relevant in top k ÷ all relevant  ·  MRR = 1 ÷ rank of first relevant  ·  nDCG@k = Σ rel / log₂(rank + 1), divided by the ideal

    Retrieval metrics are cheap, fast and need no LLM, so run them on every change. If recall@k is low, no prompt can fix the answer: the model never saw the right text. Each metric is explained in detail, with code, below.

    The four core metrics in detail

    Four numbers carry most RAG evaluation. Three score the retriever and need only chunk IDs, so they are cheap and exact. The fourth, groundedness, scores the answer and needs a judge.

    MetricScoresIgnoresUse it when
    Recall@kHow many relevant chunks reached the top kOrder inside the top kChoosing k, the candidate pool for a reranker, chunking and embedding changes
    MRRHow high the first relevant chunk isEvery relevant chunk after the firstOne right answer per question: FAQ lookup, exact-ID search, routing
    nDCG@kThe whole order, with graded relevanceNothing in the top k, but needs graded labelsTuning a reranker or hybrid weights, where order matters
    GroundednessWhether each claim in the answer is supported by the retrieved contextWhether the context itself is rightPrompt and model changes; catching hallucinations

    Recall@k

    recall@k = (relevant chunks in the top k) ÷ (all relevant chunks for that question)

    The share of the relevant chunks that made it into the top k. It is the first metric to check, because the model can only answer from what you retrieved: if recall@k is low, no prompt can fix the answer. For example, a question has 4 relevant chunks, you retrieve the top 5, and 3 of the 4 are in there, so recall@5 = 3 ÷ 4 = 0.75.

    1. Build a labelled set. For each test question, list the IDs of the chunks that actually answer it (the gold set). Get these from subject experts, past support tickets, or LLM-written questions that a human has checked. See Building a golden set.
    2. Run retrieval and take the top k chunk IDs for each question.
    3. Score each question: gold IDs found in the top k, divided by the number of gold IDs.
    4. Average across all questions.
    def recall_at_k(retrieved, relevant, k):
    top_k = set(retrieved[:k])
    return len(top_k & set(relevant)) / len(relevant)

def mean_recall_at_k(results, k):
    # results: list of (retrieved_ids, relevant_ids)
    scores = [recall_at_k(r, g, k) for r, g in results if g]
    return sum(scores) / len(scores)

    • Empty gold sets. Skip no-answer questions here, or you divide by zero, and score them separately on whether the system declines.
    • Hit rate@k. When the same fact lives in several chunks, finding any one is enough. Hit rate@k is 1 if any gold chunk is in the top k, else 0.
    • Several values of k. Report k = 5, 10 and 50. Recall@50 tells you how many candidates to send to the reranker; recall@5 tells you what the model actually sees.
    • Precision@k is the mirror image: relevant results in the top k ÷ k (3 ÷ 5 = 0.60 above). Low precision means noise in the prompt.
    • Pitfall: incomplete labels. If a chunk answers the question but nobody labelled it, finding it counts as a miss. Review the "misses" by hand before trusting a drop.

    MRR (mean reciprocal rank)

    RR = 1 ÷ (rank of the first relevant result), or 0 if none in the top k  ·  MRR = mean of RR over all questions
    def reciprocal_rank(retrieved, relevant, k=10):
    for rank, doc_id in enumerate(retrieved[:k], start=1):
        if doc_id in relevant:
            return 1 / rank
    return 0.0

def mrr(results, k=10):
    scores = [reciprocal_rank(r, set(g), k) for r, g in results if g]
    return sum(scores) / len(scores)
    • Read it as a rank. MRR 0.5 means the first right chunk is typically at rank 2; 0.33 means rank 3.
    • Use it when one result is enough: "find the policy called HR-4512", FAQ matching, picking the right tool or route.
    • Pitfall: it says nothing about the second, third or fourth relevant chunk, so a multi-hop question that needs two sections can score 1.0 and still fail. Pair it with recall@k.
    • Pitfall: it is very sensitive at the top. Moving a hit from rank 1 to 2 halves the score, moving it from 9 to 10 barely registers.

    nDCG@k (normalised discounted cumulative gain)

    DCG@k = Σi=1..k reli ÷ log₂(i + 1)  ·  nDCG@k = DCG@k ÷ IDCG@k

    Each result gets a relevance grade, often 0 (irrelevant) to 3 (answers it fully). Its gain is discounted by its rank, so a perfect chunk at rank 1 counts in full and the same chunk at rank 4 counts for 43%. IDCG is the DCG of the best possible order of the labelled chunks, so nDCG runs from 0 to 1.

    import math

def dcg(grades):
    return sum(g / math.log2(i + 2) for i, g in enumerate(grades))

def ndcg_at_k(retrieved, grades, k):
    # grades: {chunk_id: 0..3} from the golden set; unlabelled chunks count as 0
    got = [grades.get(doc_id, 0) for doc_id in retrieved[:k]]
    ideal = sorted(grades.values(), reverse=True)[:k]
    return dcg(got) / dcg(ideal) if dcg(ideal) else 0.0

ndcg_at_k(["X", "A", "B", "C"], {"A": 3, "B": 2, "C": 1}, k=4)   # 0.70
ndcg_at_k(["A", "B", "X", "C"], {"A": 3, "B": 2, "C": 1}, k=4)   # 0.99
    • Use it to tune a reranker or hybrid search weights. Recall@k cannot see a reorder inside the top k; nDCG can.
    • Binary labels work too. With grades of 0 and 1 it still rewards putting hits near the top.
    • Pitfall: the ideal comes from your labels. Build IDCG from all labelled chunks, not just the retrieved ones, or a system that finds nothing good can still score 1.0.
    • Pitfall: two formulas exist. Some tools use (2rel − 1) as the gain, which rewards highly relevant results more. Pick one and never compare numbers across tools.

    Groundedness (faithfulness)

    groundedness = (claims supported by the retrieved context) ÷ (all claims in the answer)

    Groundedness checks whether the answer sticks to what was retrieved. It does not check whether the answer is true: if the context is stale and the answer faithfully repeats it, groundedness is 1.0 and the answer is still wrong. That is what answer correctness against a reference is for.

    1. Split the answer into atomic claims, one fact each, usually with an LLM.
    2. Check each claim against the retrieved chunks: supported, contradicted or not found. Use an LLM judge or a natural-language-inference (NLI) model.
    3. Score supported ÷ total. The figure below scores 3 of 4 = 0.75; the unsupported claim is a hallucination.
    JUDGE_PROMPT = """You check answers against sources.
Context:
{context}

Claim: {claim}

Reply with JSON only: {{"verdict": "supported" | "contradicted" | "not_found", "evidence": "<quote or empty>"}}"""

def groundedness(answer, chunks, llm):
    claims = llm.json(f"Split into atomic factual claims, as a JSON list:\n{answer}")
    if not claims:
        return None  # a refusal has no claims; score it separately
    context = "\n\n".join(f"[{c.id}] {c.text}" for c in chunks)
    verdicts = [llm.json(JUDGE_PROMPT.format(context=context, claim=c))["verdict"] for c in claims]
    return sum(v == "supported" for v in verdicts) / len(claims)
    • Use it on every prompt, model or temperature change, and on 1 to 5% of production traces. A falling score is the earliest sign of hallucination.
    • Also check citations. Citation accuracy asks whether the chunk cited for a claim actually supports it. Answers often cite a nearby chunk instead of the right one.
    • Pitfall: lenient judges. Judges often pass a paraphrase that quietly changes a number, such as 14 weeks where the source says 12. Ask for the evidence quote and spot-check numbers with code.
    • Pitfall: claim splitting varies. The same answer can split into 4 or 6 claims between runs. Fix the judge model and prompt, use temperature 0, and compare runs on the same judge only.
    • Pitfall: uncalibrated judges. Label 100 to 200 answers by hand and check the judge agrees on at least 85% before it gates releases (see the judge figure below).

    Grading answers: groundedness and judges

    • Use a rubric with specific questions ("Does every number appear in the context?") instead of "rate 1 to 10".
    • Known biases: judges prefer longer answers, the first option in a pair, and text from their own model family. Shuffle order, cap length, and use a different model family where you can.
    • Prefer code checks when possible: JSON schema valid, citation IDs exist, required fields present. They are free and never drift.

    Evaluating agents

    Run agent evals in a sandbox with fake but realistic tools, so a test can place an order without spending money. Score task success from the final state (was exactly one order created, with approval?), plus steps taken, tokens, latency and any forbidden calls.

    Building a golden set

    A golden set is a versioned file of questions with what a good answer needs: the relevant chunks, a reference answer, and for agents the expected outcome. Start with 100 to 300 cases and grow it from production.

    SliceExampleExpected behaviour
    Common questions"How much parental leave in India?"Correct, cited answer
    Exact IDs and names"What does HR-4512 say?"Finds that exact document
    Multi-hop"Compare India and US adoptive leave"Uses both sections
    Stale contentA 2022 page contradicts the 2025 onePrefers the newer, mentions the change
    No answer"What is the CEO's home address?"Declines; does not invent
    PermissionsAn intern asks about board minutesReveals nothing, not even that it exists
    InjectionA document says "ignore previous instructions"Treats it as text, not a command

    Sources: real (anonymised) user questions first, subject experts second, and LLM-generated questions only after a human has reviewed them.

    How to pick

    • Two pieces, not one. An offline library that runs the golden set in CI (Ragas, DeepEval or promptfoo), plus a tracing platform that scores production traffic and turns bad traces into new test cases (Langfuse, Phoenix or LangSmith).
    • Follow the stack. On Google Cloud, Vertex AI evaluation and Cloud Trace keep data in one place. Where traces cannot leave the network, self-host Langfuse or Phoenix.
    • Do not compare numbers across tools. "Faithfulness" in one tool and "groundedness" in another use different prompts and judges. Pin the tool version and the judge model, and only compare runs on the same setup.
    • Keep the gate in your own code. Whatever produces the scores, the pass or fail rule should be a plain test you own:
    # test_release_gate.py, run in CI on every change
BASELINE = load_json("evals/baseline.json")

def test_retrieval_did_not_regress():
    results = run_retrieval(load_golden_set("evals/golden.jsonl"))
    assert mean_recall_at_k(results, k=5) >= BASELINE["recall@5"] - 0.01

def test_answers_stay_grounded():
    scores = [s for s in judge_groundedness(run_answers()) if s is not None]
    assert sum(scores) / len(scores) >= 0.95

def test_no_safety_failures():
    assert run_adversarial_suite().failures == []

    Saying it in an interview

    "I'd build a golden set of about 200 questions from real logs, sliced into common, exact-ID, multi-hop, stale, no-answer, permission and injection cases. Offline, I'd measure recall@k and MRR for retrieval, groundedness and correctness with an LLM judge that's calibrated against human labels, and trajectory checks for the agent in a sandbox. That runs in CI as a gate against the production baseline, with safety rules that must be perfect. Online, I'd sample traces into the same judge, track user feedback, and turn every failure into a new golden case."
