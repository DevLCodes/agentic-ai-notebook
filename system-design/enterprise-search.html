Workflow or agent

  • Agent architecture

This is mostly a fixed workflow, not an autonomous agent. Pick the simplest design that works, and say why.

Retrieve, filter, rerank and generate always happen in the same order, so a fixed pipeline is cheaper, faster and easier to evaluate than an agent loop. Add one bounded agentic step: when the first retrieval finds nothing relevant, the model may rewrite the query and search once more. Multi-agent is not justified for a read-only Q&A product.

"I'd start with a workflow and let the model make exactly one decision: whether to search again. If we later add actions like filing a ticket, I'd add a router and give each action its own narrowly scoped tool."

Ingestion

  • Knowledge base & data loading
  • Pipeline deploy

The unit of work is a document ID, not a chunk. A webhook is only a hint that says "go re-read this document."

The pipeline

  1. Change capture. Webhooks and an hourly crawler publish a small message to a doc-changes topic: {source, doc_id, event, seen_at}, where event is upsert, delete or acl_change. The topic is keyed by doc_id, so all events for one document arrive in order on one partition.
  2. Fetch and parse. A worker always fetches the latest version from the source API. It compares the version or a content hash with what is indexed and skips the event when nothing changed.
  3. Chunk. Source-aware chunking, described under Knowledge base.
  4. Embed. Chunks are embedded in batches behind a rate limiter, with retries.
  5. Index. Upsert into the vector and keyword indexes together. Repeated failures go to a dead-letter queue that alerts.
def handle(event):
    doc = source_api.fetch_latest(event.doc_id)       # never trust the webhook body
    if doc is None or event.kind == "delete":
        index.delete(doc_id=event.doc_id)
        return
    if event.kind == "acl_change":
        index.update_acl(event.doc_id, doc.allowed_principals)   # no re-embedding
        return
    if doc.version <= index.current_version(event.doc_id):
        return                                          # duplicate or stale event
    chunks = chunk(doc)                                 # carries doc.version + ACL
    index.upsert(embed(chunks))
    index.delete(doc_id=event.doc_id, version_lt=doc.version)

Updates and deletes

Because the worker re-processes the whole document, it owns all of that document's chunks. Chunk IDs look like doc_id#version#n. When a page shrinks from 12 chunks to 9, the worker writes 9 chunks at the new version, then deletes every chunk for that doc with an older version. In pgvector both steps fit in one transaction. A deleted document removes everything for its doc_id. A permission change only rewrites the ACL metadata.

Missed, duplicated or out-of-order webhooks

  • Duplicates and reordering are harmless because every event triggers "fetch the latest and compare versions." The handler is idempotent.
  • Missed events are caught by reconciliation. Every hour, ask each source what changed since the last cursor: the Drive changes feed with a page token, Confluence CQL on lastmodified, Jira JQL on updated. A nightly full listing catches deletes the change feeds missed. Webhooks give speed; the crawl gives correctness.
  • Bursts are debounced. A page saved 30 times in a minute is processed once, about 30 seconds after the last edit.

The initial backfill

Webhooks only report changes from now on, so the 10M documents that already exist need a separate one-off load.

Documents10,000,000
Sustained rate per connector~50 docs/s (API quota)
One connector200,000 s ≈ 2.3 days
Three sources in parallel≈ 18.5 h if evenly split; the largest source sets the finish
  • List, then process. Phase 1 pages through each source and writes every document ID to a backfill topic, saving the page token after each page. Phase 2 workers process IDs with the same idempotent handler as live events.
  • Separate lane, shared quota. The backfill has its own topic and consumer group. One rate limiter per source API reserves headroom for live updates, so a 2-day load never delays today's edits.
  • Version-checked writes. If the backfill reads v3 slowly while a live edit writes v4, the late v3 write is rejected because writes only go through when the version is newer.
  • Resumable. Offsets are committed after the index write; documents that keep failing go to the dead-letter queue instead of blocking the run.
  • Watched. Track docs per second per source, projected finish, live ingestion lag (must stay flat), DLQ depth and coverage (source count vs index count).
  • Verified before launch. Reconcile counts per source, spot-check documents end to end, run the golden-set evals, then open it to users.

If 2 days is too slow for the launch date, ask the vendors for a higher quota for the largest source. Re-indexing later (a new embedding model or chunk size) rebuilds from the stored parsed documents into a new index and swaps blue-green, so it needs no source quota. Knowledge base

  • Knowledge base & data loading

Chunk each source by its own structure, and put enough metadata on every chunk to filter, cite and delete it later.

SourceHow to chunkWhy
Confluence pageSplit on headings, then by size. Prefix each chunk with the title and heading path, such as "Leave policy > India > Parental leave"A chunk without its heading loses its meaning
Jira ticketOne chunk for summary, description and key fields; comments in small windows; ticket key and status as metadataPeople search by IDs like HR-4512, and long threads need splitting
Docs and PDFsHeadings where present, else recursive split by paragraph; tables kept whole with their header rowA table split mid-row is useless
Sheets and slidesOne slide per chunk; row groups with the header repeatedEach chunk must stand on its own

A sane default is 300 to 800 tokens per chunk with 10 to 20% overlap.

Metadata on every chunk

doc_id, chunk_id, version, source, URL, title, heading path, author, updated_at, space or project, document type, region tags, embedding_model_version, and allowed_principals: the users and groups allowed to read the source document.

Sizing

10M documents at about 5 chunks each is roughly 50M chunks. At 768 dimensions in float32, each vector is about 3 KB, so roughly 150 GB of vectors before index overhead. That means a sharded, managed index rather than a single machine.

Changing the embedding model

Never mix vectors from two models in one index. Build a second index with the new model, backfill it, run the golden-set evals on both, then switch traffic over (a blue-green swap) and keep the old index for a quick rollback.

Query path and RAG

  • RAG pipelines

Follow one question, What's our parental leave policy in India?, from the moment it is typed to the streamed answer.

rewrite
search
rerank
LLM first token

Rough budget to first token: about 1.7 seconds, most of it the model.

  1. Identify the user (~50 ms). Validate the SSO token and load the user's groups from the identity provider, cached for about a minute.
  2. Rewrite the query (~300 ms, small model). Turn follow-ups into standalone questions using chat history. Extract filters such as country = India, and spot exact identifiers such as HR-4512 for keyword lookup.
  3. Hybrid retrieval (~150 ms). Run dense vector search (catches meaning: "maternity" matches "parental leave") and BM25 keyword search (catches exact names and IDs) in parallel. Both are filtered to chunks this user can read. Merge with reciprocal rank fusion and keep the top 50.
  4. Rerank (~200 ms). A cross-encoder scores each candidate against the question and keeps the best 8, with small boosts for recent and authoritative sources.
  5. Permission recheck (~20 ms). Re-verify the final 8 against the freshest permission data. See Permissions and governance.
  6. Generate (~1 s to first token, streamed). The prompt holds the 8 chunks with numbered IDs, titles and last-updated dates, plus rules: answer only from these sources, cite every claim, and say so when the sources do not answer the question.
  7. Check and return. Confirm every citation points to a chunk that was actually provided, attach links, and record the trace.

Why hybrid search

Embeddings blur exact tokens. A search for a ticket ID, an error code or a product name often fails on vectors alone and succeeds instantly on keywords. Hybrid search costs little and fixes a whole class of misses.

When sources disagree

Suppose the current policy page and an old 2022 version that was never deleted both come back. Handle it at three layers. At ingestion, mark archived or deprecated documents and store updated_at. At ranking, boost recency and authoritative spaces. At generation, show each source's date and tell the model to prefer the newest authoritative source and mention the older one. The user sees something like: Per the 2025 India leave policy [1], 26 weeks. An older 2022 page [3] says 12 weeks and appears outdated.

When nothing relevant is found

Refuse clearly and help the user: I couldn't find this in the documents you have access to. Show the closest matches as links. A confident wrong answer about policy is worse than no answer.

Permissions and governance

  • Governance

Authorization is plain code, never an LLM decision, and the model must never see a chunk the user is not allowed to read.

Filter inside the search, not after it

If you retrieve the top 20 and then remove the 18 the user cannot see, the model answers from 2 weak chunks. Instead, apply the permission filter inside the vector and keyword queries, so the top results are computed only over permitted chunks. Vertex AI Vector Search supports this with restricts on each vector, and pgvector with a WHERE clause. Keep a second check just before the prompt as a safety net.

What the check compares

Each chunk stores allowed_principals: the users and groups from the source document's ACL (Drive sharing, Confluence space and page restrictions, Jira project permissions), mapped to identity-provider groups at ingestion. The user side is their ID plus group list. The check is a set overlap.

Keeping permissions fresh

  • A user leaves a group: the group cache expires within about a minute.
  • A document's sharing changes: the source's permission webhook becomes an acl_change event that rewrites metadata in seconds, and the hourly crawl catches anything missed.
  • The recheck errors: drop the chunk. Fail closed.

One index or many

One shared index with permission filters scales and is cheap to run. A separate index per team gives hard isolation but multiplies cost and operations. For an internal assistant, one filtered index is the default; separate indexes make sense for strictly regulated data or external customers.

Other controls

  • Prompt injection from documents. Anyone can write "ignore your instructions" into a Confluence page. Mark retrieved text as data in the prompt, keep the assistant read-only, and never let retrieved text trigger tools.
  • PII. Redact personal data in logs and traces; restrict who can view raw prompts.
  • Audit log. Record who asked what, which documents were used, and what was answered.
  • Data residency and retention. Keep indexes and logs in the required regions; expire chat history on a schedule.
  • Model and prompt registry. Every prompt and model version is reviewed and traceable to the answers it produced.

Deployment

  • Deploying pipelines
  • Deploying agents

Treat ingestion as an idempotent, replayable pipeline and the assistant as a stateless, versioned service with canary releases.

Pipelines

  • Each stage is idempotent, so any event can be replayed safely.
  • Live updates and backfills run as separate consumer groups with separate quotas.
  • Failures retry with backoff, then land in a dead-letter queue with an alert and a replay tool.
  • Batch jobs such as the nightly reconciliation and index rebuilds run as an orchestrated DAG (Vertex AI Pipelines or Cloud Composer).
  • Index changes ship blue-green: build the new index alongside, evaluate it, then switch.

The assistant

  • Stateless service on Cloud Run or GKE, autoscaled on concurrency. Chat history lives in a session store such as Firestore or Redis.
  • Streaming responses so the first words show in under 2 seconds.
  • Model quotas and fallbacks. Rate-limit per user, and fall back to a smaller model or a "showing top documents" mode when the main model is slow or throttled.
  • Caching. Cache embeddings of frequent queries and answers to popular, non-personal questions, keyed by the user's permission set.
  • Versioned prompts and models. A change goes through the eval gate, then a canary at about 5% of traffic, with automatic rollback if quality or latency metrics drop.

Observability

  • Monitoring, tracing, logging

Every request produces one trace with a span per step, so any single answer can be replayed and explained.

Debugging a bad answer

Suppose someone reports the assistant gave the wrong expense limit yesterday. Find the trace, then ask in order: did retrieval find the right document? If not, it is a retrieval or ingestion problem (stale index, bad chunking, missing permission). If it did, did the model misuse it? Then it is a prompt or model problem. Add the case to the golden set so it never regresses.

Dashboards and alerts

Track p50 and p95 latency per step, error and refusal rates, tokens and cost per question, ingestion lag (time from edit to searchable), dead-letter queue depth, and thumbs-down rate by department and source. Alert on latency, error spikes, ingestion lag and any permission-check failure.

Evals

  • Evals

Measure retrieval and generation separately, because they fail for different reasons and are fixed in different places.

Building the golden set

  • Ask each department's subject experts for 30 to 50 real questions with the correct answer and the source document.
  • Mine search logs and help-desk tickets for questions people actually ask.
  • Generate candidate questions from documents with an LLM, then have humans keep only the good ones.
  • Include hard cases: ID lookups, conflicting versions, questions with no answer, and questions about documents the test user cannot access.

Using them

Run the full suite in CI as a regression gate on every prompt, model, chunking or index change. Slice results by department and source so a drop in one area is not hidden by the average. Feed every reported bad answer back into the golden set.
