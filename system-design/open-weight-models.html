Open-Weight Models

A model you can download is a file of numbers. Whoever holds it can run it inside their own network for as long as they like. You gain control over data, cost and versions, and you take on the serving, safety and evals an API provider used to do.

What the weights are

Training adjusts billions of numbers until the model predicts text well. Those numbers are the weights (parameters). “Llama 3.1 8B” has about 8 billion of them; at 2 bytes each that is a 16 GB file.

The file does nothing alone. A runtime (vLLM, SGLang, llama.cpp) loads it with the architecture config (layers, hidden size, attention heads) and the tokenizer, and does the maths. Those three pieces together are “the model” you deploy, and all three must match.

Open-weight is not open source

“Open” covers three different things. The difference matters the day legal or security asks what you may do with the model.

Closed / API-onlyOpen-weightOpen source (OSI)
Download the weightsNoYesYes
Training code and data detailsNoRarelyYes
Use termsThe provider’s API termsA licence: Apache-2.0, MIT, or a custom one with conditionsAn OSI-approved licence
ExamplesClaude, GPT-5, GeminiLlama, Qwen, Mistral, Gemma, DeepSeek, gpt-oss, PhiAI2 OLMo (data, code and checkpoints)

The OSI Open Source AI Definition (v1.0, 2024) requires the parameters, the training code and enough information about the data to rebuild the model. By that bar most “open” models are open-weight.

Read the licence on the exact checkpoint. One vendor can ship different sizes under different terms. Custom licences can cap monthly active users, restrict using outputs to train other models, or require attribution. Record the licence next to the model version in your model registry, the same way you record a dependency’s licence.

DistilledA small model trained to imitate a large one (the DeepSeek-R1 distills into Qwen and Llama)Most of the behaviour at a fraction of the memory

Serving runtimes such as vLLM can load many LoRA adapters on one base model and pick one per request, so ten fine-tuned tasks cost one GPU, not ten.

Will it fit? The memory maths

Three things share GPU memory: the weights, the KV cache (attention keys and values for every token of every active request), and runtime overhead.

weights_GB ≈ params_B × bytes_per_param BF16 2 · FP8/INT8 1 · 4-bit ≈ 0.55
kv_GB ≈ 2 × layers × kv_heads × head_dim × 2 bytes × context × batch / 1e9
total ≈ weights × 1.1 + kv + ~1 GB

Teams size for the weights and forget the cache. Llama 3.1 8B keeps about 128 KB per token, so 32 users at 32k context need about 137 GB of cache, eight times the 16 GB of weights. Context length and concurrency are capacity decisions, not just product settings.

Mixture of experts: memory follows the total, speed follows the active. gpt-oss-120b has about 117B parameters but routes each token through about 5B. It runs at the speed of a ~5B model and needs the memory of a 117B one, because every expert must be loaded. It ships natively in 4-bit (MXFP4), about 63 GB, which is why it fits on one 80 GB GPU.

Quantization and serving

For how quantization works, with a lab, see Quantization.

Quantization stores each weight in fewer bits: a model 2–4× smaller and usually faster, for a small quality loss. Measure that loss on your own eval set, not a leaderboard; the drop tends to show first on long reasoning, maths and non-English text. See evals.

What a production server does

  • Continuous batching: new requests join the running batch every step instead of waiting for it to finish, so the GPU stays busy.
  • Paged KV cache (PagedAttention): the cache lives in fixed-size blocks, so memory isn’t reserved for the longest possible answer.
  • Prefix caching: a shared system prompt is computed once and reused across requests.
  • Tensor parallelism: a model too big for one GPU is split across several in one node, with fast GPU-to-GPU links between them.
  • Speculative decoding: a small draft model proposes tokens that the big model verifies in one pass.

Ollama or llama.cpp suit one developer. To serve many users, use vLLM or SGLang behind an OpenAI-compatible endpoint, so application code doesn’t change when you swap the model. Scale on queue depth and time to first token, not CPU. For the serving internals in depth, see LLM serving and a vendor inference stack.

API, hosted open-weight or your own GPUs

There are three routes, not two. Bedrock, Vertex AI Model Garden, Azure AI Foundry, Together, Fireworks and Groq run open-weight models for you and charge per token.

Data must stay in our VPC or on-premOnly with private deploymentsDepends on the region and contractYes

Fine-tune on our dataProvider fine-tuning APIsOften LoRA uploadsFull control

break-even tokens/month ≈ GPU cost per month ÷ API price per token
e.g. one 80 GB data-centre GPU at ~$2/h ≈ $1,460/month · at $0.60 per 1M tokens → ≈ 2.4B tokens/month

Below that volume, or with GPUs idle overnight, per-token pricing usually wins. Add the engineer time to run the fleet before you call self-hosting cheaper. Many teams mix routes: a closed model for hard reasoning, open models for the high-volume easy work, chosen per request by a router.

Where open weights already win

The most common production use isn’t a chat model. It is the small models in the retrieval pipeline that every document passes through:

  • Embedding models such as bge, e5, nomic-embed: a few hundred MB, fast on a CPU. See embeddings.
  • Cross-encoder rerankers such as bge-reranker. See reranking.
  • Small classifiers and routers. See routing.

At that volume per-token pricing adds up, and owning the embedding model has one more benefit: the vectors in your index never change underneath you because a provider retired a version. FinSight embeds 50,000 10-K chunks with bge-small-en-v1.5 (33M parameters, 384 dimensions) on a laptop CPU.

Safety and supply chain

Released weights can’t be recalled or patched. If a jailbreak is found, the fix is your guardrails, not a provider update.

  • Read the model card: intended use, known limits, the safety evals the vendor ran.
  • Load .safetensors, not pickled .bin or .pt files from strangers; unpickling can run arbitrary code. Never set trust_remote_code on a repo you haven’t reviewed.
  • Pin the exact revision (commit hash) you evaluated, mirror it into your own artifact store, and checksum it.
  • Add input and output guardrails and log usage exactly as you would for an API.

Saying it in an interview

“I’d start on a closed API to prove the product, and move a workload to open weights only for a reason: data that can’t leave the VPC, volume past the break-even, or a narrow task where a fine-tuned 8B model matches the big one on my evals. For sizing, weights are params times bytes, and the KV cache is 2 × layers × KV heads × head dim × 2 bytes per token, times context and concurrency, which often dominates. I’d serve with vLLM behind an OpenAI-compatible endpoint, pin and checksum the exact revision, check the licence per checkpoint, and gate every model or quantization change on the same eval set.”
