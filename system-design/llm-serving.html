LLM serving

How a self-hosted model turns GPU memory into concurrent users: weights, the KV cache, quantization, batching and parallelism. The ideas apply to any serving engine.

Where GPU memory goes

Two things fill the GPU: the model weights, which are fixed, and the KV cache, which grows with every token of every active request.

weights ≈ parameters × bytes per parameter

An 8B model takes about 16 GB in BF16 and 8 GB in FP8, before any KV cache. Whatever memory is left after the weights and runtime decides how many requests, and how long a context, you can serve at once.

A mixture-of-experts model keeps all its parameters in memory but uses only a fraction per token. A 120B MoE model with about 12B active parameters needs memory for 120B and compute for about 12B. MoE saves compute per token, not memory.

KV cache

To generate token 101, attention needs the keys and values of tokens 1 to 100. The KV cache keeps them, so each new token costs one step instead of reprocessing the whole prefix. The price is memory that grows with every token.

KV bytes per token = 2 × layers × KV heads × head dim × bytes per value

Worked example, Llama 3.1 8B in FP16: 2 × 32 layers × 8 KV heads × 128 × 2 bytes = 128 KiB per token. One 8,000-token conversation holds about 1 GiB, and 40 of them hold more than the model's own 16 GB of weights.

Paged KV cache

Paging removes the waste of reserving the longest possible sequence for every request, so more requests fit at once. Requests that share a prefix, such as a common system prompt, can reuse its blocks instead of computing them again (prefix caching).

Quantization

Quantization stores weights, and optionally the KV cache, in fewer bits. Memory falls and throughput usually rises, at a quality cost that must be measured on your own eval set.

FormatBytes per weightNotes
BF16 / FP162The usual full-quality serving format
FP81Small quality loss; needs GPUs with FP8 support to run faster
INT81Weight-only or weights and activations
INT4 (AWQ, GPTQ)≈ 0.5Biggest saving; quality loss depends on the task

Quantizing the KV cache to 8 bits doubles the tokens that fit, which often matters more than shrinking the weights.

Pattern: quantization cuts cost, but pair it with an evaluation before rollout, and keep redundancy so savings never come out of availability.

Batching

A GPU running one request at a time is mostly idle. Batching runs many requests together; the question is when a request may join.

KindHow it worksFits
StaticA fixed group runs to the end togetherOffline scoring where latency doesn't matter
DynamicThe server waits a short delay to group arriving requests, then runs them as one batchFixed-size work: embeddings, rerankers, classifiers
Continuous (in-flight)Batches per generation step; finished requests leave and new ones join between stepsLLM generation, where output lengths vary widely

A longer batching delay forms bigger batches and more throughput, but adds that wait to every request's latency.

Pattern: bursty, variable-length LLM traffic → continuous batching plus a paged KV cache. Together they keep the GPU busy and raise throughput without inflating tail latency.

Parallelism

To use more GPUsHow it splitsCost
Tensor parallelismEvery layer split across GPUs; all GPUs work on every tokenHeavy GPU-to-GPU traffic, so keep it inside one fast-linked node
Pipeline parallelismDifferent layers on different GPUs, like an assembly lineLess traffic, but stages can idle; can span nodes
Expert parallelismMoE experts placed on different GPUsRouting traffic between GPUs; uneven load if some experts are popular
ReplicasWhole copies of the model behind a load balancerSimplest way to add throughput, if one copy fits

Use tensor parallelism when the model doesn't fit on one GPU, and replicas when it does but you need more throughput.

Throughput vs latency

  • Time to first token (TTFT): prompt processing (prefill). Grows with prompt length; helped by prefix caching and shorter prompts.
  • Time per output token: decoding, which is limited by memory bandwidth. Helped by quantization, tensor parallelism and speculative decoding, where a small draft model proposes tokens and the big model checks several at once.
  • Throughput: tokens per second across all users. Rises with batch size, until latency or memory gives out.

Every lever moves one of these at the cost of another, so state the target first: a chat product cares about TTFT and p99 latency, a batch job about throughput.

Saying it in an interview

"Start from memory: a 120B model in FP8 is about 120 GB of weights, so four 80 GB GPUs with tensor parallelism leave about 200 GB for the KV cache. At roughly 128 KiB per token for an 8B-class model, more for bigger ones, that decides how many concurrent conversations fit. For bursty chat traffic I'd use continuous batching with a paged KV cache, prefix caching for the shared system prompt, and replicas to scale. Before switching to FP8, I'd run the eval set and keep a second replica for availability."
