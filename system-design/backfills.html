Backfills and Re-indexing

Loading millions of existing documents, and rebuilding the index later, without starving live updates or losing edits.

What a backfill is

A backfill loads everything that already exists, as opposed to the live stream of new changes. You run one at launch, when you add a source, after a bug corrupts data, and whenever you change parsing, chunking or the embedding model.

time = documents ÷ (per-connector rate × parallel connectors)  ·  10M ÷ (50/s × 3) ≈ 18.5 h

The 3-source figure assumes documents are evenly split. In practice the largest source finishes last, so plan per source.

Running it beside live traffic

  • Separate lanes. Live changes and backfill go to different topics and consumer groups, so you can scale, pause or throttle the backfill alone.
  • One shared rate limiter. A token bucket per source API keeps total calls under quota, with a reserved share for live updates.
  • Backpressure. If the embedding service or index slows down, the backfill consumers slow down rather than piling up retries.

Checkpoints and restarts

A multi-day job will crash at some point. Make it resumable:

  • Two phases. First list every document ID into the backfill topic (cheap API calls), then process them. The listing cursor (page token) is saved after each page.
  • Idempotent processing. Each document is "fetch latest, compare version, write if newer", so reprocessing after a crash is harmless.
  • Committed offsets. Consumers commit their position only after the index write succeeds.
  • Dead-letter queue. Documents that keep failing are parked with the error, not retried forever, and replayed after a fix.

Backfill vs live edits

The backfill and live workers can touch the same document at the same time. Make every index write conditional on version: write only if the incoming version is newer than what is stored. Partitioning both topics by doc_id helps within a lane, but only the version check is safe across lanes.

Re-indexing and re-embedding

Changing the embedding model, chunk size or parser means rebuilding the index. Never do it in place:

  1. Create a new index next to the live one.
  2. Rebuild from the stored parsed documents, not the source APIs, so quotas don't matter.
  3. Dual-write live changes to both indexes while the rebuild runs.
  4. Run the golden-set evals on both indexes and compare.
  5. Switch reads to the new index (blue-green), keep the old one for quick rollback, then delete it.
re-embed cost ≈ chunks × average tokens per chunk × price per token  ·  50M × 400 = 20B tokens

Price the tokens before promising a model upgrade, and batch the work so you use the embedding API's highest throughput tier.
