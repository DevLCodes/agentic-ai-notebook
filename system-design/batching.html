Batching: static, dynamic and in-flight

Running many requests through the GPU together, and the three rules for when a request may join. Pick the wrong one and the GPU sits idle while users wait.

Why batch at all

For each token it generates, the GPU reads every model weight from memory. Reading once and using the weights for many requests is almost as fast as using them for one.

An 8B model in 16-bit reads 16 GB of weights per generated token. Serving one request, the GPU spends most of its time waiting on that read and its arithmetic units sit idle. Serving 16 requests in the same pass reads the same 16 GB, and the extra maths is cheap. So batching raises throughput, total tokens per second across users, many times over, while each user's speed drops only a little.

The design question is when a waiting request may join a batch. There are three answers.

What the numbers show:

  • Mixed lengths (LLM chat): only in-flight batching keeps every reserved slot working, and it cuts the average time to finish by more than half. Dynamic batching can even do worse than static here, because it starts small batches early and a long answer then blocks them.
  • Similar lengths (fixed-size work): no slot is held idle in any scheduler, so the difference is only the wait to start. Dynamic batching with a short wait comes close to in-flight and is simpler, which is why servers use it for embedders and rerankers.
  • Static always makes early arrivals wait for a full batch. It only makes sense when there is no user waiting.

Static batching

The server collects a fixed number of requests, runs them together and returns all results when the last one finishes.

  • Good for: offline jobs where everything is available up front, such as scoring a million documents overnight or generating evaluation outputs.
  • Bad for: live traffic. The first request waits for the batch to fill, and short requests wait for the longest one to finish.
  • Cost: wasted slots grow with the spread of lengths in a batch. Sorting a job by length before batching reduces the waste.

Don't confuse this with a provider's batch API, which charges about half price for jobs that can wait up to a day. That is a job queue: the provider still schedules the GPUs however it likes.

Dynamic batching

The server waits a short, set time after the first request arrives, gathering any others, then runs whatever it has as one batch. It runs early if the batch fills first.

  • The knob: the maximum wait, usually a few milliseconds or less. A longer wait forms bigger batches and more throughput, and adds up to that wait to every request.
  • Good for: models where each request costs about the same and finishes in one pass: embedding a query, reranking 50 passages, classifying a message, an image model.
  • Bad for: LLM generation. Requests finish at different steps, so the batch still waits for its longest answer, just as in static batching.

Servers expose the wait and the preferred batch sizes as settings; here is a real configuration.

In-flight batching

Also called continuous batching. The scheduler works one generation step at a time instead of one request at a time. After every step, finished requests leave and queued requests take their slots straight away.

  • Good for: LLM serving with live traffic, where one answer is 10 tokens and the next is 2,000.
  • Needs: a KV cache that can grow and free per request without fragmenting memory, which is what a paged KV cache provides.
  • Prefill and decode: a new request first processes its whole prompt (prefill), which is heavy, then generates one token per step (decode). Servers split long prompts into chunks (chunked prefill) so one big prompt doesn't stall everyone else's next token.

What limits the batch

  • KV cache memory. Every active request holds its context in the KV cache, so memory, not compute, usually caps the batch. Quantizing the weights or the KV cache frees room for more requests.
  • Latency targets. Bigger batches make each step slower. Servers cap the batch size or the tokens per step to keep time per token within budget.
  • Prompt length. Long prompts make prefill heavy, so a few long-context requests can slow every user's next token unless prefill is chunked.

Saying it in an interview

"Decoding is memory-bound, so batching gets many requests' tokens out of one read of the weights. For the LLM I'd use in-flight batching: requests join and leave every step, so short answers don't wait for long ones, with a paged KV cache so memory follows the real sequence lengths, and chunked prefill so long prompts don't stall others. For the embedder and reranker I'd use dynamic batching with a wait of a few milliseconds. Static batching is only for offline jobs."
