AI Customer Support Agent with Actions

Design an AI customer support agent for a food delivery app. It answers customer questions and can take actions: check order status, cancel an order and issue refunds. It handles about 200,000 conversations a day.

Requirements

  • Clarify

Ask about accuracy, latency and cost straight away, then about the actions. An agent that only answers questions and one that moves money are different systems.

The one-minute picture

  • Start here

Before any component deep dive, draw the path of one message from end to end. It gives the interviewer a map to hang every later question on, and it stops the discussion from starting in storage or the database, which comes last.

  1. Gateway: the customer is already logged in to the app; the gateway attaches the session (user ID, their recent orders) to the conversation.
  2. Router: a small, fast model classifies the intent: order status, cancel, refund, help question, or human.
  3. Specialist agent: each intent has an agent with its own short prompt and only the tools it needs.
  4. Pre-tool hook: every tool call passes deterministic checks in code before it reaches a real system.
  5. Systems: the Orders API, the Payments API and the help-centre index.
  6. Human handoff: anything the agent shouldn’t decide goes to a support agent with a summary attached.
  7. Cross-cutting: traces, dashboards, a golden set and a release gate around the whole thing.

Say it in one breath: “Logged-in session, small-model router, three specialist agents with their own tools, a code hook in front of every action, the Orders and Payments APIs behind it, a human queue for anything risky, and evals plus monitoring around all of it. Now let me go deeper on routing and refunds.”

Routing and agents

  • Trade-off

Router plus specialists, as a trade-off

Splitting into a router and specialist agents is a choice with a cost, so state both sides rather than presenting it as obvious.

One agent with all toolsRouter + specialist agents
Tools exposedAll of them, every turnOnly what the intent needs; the help agent can’t call refunds at all
PromptOne long prompt with every policyShort prompts, each with one policy
Evals and changesA refund-policy edit can change how order-status answers behaveEach agent is tested and changed on its own
LatencyOne model call per stepOne extra hop: a small router call, ~100–300 ms
CostOne large prompt per stepA cheap router call, then smaller specialist prompts
Failure modeWrong tool chosen inside one big loopWrong route; the specialist can hand back

The justification: the actions here move money, so least privilege matters more than one saved hop. The extra router call is small because it runs on a small model, and it pays for itself in smaller prompts downstream. If the product only answered questions, one agent with retrieval would be the better default.

The router

  • A small model, or a fine-tuned classifier, returning an intent and a confidence. Most messages are short and the intents are few.
  • Below a confidence threshold, ask one clarifying question rather than guess.
  • Explicit requests for a person, and anything about safety, abuse or legal matters, go straight to a human.
  • A specialist can hand a conversation back to the router when the customer changes topic.

Actions and money rules

  • Code decides

The language model understands what the customer wants and gathers evidence. Code decides what is allowed and computes every amount.

Confirm which order

Customers often have several recent orders. The agent lists them from the session (“the biryani from 8:10 pm or the groceries from this morning?”) and acts only after the customer picks one. The chosen order’s ID is carried in conversation state, never retyped from the model’s text.

Check claims against data

“My order was late” is checked against the Orders API’s promised ETA and actual delivery time. “An item was missing” is checked against the order’s items and the restaurant’s or courier’s report. The model reports what the customer says; the rules decide using what the systems say.

The three actions

ActionAllowed whenOtherwise
Order statusThe order belongs to the userAsk which order
CancelBefore the restaurant accepts: free. After acceptance, before pickup: per policy, may carry a feeAfter pickup: explain, offer a human
RefundDelivered, within the refund window, a policy rule applies, amount within limitsHuman with context

The rules compute the amount

late = delivered_at - promised_eta            # from the Orders API
if issue == "late" and late > 45 min: amount = 0.5 × food_total
elif issue == "late" and late > 20 min: amount = delivery_fee
elif issue == "missing_item":           amount = price(item)
amount = min(amount, order_value, 500)        # ₹; above 500 goes to a human

Illustrative policy. The model never writes a number into a refund call; it passes the order and the issue, and the rules return the amount. The hook then checks that the call’s amount equals what the rules computed.

The pre-tool hook

  • Deterministic
  • Every call

A hook is code that runs between the model proposing a tool call and the call executing. It can approve, reject or send the call to a human. For refunds, the checks are:

#CheckStops
1Ownership: the order belongs to the logged-in user. The order ID comes from the session, never from the model’s text.Refunding someone else’s order; IDs typed or injected into the chat
2Eligibility: the order is delivered and inside the refund window.Refunds on orders still cooking, or from last year
3Amount: ≤ ₹500, ≤ the order value, and equal to what the rules computed.A model or attacker choosing the number
4No double payment: not already refunded, and an idempotency key so a retry can’t pay twice.Duplicate refunds from retries, timeouts or repeated asks
5Fraud cap: the customer’s refunds this month are under the cap.Serial refund abuse
6Fail to a human: anything that fails goes to a support agent with the context attached.Silent failures and angry repeat contacts

Cancels get the same treatment: ownership, order state, and an idempotency key. Status checks need only ownership. Every decision the hook makes is logged with its inputs, which is also what the evals and the finance reconciliation read.

When asked for the checks, give the list. “It validates the refund” is not an answer. Ownership from the session, delivered and in window, amount within limits and equal to the rules, idempotency, monthly cap, human on failure: six items, stated in order.

Prompt injection

  • Prevented by design
  • Measured by evals

Assume the model will sometimes be fooled. The design makes that harmless: a fooled model can only propose calls that the code then refuses.

LayerWhat it does
Identity from the sessionUser and order IDs come from the login and conversation state, so text can’t point an action at another account
Least-privilege toolsThe help agent has no refund tool; no tool can do more than the logged-in user could
Rules compute amounts“Refund me ₹5,000” has nothing to set: the amount comes from policy
The hookEvery argument is validated in code before any call runs
Untrusted content is markedCustomer text and retrieved articles are wrapped as data, never as instructions
Humans for high stakesAnything over the limit, or unusual, goes to a person

Evals don’t stop injection; they measure it. A red-team set of injection attempts (in chat messages, in order notes, in a crafted help article) runs before every release, and the attack success rate must be zero for actions. If an attack gets through, the fix goes into the design (a check, a permission), not only into the prompt.

Help-centre answers

  • RAG

Policy questions (“what’s your refund policy for groceries?”) are answered from the help-centre articles with retrieval: hybrid search over chunked articles filtered by city and product, a reranker, and an answer that cites the article. If retrieval finds nothing relevant, the agent says so and offers a person instead of improvising policy. Articles are versioned, so a policy change shows up within minutes; see the fresh knowledge base pipeline.

Evals before launch

  • Golden set
  • Graders
  • Release gate

The golden set

About 1,000 real past tickets, stratified by intent so rare but costly cases are present in useful numbers, plus hand-written edge cases and injection attempts. Support leads label each one with:

  • the correct intent,
  • the correct action and amount (or “escalate”),
  • what a good answer contains.
SliceShareWhy
Order status~30%Most common; must be fast and exact
Refund cases (late, missing, wrong item)~25%Money; every rule branch covered
Cancel requests in each order state~15%State-dependent rules
Help-centre questions~15%Groundedness
Edge cases: several orders, unclear intent, topic changes~10%Clarifying questions and handback
Injection and abuse attempts~5%Attack success must be zero

Graders

  1. Exact checks first: right tool, right arguments, right amount, escalated or not. Cheap, fast and unambiguous.
  2. An LLM judge with a rubric for free text: tone, completeness, groundedness. Calibrate it on about 200 human-graded conversations and adjust the rubric until it agrees with the humans about 90% of the time.
  3. Humans for anything the judge and the labels disagree on.

The release gate

Every change (prompt, model, tool, policy) runs the full set in CI. The release is blocked if any metric drops against the current production version, and always if a hard-gate metric is above zero.

After launch

  • Rollout
  • Monitoring
  • Feedback loop

An offline score is a prediction. Production is where real customers, new policies and attackers show up, so the rollout and the monitoring are part of the eval plan.

Rollout

  1. Shadow mode: the new version sees a copy of live traffic and decides, but its actions are not executed and its replies are not sent. Compare its decisions with what actually happened.
  2. Canary at 5%: real customers, real actions, with the full monitoring below and an instant switch back.
  3. Ramp: 25%, 50%, 100%, holding at each step until the metrics settle.

What to watch

SignalWhyAlert or roll back when
Refund rate and money refunded per dayThe most direct cost of a mistakeJumps beyond a set band versus the control group
Escalation rateToo low may mean it isn’t escalating when it shouldMoves sharply either way
Repeat contacts within 24 hThe best proxy for “not actually resolved”Rises above control
Customer satisfactionThe outcome customers feelDrops beyond a threshold
Ungrounded answers, judged on a sampleHallucinated policyRises above a threshold
Hook rejections by checkA spike in one check means a bug or an attackAny sudden spike
Latency and cost per conversationBudget and experienceAbove budget

Roll back

Decide the thresholds before the canary starts, and roll back automatically when refunds per day jump or satisfaction or groundedness drops past them. Then investigate.

Feedback loop

Each week, sample conversations for human review: low ratings, escalations, repeat contacts, hook rejections, plus a random slice. Every confirmed failure becomes a labelled case in the golden set, so the next release is tested against it.

Variant: cloud billing support

  • What changes

The same design handles a cloud billing agent ("I deleted my VM on the 3rd but was charged until the 10th", "raise my GPU quota"). Routing, money rules in code, the pre-tool hook, idempotency and the evals carry over. These are the parts that are new.

AreaFood delivery (above)Cloud billing
Who may act on whatThe order belongs to the signed-in userA user can reach several billing accounts and an account has several users. Code checks the user's IAM role on the chosen billing account before any lookup or credit; the model never picks an account the user cannot access.
Checking the claimOrders API: promised vs actual delivery timeAudit logs give the real deletion time of the resource; the claim is checked against them, not against the customer's date.
Where the amount comes fromA policy formula on the order totalThe actual charges: billing-export line items for that resource between the deletion time and the end of the disputed period. The credit is their sum, capped by policy. Never recomputed from list prices, never taken from the customer's figure.
Explaining whyLate courier, missing itemOften the charge is real: deleting a VM can leave its persistent disk, snapshots or a static IP still billing. The agent shows the line items and names the resource still running, which resolves many tickets without a credit.
Second actionCancel an orderFile a quota-increase request into the existing quota-review system. The agent fills the form (project, region, resource, amount, justification) and returns the ticket id; it does not decide the increase.
Approval tiersAbove a cap, a humanAuto-apply small credits that pass the rules (for example up to $100); above that, a human agent; above the agent limit ($500), a manager.

Using the non-functional requirements

  • Predictable spike: volume roughly triples in the first days of the month when invoices go out. Scale model capacity and workers ahead of the invoice date, queue non-urgent requests, and keep cached prompts warm.
  • 99.9% availability: if the model or a tool is down, the conversation goes to the human queue with the context collected so far, never a dead end.
  • Several languages: answer in the customer's language, but run rules and tools on structured fields, and keep policy retrieval multilingual or translated at query time.
  • Cost: compare cost per resolved conversation with the human cost (for example about $8) and report it next to resolution rate.
