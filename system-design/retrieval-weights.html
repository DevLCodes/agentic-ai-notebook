Weights in Retrieval

Every retriever turns a query into one number per document and sorts. That number is a weighted sum of signals, and the weights decide what “relevant” means.

A score is a weighted sum

Keyword match, meaning match, freshness, field and business rules each give one number per document. You tune only the weights.

score(d) = w₁·bm25(d) + w₂·dense(d) + w₃·recency(d) + w₄·field(d) + w₅·business(d)

In hybrid search the first two terms are usually one knob: alpha·dense + (1 − alpha)·bm25. With alpha = 1 the search is pure vector search, and with alpha = 0 it is pure keyword search.

Scales and normalisation

You can’t add numbers on different scales. A BM25 score of 18 next to a cosine of 0.84 means BM25 wins every sum unless you normalise first.

MethodHowWatch out for
Min-max(s − min) / (max − min), per query, per listOne outlier squashes the rest; a list of near-ties gets stretched to 0–1
Z-score(s − mean) / std, per query, per listUnbounded; needs enough results for a stable mean
Distribution-based (DBSF)Clip at mean ± 3 std, then rescaleSame idea as z-score with fixed bounds; Qdrant ships it
Rank fusion (RRF)Ignore scores and use ranksLoses how much better #1 is than #2

Fuse ranks: RRF

Reciprocal Rank Fusion ignores raw scores and uses only each document’s rank in each list. No normalisation is needed, which is why most engines ship it as the default hybrid mode.

RRF(d) = Σᵢ wᵢ / (k + rankᵢ(d)) k = 60 by default (Cormack et al., 2009)

A small k makes the #1 slot in either list dominate. A large k flattens the curve, so documents that do well in both lists win. Weighted RRF adds a weight per list: the same idea as alpha, applied to ranks.

Boosts, decay and filters

Field boosts

A match in the title or a section header says more than a match in a footnote. Keyword engines let you weight fields, as in title^3 section^2 body. For a 10-K, a hit in “Item 7. Management’s Discussion and Analysis” is worth more than one in the exhibit index.

Recency decay

recency = 0.5^(age / half_life) score = (1 − w)·relevance + w·recency

With a 90-day half-life, a 90-day-old filing gets 0.5 and a 180-day-old one gets 0.25. Pick the half-life per content type: prices decay in days, policies in months, filings in a year.

Business boosts

“Promote our own research notes” is legitimate, but it quietly overrules relevance. Keep business boosts small and named, log them on every result, and measure them with the same eval as everything else. Otherwise nobody can explain why result #1 is #1.

Filter or boost?

Filters remove, boosts reorder. Use a filter when the question pins a value (WHERE fiscal_year = 2023, ticker, tenant). Use a boost for a preference (“newer is usually better”). Permissions are always filters, never boosts: see access control.

Choosing the weights

Weights are hyperparameters. Picking alpha by trying three queries and eyeballing the results ships a search that is great on the demo and worse everywhere else. The repeatable way is a grid search on a labelled set.

  1. Label 100–300 real queries with graded relevance (2 answers it, 1 related, 0 not), covering each query type: exact IDs, paraphrases, mixed.
  2. Sweep alpha from 0 to 1 in steps of 0.1 (or k and the list weights for RRF), and compute NDCG@10 or recall@k for each value. See evals.
  3. Hold out a test split. Tune on one half and report on the other, or the score flatters you.
  4. Re-tune after any signal changes. A new embedding model, chunker or BM25 analyser moves score distributions, and yesterday’s best alpha may now be wrong.
  5. Split by query type if the best values differ. ID lookups want low alpha, open questions want high alpha, and a router can pick the profile.

Past a handful of signals, hand-tuned weights stop scaling. Learning to rank (LTR) trains a model, often LambdaMART gradient-boosted trees, on the same labelled pairs to learn the weights and their interactions. A cross-encoder reranker goes one step further and reads the query and document together.

Failure modes

  • Raw BM25 plus cosine. BM25 silently wins every query because its scale is larger.
  • Alpha tuned on five demo queries. It overfits the demo; measure on a labelled set with a held-out split.
  • Recency as a filter. Last year’s 10-K vanishes exactly when it is the only answer.
  • Unlogged business boosts. Nobody can explain the ranking, and evals don’t see them.
  • The same weights after swapping the embedding model. The new cosine distribution needs a new alpha.

Saying it in an interview

“I’d run BM25 and dense retrieval in parallel and fuse them with RRF at k = 60 as the default, because it needs no score calibration. If we need finer control I’d switch to linear fusion with per-list min-max normalisation and tune alpha on a labelled set of a few hundred queries, split by query type, using NDCG@10 on a held-out half. Recency is a soft decay with a half-life per content type, permissions are hard filters, and every boost is named and logged. Any change to the embedder or analyser triggers a re-tune.”
