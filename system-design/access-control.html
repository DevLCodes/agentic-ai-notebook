What an ACL is

An access control list (ACL) says which principals (users, groups, service accounts) may do what with a resource. For search, the only question is: may this user read this document?

ABAC (attribute-based)A policy over attributesReadable if user.region == doc.region and doc.classification ≤ user.clearance

Source systems mostly use ACLs, often driven by groups. An assistant should mirror the source's decision exactly: never grant more than the source would.

Mapping source permissions

  • Resolve inheritance. A Confluence page restriction narrows its space's permissions; store the effective result.
  • Prefer groups to users. Store group IDs and expand the user's groups at query time. Expanding groups into user lists on every chunk explodes in size and goes stale.
  • Handle "anyone with the link". Treat link-shared files as private to the owner unless policy says otherwise.

Where to enforce

Filter inside the vector and keyword queries so ranking only considers permitted chunks; filtering after retrieval leaves the model with scraps. Then recheck the final few chunks against the freshest permission data just before building the prompt. Never let a model decide access.

Freshness of permissions

Permissions change faster than content: people switch teams, leave, or get removed from a sensitive page. Treat permission changes as their own events that rewrite chunk metadata without re-embedding, keep the user-group cache short, and fail closed when the recheck cannot answer.

Shared index or one per tenant

One index with permission filters is cheap and scales well, and is the default for an internal assistant. A separate index per team or customer gives hard isolation (a bug in the filter cannot leak across) at the cost of many more indexes to run. Use separate indexes for external customers and strictly regulated data.
