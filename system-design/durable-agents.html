Durable agent execution: checkpointers

A long agent conversation should survive a crash or a redeploy. Save the agent's state after every step, name each conversation, and any process can pick it up where it stopped.

The idea

Durable execution means a running agent can be stopped at any moment and resumed later without losing work or repeating it.

An agent turn can take many steps: call the model, run a tool, call the model again. If the process holding that state crashes, is redeployed or scales down, an agent that keeps state only in memory starts over and the user loses their context. Two pieces fix this:

  • A checkpointer saves the agent's full state (messages, tool results, where it is in its graph) after every step, to a store outside the process.
  • A thread id names the conversation, such as user-4471. Whichever process handles the next request loads that thread's latest checkpoint and continues.

Deployment

In LangGraph

LangChain's prebuilt agent, create_agent from langchain.agents, builds a model-plus-tools agent that runs on LangGraph and takes a checkpointer directly. The older create_react_agent from langgraph.prebuilt is deprecated.

from langchain.agents import create_agent
from langgraph.checkpoint.postgres import PostgresSaver

with PostgresSaver.from_conn_string(DB_URL) as checkpointer:
    checkpointer.setup()                       # creates the checkpoint tables once
    agent = create_agent(
        model,
        tools=[lookup_order, issue_refund],
        checkpointer=checkpointer,             # state saved after every step
    )
    agent.invoke(
        {"messages": [{"role": "user", "content": "Where is my order?"}]},
        config={"configurable": {"thread_id": "user-4471"}},   # same id resumes
    )

Call it again with the same thread_id, from any process that uses the same database, and the agent sees the whole conversation so far. The same checkpoints power human-in-the-loop pauses: the graph stops before a risky tool, and resumes when a person approves.

Choosing a checkpointer

Pick the cheapest store that meets your durability need.

CheckpointerSurvives a restart?Shared across pods?Use for
InMemorySaver (also MemorySaver)NoNoTests and notebooks only
SqliteSaver, AsyncSqliteSaverYesNo: a local fileA single server or a local tool
PostgresSaver, RedisSaver, AsyncMongoDBSaverYesYesA fleet of replicas where any pod can resume any conversation

Async serving

A high-throughput agent server is almost always async, so one process can keep many model and tool calls in flight while it waits. Use the async checkpointer classes, whose methods are aput, aget and alist instead of put, get and list, and call the agent with ainvoke or astream.

Gotcha: async tool fan-out

When one model step asks for several tool calls, LangGraph's prebuilt ToolNode runs them differently depending on how you call it:

  • Sync (invoke): runs the calls in a thread pool that respects max_concurrency from the run config.
  • Async (ainvoke): starts every call at once with asyncio.gather and ignores max_concurrency.

We confirmed this in the langgraph-prebuilt 1.1.1 source. So if a step requests ten tool calls that each hit your self-hosted model endpoint, all ten land together. That can spike the server's queue or trigger a cold scale-up. Bound the fan-out yourself:

import asyncio
gpu_slots = asyncio.Semaphore(4)               # at most 4 concurrent calls to the endpoint

async def summarize(doc: str) -> str:
    async with gpu_slots:
        return await llm.ainvoke(f"Summarize: {doc}")

Limiting how many tools the model may call in one step also helps.

Saying it in an interview

"Agent state can't live in the process, because pods restart and requests land on different replicas. I'd build the agent with a Postgres checkpointer and pass the user's thread id on every call, so any pod can resume the conversation from its last step. In-memory savers are for tests only. The server is async for throughput, so I'd use the async checkpointer and put a semaphore in front of the model endpoint, because async tool execution fans out without a concurrency limit."
