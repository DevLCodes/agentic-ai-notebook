At a glance

Launch is the start of an agent's life, not the end. Models get updated, users ask new things, tools change their APIs, and one day someone asks you to prove what the agent did six months ago.

Think of an airliner. The instruments in the cockpit say whether the flight is healthy right now. The flight data recorder keeps every control input so engineers can replay a problem. The sealed black box is built so nobody can quietly edit it after a crash. And a maintenance schedule replaces parts before they fail. An agent in production needs the same four things, and they are different systems with different rules.

PieceQuestion it answersWho reads itRules
Traces (the flight recorder)What exactly happened in this run, step by step?Engineers debuggingSampled, redacted, kept days to weeks
Metrics and alerts (the instruments)Is the agent healthy right now, and is it getting worse?On-call, dashboardsAggregated numbers, kept months
Audit log (the black box)Who did what, when, with which version, and can we prove it was not changed?Auditors, legal, securityComplete, append-only, tamper-evident, kept years
Maintenance (the schedule)Has anything drifted, and is the next change safe?The owning teamPinned versions, evals and canaries for every change

The most common mix-up: treating application logs as the audit log. Logs are for engineers, so they are sampled, trimmed and editable. An audit log is evidence, so it must be complete and provably unchanged. Keep them as separate systems.

Traces: see every step

An agent run is a tree of steps: a model call decides to search, a tool runs, the model reads the result, a guardrail checks the answer. A trace records the whole tree for one run, and each step is a span with a start time, a duration and attributes. One trace ID follows the run across every service and every agent, so a slow or wrong answer can be traced to the exact step that caused it.

What to record on each span

SpanAttributes worth keeping
Agent run (root)Trace ID, user or tenant ID, agent name and version, prompt version, outcome (answered, escalated, refused, failed)
Model callModel name and exact version, input and output tokens, time to first token, finish reason, cost
Tool callTool name, arguments (redacted), status, retries, latency, size of the result
RetrievalQuery, document IDs and scores returned, index version
GuardrailWhich check, pass or block, and the reason
  • Use a standard. OpenTelemetry has semantic conventions for generative AI spans (model, token counts, operation), so traces work in any backend you choose later.
  • Sample smartly. Keep every trace that failed, was slow or got bad feedback, and a few per cent of the healthy ones. Tail-based sampling decides after the run ends, when you know which kind it was.
  • Redact before export. Prompts and tool results carry personal data. Mask it in the collector, before traces leave your network, and keep full payloads only where access is controlled. See safety and PII.

Metrics, SLOs and alerts

Traces explain one run; metrics summarise millions. Classic services watch latency, errors, traffic and saturation. An agent needs those plus three more, because an agent can be fast, error-free and still wrong or expensive.

FamilyMetricsWhy it matters for agents
LatencyTime to first token, end-to-end p50 and p95, steps per runA loop that takes 12 steps instead of 4 is a latency and a cost bug
ErrorsTool failures and timeouts, model API errors, malformed outputs, guardrail blocksTools fail far more often than models
Traffic and saturationRequests per second, queue depth, GPU use, KV cache use, rate-limit headroomSaturation predicts the next outage; see LLM serving
QualityOnline eval score on sampled traces, task success, escalation rate, thumbs downThe agent can degrade with zero errors; see production monitoring
CostTokens per task, cost per resolved task, cache hit rateA prompt change can double cost silently
SafetyPrompt-injection detections, PII caught in outputs, refusals, actions needing approvalThese are the incidents that reach the news

SLOs and error budgets

A service level objective (SLO) is a target for a metric over a window, such as "99.5% of runs finish successfully within 10 seconds over 30 days". The gap to 100% is the error budget: the failures you are allowed. While budget is left, ship changes; when it runs out, freeze risky changes and fix reliability.

error budget = (1 − SLO) × runs in the window    burn rate = observed error rate ÷ (1 − SLO)

A burn rate of 1 spends the budget exactly over the window. Alerting on raw error rate pages people for blips; alerting on burn rate pages only when the budget is really at risk. The usual pattern, from Google's SRE practice, is a fast alert (burn rate above about 14 over the last hour, which spends 2% of a 30-day budget in that hour) and a slow ticket (burn rate above about 1 over several days). Quality and safety SLOs, such as "online groundedness above 0.9", use the same arithmetic.

Audit logs that hold up

An agent that reads records, sends emails or moves money must leave evidence of what it did. Picture a practice-exam case: the agent's audit trail lives in a PostgreSQL table that administrators can update. An external auditor rejects it, because nothing proves the entries were not changed after the fact. Adding more access controls does not fix that: whoever holds the highest privilege can still edit rows, and the auditor has to take their word for it.

The property the auditor wants is tamper evidence: any change, deletion or insertion after the fact can be detected by someone who does not trust the administrators. That takes an append-only, hash-chained log, anchored or stored somewhere the administrators can't rewrite.

How a hash chain works

Each entry stores a cryptographic hash of its own content together with the previous entry's hash. Change one old entry and its hash no longer matches, and neither does every entry after it. It works like a row of numbered, wax-sealed envelopes where each seal also stamps the previous seal's number.

hi = SHA-256( hi−1 ‖ timestampi ‖ actori ‖ actioni ‖ payloadi )

The catch interviewers look for: a hash chain alone stops casual edits, not a determined administrator, who could rewrite an entry and recompute every hash after it. Close the gap by publishing the head hash outside their control: sign it with a key they don't hold, write it to WORM storage, get a trusted timestamp, or send it to the auditor. Then a recomputed chain no longer matches the anchor. Try both cases in the lab below.

What an agent's audit entry holds

  • Who: the human principal, the agent's identity, and any delegated credential it used.
  • What and with which version: agent version, prompt version, model name and version, tools available.
  • Inputs and evidence: the request, retrieved document IDs, and each tool call with its arguments and result. Store large or personal payloads elsewhere and log their hash and a pointer, so the entry still proves what was used.
  • Decisions: guardrail and policy outcomes, human approvals or rejections, and the final output or action.
  • When: a timestamp from a trusted, synchronised clock, and a sequence number so gaps show.

Write the entry from the platform that executes tools, not from the model's own narration: the model's account of what it did is not evidence. Keep the log in a separate account or project from the application, so the team that runs the agent cannot also delete its history. Reading the log needs access controls too, because it contains everything the agent saw; see Access control.

Drift and maintenance

Even if you change nothing, an agent's world changes around it. Drift is a gradual shift in inputs or behaviour that slowly moves the agent away from what you tested.

What driftsExampleHow you notice
InputsA product launch brings questions the golden set never coveredTopic and intent mix, embedding clusters, retrieval scores falling
The modelThe provider updates a model behind an aliasOutput length, refusal rate and tool-call mix shift on one day
Tools and APIsA partner API renames a field; the tool starts returning nullsTool error rate, empty results, contract tests in CI
KnowledgePolicies change but the index still holds the old PDFFreshness lag and stale citations; see Fresh Knowledge Base
Cost and loadLonger conversations raise tokens per taskCost per resolved task, context length percentiles

Maintenance habits

  • Pin everything. Use exact model snapshots instead of moving aliases, keep prompts in a versioned registry, and record every version on the trace and the audit entry.
  • Every change is a release. A new prompt, model, tool or index runs the golden-set regression, then shadow or canary traffic, with a one-click rollback. See shadow, canary and A/B.
  • Close the loop. Failed and down-voted traces go to a review queue, the real failures become golden-set cases, and CI blocks the next change that breaks them.
  • Keep a calendar. Model deprecation dates, certificate and key rotation, re-embedding when the embedding model changes, and log retention deadlines.

Changing the model safely

The riskiest routine change is the model itself: a new version, a smaller model, or the same model quantized to save memory. Treat each as a new release, even when "the weights are the same, only smaller".

  • Quantizing to raise throughput. Going from 16-bit to 8-bit halves weight memory, which frees room for KV cache and bigger batches. It is post-training work, with no retraining, but accuracy can drop on fragile tasks, so validate before rollout. Worked through in the 13B throughput case.
  • Moving to the edge. A model that must run offline on a small device has a hard latency and memory budget. The usual fix is an optimised engine in FP16 with INT8 where calibration shows it is safe, then accuracy validation on real cases. See the edge deployment case.
  • Swapping versions. Re-run the golden set, compare cost and latency, shadow real traffic, and canary with automatic rollback on SLO burn.

Whatever the change, the decision rule is the same: measure on your own tasks, compare against the current version, roll out gradually, and keep the old version ready.

Incidents and runbooks

When an alert fires, the first job is to stop the harm, not to find the root cause. Agents need a few levers that ordinary services lack, and they should exist before the incident.

  1. Detect: a burn-rate alert, a safety metric spike, or a user report linked to a trace ID.
  2. Mitigate: roll back the last prompt or model version; disable one tool with a feature flag; switch to read-only mode, where the agent can answer but not act; route to humans; or fall back to a smaller, stable model. A kill switch stops all autonomous actions at once.
  3. Diagnose: open the failing traces, compare with healthy ones, and check what changed (deploys, provider status, tool APIs).
  4. Recover and learn: fix, add the failing cases to the golden set, write a blameless postmortem, and check the audit log for actions that need to be undone or reported.

Protect against cascading failures too: put circuit breakers and timeouts on every tool, cap steps and tokens per run, and make tool actions idempotent so retries cannot repeat a payment.

Saying it in an interview

"I'd run the agent with four separate systems. Traces: one trace per run with spans for every model call, tool call, retrieval and guardrail, using OpenTelemetry conventions, redacted in the collector and tail-sampled so every failure is kept. Metrics: latency, errors and saturation, plus quality from online evals, cost per resolved task and safety signals, with SLOs and burn-rate alerts instead of raw thresholds. An audit log: written by the platform that runs tools, append-only and hash-chained, with the head hash signed or written to WORM storage outside the admins' account, so an auditor can verify nothing changed. And maintenance: pinned model and prompt versions, drift dashboards, and every change, including quantization or a model swap, through golden-set regression, canary and rollback. For incidents I'd have a kill switch, per-tool flags and a read-only mode ready before launch."
