Fresh Knowledge Base Pipeline

Thousands of product docs change every day across several sources. Design the pipeline that keeps a support agent’s knowledge base fresh, so any change shows up in its answers within 15 minutes.

Requirements

  • Clarify

Before you draw anything, find out how each source reports change, how big bursts get, and what has to disappear fast. Also ask what exists today.

Corpus2M docs, ~20 chunks each ≈ 40M chunksA full rebuild is hours of work; only incremental updates fit in 15 minutes

Access~30% restricted: per-customer docs and internal-only pagesThe ACL has to live on every chunk and be enforced at query time

Ask what exists today. “Is everything already indexed, and how?” tells you whether you’re designing a migration or a greenfield system, and gives you the current baseline to beat.

Architecture

  • Whole system

Replace the nightly rebuild with an event-driven pipeline. Cost and latency then scale with what changed, not with the size of the corpus. The 3D view at the top of the page plays one full cycle.

ComponentJob
Change listenerReceives webhooks, push events and bucket notifications, turns each into one event shape and acks the source only after the event is written to the topic.
Wiki pollerLists pages modified since a saved cursor every minute; lists all page IDs every 3 minutes and diffs them against the registry to find deletes.
doc-changes topicKafka or Pub/Sub, keyed by doc ID, so each doc’s events stay in order on one partition.
Priority topicDeletes and permission changes, with reserved workers so a burst of edits never delays them.
Ingest workersVersion check, fetch, parse, chunk, hash, embed only changed chunks, versioned write. Stateless and autoscaled on consumer lag.
Doc registryOne row per doc: current indexed version, chunk IDs, ACL, chunk hashes, stage timestamps, tombstones. The source of truth for what should be in the index.
Vector indexChunks with vectors and filterable metadata: tenant, ACL groups, visibility, doc ID, version, embedding model.
Nightly reconcileCompares each source, the registry and the index, and emits events for anything that drifted. It catches whatever the real-time path missed.

Why not run the batch job more often? It takes 6 hours and its cost grows with the corpus. Even at 10× the hardware it would take 36 minutes and re-embed 40M chunks to pick up a few hundred changes.

Change capture

  • Data loading
  • Kafka

Every source change turns into one small, uniform event on a durable topic. Push where the source can push, and poll where it can’t.

The event is a pointer

{
  "source": "help_center",
  "doc_id": "hc-42",
  "change": "upsert",
  "source_version": 7,
  "source_updated_at": "2026-03-04T14:00:03Z",
  "received_at": "2026-03-04T14:00:04Z",
  "event_id": "c1f0e8…"
}

change is one of upsert, delete or acl_change. The event carries no content: the worker always fetches the latest version. That keeps events tiny, and a replayed or duplicated event simply fetches the current text again.

Ordering and delivery

  • Partition key = doc ID. All events for one doc land on one partition, so one consumer sees them in order.
  • At-least-once, so idempotent consumers. Webhooks get retried and consumers restart, so assume duplicates. The worker compares the event’s version with the registry and drops anything not newer.
  • Ack after the write. The listener returns 200 to the source only once the event is on the topic. If the listener is down, the source’s own retries cover the gap, and the nightly reconcile catches anything still missing.

The source that can’t push

A “modified since” query can find edits but will never return a page that no longer exists. Deletes need a set difference: list every wiki page ID (IDs only, so it’s cheap), compare it with the wiki IDs in the registry, and publish a delete for each ID that has gone. Running it every 3 minutes leaves 2 minutes of the 5-minute delete budget for processing.

Processing and versioned writes

  • Pipelines
  • Correctness

The hard part isn’t embedding, it’s replacing a document’s chunks without ever serving a mix of versions or leaving orphans behind.

The worker, step by step

  1. Read the registry. If the event’s version is not newer than the indexed one, skip it.
  2. Fetch the latest content and parse it (layout-aware for PDFs).
  3. Chunk by headings, about 500 tokens with some overlap.
  4. Hash each chunk. Reuse cached vectors for unchanged hashes and embed the rest in batches.
  5. Insert every chunk under the new version: hc-42:v7:0 … hc-42:v7:4.
  6. Flip the registry to v7. Retrieval only returns chunks whose version matches the registry’s current one.
  7. Delete where doc_id = hc-42 and version < 7.
  8. On repeated failure, send the event to a dead-letter queue and alert.

The orphan trap. If chunk IDs are just doc#0 … doc#19 and the new version has 17 chunks, an upsert overwrites 0 to 16 and leaves 17, 18 and 19 serving stale text forever. Version the IDs and delete by version.

Retrievaltext, vector, title and heading path, updated_at
Accesstenant_id, acl_groups, visibility (public, customer, internal)
Operationscontent_hash, embedding_model, chunker_version

Deletes and permission changes

  • Governance
  • 5-minute rule

These are rare but urgent. Showing a doc that was unpublished, or one meant for another customer, does more damage than an answer a few minutes stale.

ChangeWhat the pipeline doesCost
Delete or unpublishDelete all chunks where doc_id = X, write a registry tombstoneOne call, seconds
Permission changeUpdate acl_groups and tenant_id on existing chunks; no re-chunking, no re-embeddingMetadata write, seconds
Wiki deleteFound by the 3-minute ID diff, then handled as a delete≤ 3 min to detect

Enforcement at query time

  • Filter inside the search. Post-filtering a top-k throws away results and can return nothing; a pre-filter keeps recall and latency predictable.
  • Built from identity. The retrieval service builds the filter from the authenticated user’s tenant and groups. Nothing the model says can widen it.
  • Fail closed. If the identity lookup fails, serve public content only.
  • Tombstones. The registry remembers deleted docs, so an edit event that arrives late can’t bring one back.

Bursts and scaling

  • Capacity

A quiet day is about 7 changes a minute. Release day can be 50,000 in an hour. The design has to absorb the spike without missing the deadline.

50,000 docs in 1 hour≈ 14 docs/s
× 20 chunks, embedding everything≈ 280 chunks/s
With hash dedupe (1 changed chunk per doc)≈ 14 chunks/s
Max parallel workers= partition count, so pick e.g. 24
  • Scale on lag, not CPU. Consumer lag is the signal that tracks the freshness target.
  • Respect the embedding quota. Batch requests, cap concurrency, and back off on 429s. Lag can rise for a while, but it must drain inside the window.
  • Protect the priority lane. Separate topic, separate workers, so deletes never wait behind 50,000 edits.

Observability

  • Monitoring
  • Tracing

Two questions: is the pipeline meeting its freshness target, and when an answer is wrong, was the data stale or did the model get it wrong?

What to record

Per doc (pipeline)Per request (agent)
t0 source changed, t1 event received, t2 fetched, t3 embedded, t4 writtenUser, tenant, the ACL filter applied
Version, chunk count, chunks embedded vs reusedRetrieved chunk IDs with versions and scores
Retries, dead-letter reasonPrompt version, model, tokens, latency, answer, feedback

Dashboards and alerts

  • p50 and p99 freshness lag per source; page when p99 > 12 minutes or delete lag > 4 minutes.
  • Consumer lag per partition, the early warning before freshness slips.
  • Dead-letter queue size and the oldest item’s age.
  • Canary freshness per source. If the canary stops showing up, alert even when every other graph looks green.

Start debugging from the request, not the doc. The trace’s chunk versions tell you in one look whether to investigate the pipeline or the prompt.

Re-embedding and evals

  • Evals
  • Safe rollout

A new embedding model or chunker changes every vector, so it means building a whole new index. Build it next to the old one, prove it’s better, then switch.

The golden set

  • About 1,000 real questions from support tickets and resolved conversations, each labelled with the doc that answers it and checked by support staff.
  • Negatives: questions only a restricted or internal doc could answer, asked as a user who must not see it. The right result is “not found”.
  • Freshness questions about recently changed docs, where the old answer is now wrong.

Deployment

  • Pipeline deploy
  • Pipeline as code. Worker code, chunker config and embedding model version are versioned and shipped through CI/CD with tests on sample docs.
  • Idempotent everywhere. Every step can be replayed from any topic offset, so recovery means rewinding the offset rather than writing a special script.
  • Canary workers. Roll a new worker build to a few partitions first and compare error rate and chunk counts before the rest.
  • Config changes that alter chunks (chunker, model) go through the blue-green index flow above, never in place.

v2: section-level diffs so only changed sections are re-chunked, per-tenant freshness targets, and change-aware answers (“this policy was updated today”).

Presenting it in 45 minutes

  • Interview script
StepTimeWhat to cover
1. Clarify5 minSources and how each signals change, scale, bursts, deletes, ACLs, what exists today
2. Define success2 minFreshness p99, delete deadline, zero stale or leaked chunks, and how each is measured
3. Draw the whole system8 minListener and poller, topics, workers, registry, index, agent, cross-cutting
4. Deep dive: correctness10 minEvent schema, partition key, version check, versioned writes, deletes, ACLs
5. Deep dive: production10 minBursts, stage timestamps, canary, request traces, blue-green re-embedding, golden set
6. Risks and next steps3 minMissed events, orphans, poison docs, outages

Turn verbs into mechanisms. “Listen”, “replace” and “detect” each need an answer to which component does it, keyed on what, in what order, and what happens on failure. Give those answers before you’re asked.
