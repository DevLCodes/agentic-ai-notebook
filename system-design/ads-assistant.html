The problem and assumptions

Account managers answer advertiser questions such as "Why did my CPC go up last week?" or "Which campaigns should I move budget to?". The assistant answers from three sources and can suggest budget changes, but never applies them.

SourceShapeWhere it lives
Campaign dataDaily rows per campaign, ad group and keyword: impressions, clicks, cost, CPC, conversions, budget, bid strategy, plus a change history of editsBigQuery (structured, stays there)
Help docsPublic product documentationChunked into pgvector
Past account-manager notesFree text per advertiser, may contain personal dataChunked into pgvector with advertiser and access metadata

Ask these in one batch in the first two minutes, or state them as assumptions: about 5,000 account managers, each covering around 20 advertisers; answers in under 10 seconds; read-only apart from suggestions.

The one-minute picture

Three sources, two stores

  • Campaign data stays in BigQuery. Copying warehouse rows into a vector database gives stale, unfilterable numbers. Query it live.
  • No vector database for the schema. 30 to 40 table descriptions are roughly 10K tokens. Put them in the system prompt with a few example questions and cache that prefix. Schema retrieval only pays off at hundreds of tables.
  • Help docs and notes go into pgvector, chunked on headings and paragraphs, each chunk tagged with doc_id, advertiser_id (for notes), source and access group. Use hybrid search (keyword plus embeddings), take the top 20, rerank, keep the best 5.

Predefined tools, not free-form SQL

The model picks a tool and fills in parameters. Code builds and runs the SQL, so the model cannot write a query that scans everything or skips a filter.

ToolReturns
get_metrics(advertiser_id, metrics, date_range, group_by)Aggregated metrics, e.g. cost and clicks by campaign for two weeks
get_change_history(advertiser_id, date_range)Bid strategy, budget, keyword and ad edits with timestamps
search_docs(query)Top help-doc chunks with links
search_notes(advertiser_id, query)Top note chunks for that advertiser
propose_budget_shift(from, to, amount, reason)A suggestion card for the account manager. There is no tool that writes to the account.

Free-form SQL is a fallback for questions the tools cannot express. It runs with a read-only service account, SELECT only, a dry run first with a cap on bytes scanned, and a row limit.

Keeping each advertiser's data separate

A filter written by the model is not a guarantee. Use two layers that do not depend on the model:

  • Code adds the filter. The tool layer reads the manager's advertiser list from the signed-in session and adds advertiser_id IN (...) to every query. An advertiser_id the manager does not own is rejected before any query runs.
  • The warehouse enforces it again. BigQuery row-level access policies (or authorised views) scoped to the manager mean even a buggy query cannot return another advertiser's rows.

The same applies to notes: the advertiser_id and access-group filter is applied inside the vector search, not after it.

Walkthrough: "Why did CPC go up for advertiser X last week?"

  1. Gateway: verify the user, load their advertiser list, check the input for prompt injection and personal data.
  2. Agent calls get_metrics for this week and last week, grouped by campaign. CPC is cost divided by clicks, so it checks which one moved and which campaigns explain most of the change.
  3. Agent calls get_change_history for the same window to find a cause: a bid strategy switch, a budget cut, new broad-match keywords.
  4. Agent calls search_docs for how that change affects CPC, and search_notes for context from past conversations with this advertiser.
  5. The model writes the answer with sources. Code checks that every number in it appears in a tool result, then sends it.

Tool calls with no dependency on each other run in parallel to stay under the latency budget.

Guardrails, enforced in code

  • Prompt injection. Notes and docs are data, never instructions. Detected injection is blocked and logged. Tools have least privilege, and no tool can change an account.
  • Grounded numbers. Any number in the answer that is not in a tool result fails the check; the answer is regenerated or returned as "I couldn't find that in the data".
  • Suggest, never apply. Budget changes are cards the manager accepts in the normal Ads UI, where existing permissions and audit apply.
  • Personal data. Notes are scanned for personal data at ingestion and masked in answers.

Is a budget suggestion any good?

A suggestion must be grounded in the data, agreed with by experts, and improve results. Check each one. Targets below are illustrative.

WhenCheckBar
Before it is shownRules in code: only suggest moving budget to B if B is limited by budget (losing over 10% of impression share to budget) and B's cost per conversion is at least 20% better than A's, with 30+ conversions eachOtherwise, no suggestion
Before launchExpert review: 300 suggestions on last quarter's data, stratified by advertiser size and vertical, rated by senior account managers≥ 80% "I would make this change", < 2% "would hurt the advertiser"
Before launchBacktest: past cases where managers moved budget the same way, conversions over the next 14 daysBetter than no change
After launchA/B test randomised by advertiser (not by suggestion, since one advertiser's suggestions affect each other) for 4 weeksConversions or ROAS at equal spend up ≥ 3%, p < 0.05
After launchAcceptance rate, reverts within 7 days, complaintsAcceptance ≥ 40%, reverts < 10%; reverts > 15% or a ROAS drop turns the feature flag off

Rollout: shadow mode against real questions, then 1%, 10%, 50%, 100% behind a flag, with an automatic rollback if quality drops more than 2 points or errors cross a threshold. After launch, watch thumbs-down rate, a weekly graded sample, and how often managers rewrite the answer before sending it.

Cost and latency

  • Cache the stable prefix: system prompt, schema descriptions and tool definitions.
  • A small, fast model classifies the question; the large model only plans and writes the final answer.
  • Independent tool calls run in parallel; aggregation happens in BigQuery, so only small result sets reach the model.

Saying it in an interview

"Campaign data is structured, so it stays in BigQuery and the model reaches it through a few predefined tools; code builds the SQL and always adds the advertiser filter from the session, and row-level security enforces it again. With only 30 to 40 tables I'd put the schema in a cached prompt rather than a vector database. Help docs and notes go into pgvector with advertiser and access metadata and hybrid search. For 'why did CPC go up', the agent compares weeks, splits cost and clicks by campaign, checks the change history and explains with docs and notes, and code checks every number against the tool results. Budget changes are only suggestions. I'd validate them with rules, expert review and a backtest before launch, and an advertiser-level A/B test after, with acceptance and revert rates as guardrails and a rollback rule."
