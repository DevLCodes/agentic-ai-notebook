Chain-of-thought

Reason step by step, then answer. Each step is conditioned on the last, so multi-step problems come out right far more often.

Q: PO 40 units at $12. 35 arrived. Invoice bills 40 at $12.50. Amount to approve?
A: 35 received × $12 = $420. Invoice asks 40 × $12.50 = $500 → $80 disputed. Approve $420.
  • Variants: few-shot (worked examples) · zero-shot ("let's think step by step") · self-consistency (sample several chains, majority vote).
  • Reasoning models do it internally with hidden reasoning tokens; no need to ask.
  • Use when: logic or arithmetic over facts already in the prompt.
  • Watch out: can't fetch facts, so reasons confidently from wrong ones; more tokens and latency.

ReAct

Reason + act, interleaved: thought → action (tool call) → observation, repeat until it can answer. Modern tool-calling agent loops are ReAct.

Thought: Need the PO for INV-7781.      Action: get_po(invoice="INV-7781")
Observation: PO-5520, 40 units at $12   Action: get_receipts(po="PO-5520")
Observation: 35 received on 3 Nov
Answer: Hold: billed 40, received 35.
  • Use when: needs tools or live data, and each step depends on the last result.
  • Watch out: greedy, no look-ahead; can repeat or wander; resends a growing context. Cap the steps (the three-way match agent caps at 8 tool calls).

Tree of thoughts

Explore several chains: propose candidate next thoughts → evaluator scores partial solutions → search (BFS, DFS or beam) keeps good branches and backtracks from dead ends. Heuristic search below shows how it picks a branch.

  • Evidence: Game of 24, GPT-4: CoT 4% → ToT 74% (Yao et al., 2023).
  • Use when: an early wrong choice ruins everything and partial progress can be scored: puzzles, constraint solving, scheduling.
  • Watch out: branches × depth calls; rarely worth it for ordinary questions or tool tasks.

Heuristic search: how the tree picks a branch

You can't afford to expand every branch, so you guess which ones are closest to an answer and expand those first. That guess is the heuristic.

A sat-nav doesn't try every road in the country. It prefers roads that point towards the destination, because "straight-line distance left" is a cheap, decent guess. Tree of thoughts works the same way. Some terms:

  • Node: one partial solution, such as "4 + 6 = 10, numbers left: 10, 2, 7".
  • Expand: ask the model for the next few thoughts from a node. Each expansion costs model calls.
  • Frontier: the nodes found so far but not yet expanded.
  • Heuristic, h(n): a score for how promising node n looks. A model prompted to rate it ("sure, likely or impossible to reach 24", as in the tree of thoughts paper), or code: tests passed, constraints met.
  • Cost so far, g(n): what reaching n has already cost, such as steps or tokens.

The search strategy decides which frontier node to expand next. The heuristic decides how good that choice is.

A* is guaranteed to find the cheapest path only if h never overestimates the cost left. A model's score gives no such guarantee, so with LLMs treat A* as "best-first that prefers short plans", not as optimal.

The search is only as good as the scorer

  • Prefer a real check: tests that pass, a constraint solver, a calculator, a schema. They're cheap per call and they don't flatter.
  • If the model scores, ask for coarse labels (sure, likely, impossible) rather than 1 to 10, and take a vote of 2 or 3 samples. Models tend to rate their own ideas too kindly.
  • Cap the budget: a beam width of 2 to 5, a depth limit, a maximum number of expansions, and stop at the first answer that passes a real check.

Decoders use beam search too, keeping the k most likely token sequences. It's the same algorithm with tokens as nodes and probability as the score.

Plan-and-execute

Split thinking from doing: a strong planner writes all steps once; a cheap executor (small model or code) runs them; the planner may write the final answer.

  • Why: fewer expensive calls · independent steps run in parallel · visible plan a person can approve.
  • Related: ReWOO plans all tool calls up front with no observation in between · HTN (hierarchical task network) breaks a goal into sub-tasks via known procedures.
  • Use when: long task, steps mostly known, cost / parallelism / auditability matter.
  • Watch out: plan is written before observing anything; a surprise at step 2 is ignored → add re-planning.

Reflection and re-planning

Feedback loop: attempt → check (unit tests, schema validator, rule or critic model) → on failure, write what went wrong (the reflection) → retry with that note. Reflexion (Shinn et al., 2023) also keeps the notes as memory for later attempts.

  • Re-planning: same idea for plans; on a failed step or contradicting observation, rewrite the remaining steps.
  • Use when: first attempts are often wrong but a check can tell: code + tests, extraction + schema, plans with failing steps.
  • Watch out: self-critique with no outside signal can talk itself into a wrong answer. Prefer a real check, cap retries at 2–3, stop when an attempt doesn't improve.

Reasoning under uncertainty

The patterns above set the shape of thinking. Each decision inside them also needs a way to conclude. Certain facts → rules suffice. Uncertain facts → weigh probability against cost: probabilistic (decision-theoretic) reasoning, using expected value = each outcome's cost × its probability, summed.

Worked example: reroute around a storm?

Forecast: 40% chance the port closes; sensor feed incomplete, so closure can't be confirmed. Reroute costs $12k for certain. Keep the route and it closes: $50k delay.

Break-evenReroute when p × $50k > $12k → p > 24%. At 40%, well past it.
50% rule fails"Reroute if closure is more likely than not" keeps the route → $20k expected loss. Looks at probability, ignores costs.
Deduction fails"If port closed → reroute" never fires: incomplete sensors never establish closure.
Heuristic n/aPruning cuts a large search; this is one uncertain bet.
Value of infoPerfect forecast → reroute only in the 40% of closures: 0.40 × $12k = $4.8k. So perfect info is worth at most $12k − $4.8k = $7.2k. Pay up to that for better data, no more.
Risk attitudeEV assumes risk-neutral. If one $50k loss would break a contract, add that penalty to the cost (a utility function); don't override by gut.

They combine: heuristic search shortlists routes, rules drop illegal ones, deduction where facts are certain, expected value picks among the rest.

Building it into an agent

  • Tools supply the numbers: in a ReAct loop, a weather tool gives p, a pricing tool gives costs; don't let the model guess.
  • Arithmetic in code: an expected_cost(options) tool is exact and testable.
  • Calibrated probabilities: a "40%" that is really 15% gives a confidently wrong answer (confidence scoring).
  • Escalate near break-even (p ≈ 24%) or on stale inputs: buy information or ask a person.
  • Log inputs (p, costs, values) with the decision for review.

Which one to choose

  1. Answerable from what it has, with reasoning? → CoT or a reasoning model (+ self-consistency if accuracy beats cost).
  2. Needs tools or fresh data, unpredictable path? → ReAct with a step cap.
  3. Steps known, task long or costly? → Plan-and-execute + re-planning.
  4. Early choice decides everything, partial answers scorable? → Tree of thoughts, budget permitting.
  5. Output checkable? → wrap any of the above in reflection.
  6. Decision hinges on an uncertain outcome with known costs? → compute expected value in a tool.

Saying it in an interview

"Cheapest pattern that solves it. Facts in the prompt: chain-of-thought or a reasoning model. Tools and an unclear path: ReAct with a step cap. Known, long job: plan-and-execute, strong planner, cheap parallel steps, human-approvable plan, re-plan on failure. Tree of thoughts only when early choices decide everything and partials can be scored. Checkable output: add reflection with a real check and a retry cap."
