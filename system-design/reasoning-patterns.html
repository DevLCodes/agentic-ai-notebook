Reasoning and planning patterns

Chain-of-thought, ReAct, tree of thoughts, plan-and-execute, and reflection with re-planning: how each makes an agent think, what it costs, and which one to pick. Plus reasoning under uncertainty: expected value against heuristic, rule-based and deductive reasoning.

At a glance

Each pattern answers one question differently: how does the agent get from a goal to an answer?

They combine. A common production agent plans with a strong model, runs each step as a short ReAct loop, and reflects when a check fails.

See them think

Pick a pattern to watch the gold token trace how it reasons, or answer the questions underneath and the scene switches to the pattern that fits.

Chain-of-thought

Ask the model to reason step by step before it answers. Writing the steps out gives it room to work: each step is conditioned on the ones before, so multi-step problems come out right far more often than with a direct answer.

Q: A PO is for 40 units at $12. 35 arrived. The invoice bills 40 at $12.50.
   Think step by step, then give the amount to approve.
A: Received 35 units. The PO price is $12. 35 × $12 = $420.
   The invoice asks for 40 × $12.50 = $500, so $80 is disputed.
   Approve $420.
  • Variants: few-shot (show worked examples), zero-shot ("let's think step by step"), and self-consistency (sample several chains and take the majority answer).
  • Reasoning models do this internally: they spend hidden reasoning tokens before answering, so you rarely need to ask for it explicitly.
  • Use it when: the answer needs several steps of logic or arithmetic over information already in the prompt.
  • Watch out: it can't fetch facts, so it reasons confidently from wrong ones. Longer outputs cost tokens and time.

ReAct

ReAct (reason plus act) interleaves thinking with tool use. The model writes a thought, picks an action, reads the observation that comes back, and repeats until it can answer. Modern tool-calling APIs and agent loops are ReAct in practice.

Thought: I need the PO for invoice INV-7781.
Action: get_po(invoice="INV-7781")
Observation: PO-5520, 40 units at $12.00
Thought: Now check what was received.
Action: get_receipts(po="PO-5520")
Observation: 35 units received on 3 Nov
Thought: The invoice bills 40; only 35 arrived. Hold for 5 units.
Answer: Hold: quantity billed exceeds quantity received by 5.
  • Use it when: the agent needs tools or live data, and the next step depends on what the last step found.
  • Watch out: it chooses greedily, one step at a time, with no look-ahead. It can repeat itself or wander, and every step re-sends a growing context. Cap the steps, as the three-way match agent does at 8 tool calls.

Tree of thoughts

Instead of one chain, explore several. At each step the model proposes a few candidate next thoughts, an evaluator scores each partial solution, and a search (breadth-first, depth-first or beam) keeps the promising branches and backtracks from dead ends. Heuristic search below shows how that choice is made.

  • Evidence: on the Game of 24 puzzle, GPT-4 with chain-of-thought solved 4% of problems and tree of thoughts solved 74% (Yao et al., 2023).
  • Use it when: an early wrong choice ruins everything after it, and you can judge partial progress: puzzles, constraint solving, scheduling, some planning.
  • Watch out: branches × depth calls make it many times more expensive and slower. It's rarely worth it for ordinary questions or tool-driven tasks.

Heuristic search: how the tree picks a branch

You can't afford to expand every branch, so you guess which ones are closest to an answer and expand those first. That guess is the heuristic.

A sat-nav doesn't try every road in the country. It prefers roads that point towards the destination, because "straight-line distance left" is a cheap, decent guess. Tree of thoughts works the same way. Some terms:

  • Node: one partial solution, such as "4 + 6 = 10, numbers left: 10, 2, 7".
  • Expand: ask the model for the next few thoughts from a node. Each expansion costs model calls.
  • Frontier: the nodes found so far but not yet expanded.
  • Heuristic, h(n): a score for how promising node n looks. A model prompted to rate it ("sure, likely or impossible to reach 24", as in the tree of thoughts paper), or code: tests passed, constraints met.
  • Cost so far, g(n): what reaching n has already cost, such as steps or tokens.

The search strategy decides which frontier node to expand next. The heuristic decides how good that choice is.

Three candidate thoughts at each step, three steps deep, one answer among 27 endings. Each scored thought is one model call. Switch the scorer to misleading: it rates the wrong first step highest.

A* is guaranteed to find the cheapest path only if h never overestimates the cost left. A model's score gives no such guarantee, so with LLMs treat A* as "best-first that prefers short plans", not as optimal.

The search is only as good as the scorer

  • Prefer a real check: tests that pass, a constraint solver, a calculator, a schema. They're cheap per call and they don't flatter.
  • If the model scores, ask for coarse labels (sure, likely, impossible) rather than 1 to 10, and take a vote of 2 or 3 samples. Models tend to rate their own ideas too kindly.
  • Cap the budget: a beam width of 2 to 5, a depth limit, a maximum number of expansions, and stop at the first answer that passes a real check.

Decoders use beam search too, keeping the k most likely token sequences. It's the same algorithm with tokens as nodes and probability as the score.

Plan-and-execute

Split thinking from doing. A planner, usually a strong model, writes the full list of steps once. An executor, a cheaper model or plain code, runs each step and records the result. The planner may write the final answer from the results.

Plan:
1. get_po(invoice)          3. compare_lines(po, receipts, invoice)
2. get_receipts(po)         4. draft_resolution(differences)
  • Why choose it: fewer calls to the expensive model, independent steps can run in parallel, and the plan is visible, so a person can approve it before anything runs.
  • Related ideas: ReWOO plans tool calls up front without observing in between, and hierarchical task network (HTN) planning breaks a goal into sub-tasks using known procedures.
  • Use it when: the task is long, its steps are mostly known in advance, and cost, parallelism or auditability matter.
  • Watch out: the plan is written before anything is observed. If step 2 reveals a surprise, a pure plan carries on regardless, which is why you add re-planning.

Reflection and re-planning

Add a feedback loop. After an attempt, a check judges it: unit tests, a schema validator, a rule, or a critic model. If it fails, the agent writes down what went wrong (the reflection) and tries again with that note in its context. Reflexion (Shinn et al., 2023) also keeps those notes as memory for later attempts.

  • Re-planning is the same idea for plans: when a step fails or an observation contradicts the plan, the planner rewrites the remaining steps instead of pressing on.
  • Use it when: first attempts are often wrong but a check can tell, such as code with tests, extraction with a schema, or a plan whose steps can fail.
  • Watch out: a model criticising itself with no outside signal can talk itself into a wrong answer. Prefer a real check, cap the retries (2 or 3), and stop when an attempt doesn't improve.

Reasoning under uncertainty

The patterns above decide how an agent lays out its thinking: a line, a loop, a tree or a plan. Inside any of them, each decision also needs a way of drawing a conclusion, and that depends on what the agent knows. When the facts are certain, rules are enough. When they aren't, the agent has to weigh how likely each outcome is against what each one costs. That weighing is called probabilistic or decision-theoretic reasoning, and its everyday tool is expected value: the average cost (or gain) of an action, with each possible outcome weighted by its probability.

Worked example: reroute around a storm?

A logistics agent must decide whether to reroute a shipment around a port that a storm may close. The forecast gives a 40% chance of closure, and the port's sensor feed is incomplete, so the agent cannot confirm either way. Rerouting costs $12k for certain. If the agent keeps the route and the port closes, the delay costs $50k.

keep route: E[cost] = 0.40 × $50k + 0.60 × $0 = $20k  ·  reroute: E[cost] = $12k (certain)  →  reroute, saving $8k on average
  • Break-even probability: rerouting wins whenever p × $50k > $12k, so whenever p > 12 ÷ 50 = 24%. At 40% the agent is well past it.
  • Why the other strategies miss: a rule such as "reroute if closure is more likely than not" (threshold 50%) keeps the route and accepts a $20k expected loss, because it looks at the probability but not the costs. Deduction ("if the port is closed, reroute") can't fire, because the incomplete sensors never establish that the port is closed. Heuristic pruning is for cutting down a large search, not for weighing one uncertain outcome.
  • Value of information: with a perfect forecast the agent would reroute only in the 40% of cases where the port closes, an expected cost of 0.40 × $12k = $4.8k instead of $12k. So perfect information is worth at most $12k − $4.8k = $7.2k. Paying up to that for better sensor data or a sharper forecast, before deciding, is rational; paying more is not.
  • Risk attitude: expected value assumes you are risk-neutral, meaning a sure $12k hurts exactly as much as a 24% chance of $50k. If one $50k loss would break a contract, put that penalty into the cost (a utility function) rather than overriding the arithmetic by gut feel.

They work together. A planner may use heuristic search to shortlist routes, rules to rule out illegal ones, deduction where facts are certain, and expected value to choose between the routes that are left.

Building it into an agent

  • Let tools supply the numbers. In a ReAct loop the model calls a weather tool for the closure probability and a pricing tool for the costs, rather than guessing them.
  • Do the arithmetic in code. A small expected_cost(options) tool is exact and testable; a model doing sums in its head is neither.
  • Use calibrated probabilities. A "40%" that is really 15% gives a confidently wrong answer. See confidence scoring for calibration.
  • Escalate near the break-even point. If p sits close to 24%, or the inputs are stale, the choice is a coin flip on bad data: buy information or ask a person.
  • Log the inputs. Record the probability, costs and resulting values with the decision, so a reviewer can see why the agent rerouted.

Exam pattern: uncertain outcome, a probability, costs for each choice, incomplete data → probabilistic reasoning with expected value. Certain facts plus rules → deductive. Fixed cutoffs on a reading → rule-based. Huge option space that needs cutting fast → heuristic search.

Which one to choose

  1. Can the model answer from what it already has, with some reasoning? Use chain-of-thought, or a reasoning model. Add self-consistency if accuracy matters more than cost.
  2. Does it need tools or fresh data, with a path you can't predict? Use ReAct, with a step limit.
  3. Are the steps known up front, and the task long or costly? Use plan-and-execute, and add re-planning for when a step fails.
  4. Does an early choice decide everything, and can you score partial answers? Use tree of thoughts, if the budget allows.
  5. Can the output be checked? Wrap whichever pattern you chose in a reflection loop.
  6. Does a decision hinge on an uncertain outcome with known costs? Compute expected value in a tool, whichever pattern carries the loop.

Saying it in an interview

"I pick the cheapest pattern that solves the task. If the facts are in the prompt, chain-of-thought or a reasoning model in one call. If it needs tools and the path is unclear, a ReAct loop with a step cap. If the steps are known and the job is long, plan-and-execute: a strong model plans, cheap steps run in parallel, a person can approve the plan, and failures trigger re-planning. Tree of thoughts only when early choices decide everything and I can score partial solutions, because it multiplies cost. And whenever the output can be checked, I add a reflection loop with a real check and a retry cap."
