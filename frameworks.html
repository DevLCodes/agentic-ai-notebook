Framework Utilisation

Six frameworks, one custom loop, and how to make them work together. Every framework is the same agentic loop with opinions on top. Learn the opinions, and you can debug any of them.

0 · What a framework actually gives you

  • Frameworks buy you speed: tool schemas from type hints, retries, streaming, state, and a dev UI.
  • They cost you visibility: another layer between you and the messages array, plus version churn.
  • Each one has a core idea. CrewAI: roles. ADK: agent trees. LangGraph: state graphs. LlamaIndex: typed events. SK: plugins and filters. AutoGen: conversations.

Part A · The frameworks

A1 · CrewAI orchestration

Core idea: a crew of role-playing agents working through a list of tasks. You describe who (role, goal, backstory) and what (tasks with an expected_output), and a Process decides the order.

from crewai import Agent, Task, Crew, Process

researcher = Agent(role="Weather researcher",
    goal="Find the afternoon forecast",
    backstory="Checks two sources before answering.",
    tools=[forecast_tool])
advisor = Agent(role="Advisor", goal="One clear recommendation",
    backstory="Blunt and practical.")

research = Task(description="Hourly forecast for {city}",
    expected_output="rain hours as a list", agent=researcher)
advise = Task(description="Umbrella or not?",
    expected_output="yes/no + one reason", agent=advisor,
    context=[research])        # gets research's output

crew = Crew(agents=[researcher, advisor], tasks=[research, advise],
            process=Process.sequential)
crew.kickoff(inputs={"city": "Paris"})

# Flows: deterministic, event-driven control around crews
from crewai.flow.flow import Flow, start, listen, router

class Trip(Flow):
    @start()
    def pick_city(self):
        self.state["city"] = "Paris"

    @listen(pick_city)
    def forecast(self):
        self.state["rain"] = WeatherCrew().crew().kickoff(
            inputs={"city": self.state["city"]}).raw

    @router(forecast)
    def decide(self):
        return "wet" if "yes" in self.state["rain"] else "dry"

    def pack_umbrella(self): ...
Crews vs Flows
  • Crew: autonomy. The agents collaborate and may delegate (allow_delegation=True).
  • Flow: control. Plain Python steps with shared state and branches through @router, and a crew can run as one step.
  • Production pattern: a Flow on the outside, small crews inside.
  • Also useful: memory=True, human_input=True on a task, and output_pydantic for typed results.

A2 · Google ADK (Agent Development Kit)

Core idea: a tree of agents. LlmAgents do the thinking. Workflow agents (SequentialAgent, ParallelAgent, LoopAgent) arrange them deterministically, with no LLM involved. It's model-agnostic but built for Gemini and Google Cloud.

from google.adk.agents import Agent, SequentialAgent

def get_forecast(city: str) -> dict:
    """Hourly rain forecast for a city."""   # docstring + hints = schema
    return {"rain_hours": ["15:00", "16:00"]}

weather = Agent(name="weather", model="gemini-2.5-flash",
    instruction="Answer weather questions with get_forecast.",
    tools=[get_forecast],
    output_key="forecast")          # reply → session.state["forecast"]

advisor = Agent(name="advisor", model="gemini-2.5-flash",
    instruction="Given {forecast}, say umbrella yes or no.")

root_agent = SequentialAgent(name="trip", sub_agents=[weather, advisor])
# adk web   → local dev UI with an event trace
# adk eval  → run eval sets · deploy: Cloud Run / Vertex AI Agent Engine

The ADK runtime pieces
  • Runner drives the loop and yields Events: every model reply, tool call and state change.
  • SessionService (in-memory, database or Vertex) stores session.state, where output_key writes and {key} reads.
  • Callbacks such as before_model_callback and before_tool_callback are your guardrails and logging hooks.
  • AgentTool wraps an agent as a tool. MCPToolset connects to MCP servers. A2A support lets agents talk across services.

A3 · LangChain architecture (and LangGraph)

Core idea: everything is a Runnable. Prompts, models, parsers and retrievers all share invoke, stream and batch, so they chain with | (LCEL). For agents, LangGraph adds state, cycles and checkpoints. Click a layer to see what it does.

# LCEL: a pipe of Runnables
chain = prompt | model | StrOutputParser()
chain.invoke({"city": "Paris"})       # or .stream / .batch

# Agent (LangChain 1.x): a prebuilt LangGraph agent
from langchain.agents import create_agent
agent = create_agent(model="anthropic:claude-sonnet-5",
                     tools=[get_forecast],
                     system_prompt="Answer umbrella questions.")
agent.invoke({"messages": [{"role": "user",
                            "content": "Umbrella in Paris?"}]})
# LangGraph: the loop, drawn as a graph
from langgraph.graph import StateGraph, START, END
g = StateGraph(State)
g.add_node("model", call_model)
g.add_node("tools", run_tools)
g.add_edge(START, "model")
g.add_conditional_edges("model",
    lambda s: "tools" if s["messages"][-1].tool_calls else END)
g.add_edge("tools", "model")
app = g.compile(checkpointer=saver)   # resume · interrupt() · time travel

A4 · LlamaIndex Workflows

Core idea: steps that listen for typed events. A step's type hint is its wiring: it runs when an event of its input type appears, and whatever event it returns decides what runs next. It's async-first and pairs naturally with LlamaIndex's RAG tools.

from llama_index.core.workflow import (Workflow, step, Event,
    StartEvent, StopEvent, Context)

class Retrieved(Event):
    nodes: list

class Retry(Event):
    query: str

class RAGFlow(Workflow):
    @step
    async def retrieve(self, ctx: Context,
                       ev: StartEvent | Retry) -> Retrieved:
        await ctx.store.set("query", ev.query)
        return Retrieved(nodes=retriever.retrieve(ev.query))

    @step
    async def answer(self, ctx: Context,
                     ev: Retrieved) -> StopEvent | Retry:
        if not ev.nodes:                        # loop back
            return Retry(query=rewrite(await ctx.store.get("query")))
        return StopEvent(result=await llm.acomplete(...))

result = await RAGFlow(timeout=60).run(query="Umbrella policy?")
Context tricks
  • ctx.store: shared state across steps (older versions: ctx.set / ctx.get)
  • ctx.send_event + ctx.collect_events: fan out, then wait for all
  • ctx.write_event_to_stream: stream progress to a UI
  • @step(num_workers=4): run a step concurrently
  • Ready-made agents: FunctionAgent, ReActAgent, and AgentWorkflow for handoffs

A5 · Semantic Kernel usage

Core idea: a Kernel holding AI services and plugins. A plugin is a class of @kernel_functions (C#: [KernelFunction]), and filters wrap every call like middleware. It's Microsoft's enterprise option for C#, Python and Java, with Azure first-class.

from semantic_kernel.agents import ChatCompletionAgent
from semantic_kernel.connectors.ai.open_ai import AzureChatCompletion
from semantic_kernel.functions import kernel_function

class WeatherPlugin:
    @kernel_function(description="Hourly rain forecast for a city")
    def get_forecast(self, city: str) -> str:
        return '{"rain_hours": ["15:00", "16:00"]}'

agent = ChatCompletionAgent(service=AzureChatCompletion(),
    name="advisor", instructions="Answer umbrella questions.",
    plugins=[WeatherPlugin()])
reply = await agent.get_response(messages="Umbrella in Paris?")
# outside agents: FunctionChoiceBehavior.Auto() in the
# execution settings lets the model call kernel functions
# a function-invocation filter = middleware around every tool call
@kernel.filter(FilterTypes.FUNCTION_INVOCATION)
async def approval(context, next):
    if context.function.plugin_name in {"email", "files"} \
            and not await ask_human(context):
        context.result = FunctionResult(
            function=context.function.metadata, value="denied")
        return                        # next() never called
    await next(context)               # run the function

A6 · AutoGen configuration

Core idea: agents that talk to each other in a team until a termination condition fires. From v0.4 it's layered: autogen-core (an event-driven actor runtime), autogen-agentchat (agents and teams) and autogen-ext (model clients, code executors, MCP).

from autogen_agentchat.agents import AssistantAgent
from autogen_agentchat.teams import RoundRobinGroupChat
from autogen_agentchat.conditions import (
    TextMentionTermination, MaxMessageTermination)
from autogen_ext.models.openai import OpenAIChatCompletionClient

model = OpenAIChatCompletionClient(model="gpt-4o")
writer = AssistantAgent("writer", model_client=model,
    tools=[get_forecast], system_message="Draft the answer.")
critic = AssistantAgent("critic", model_client=model,
    system_message="Review it. Say TERMINATE when it's good.")

stop = TextMentionTermination("TERMINATE") | MaxMessageTermination(12)
team = RoundRobinGroupChat([writer, critic], termination_condition=stop)
result = await team.run(task="Umbrella in Paris this afternoon?")

team typeRoundRobinGroupChat (take turns), SelectorGroupChat (a model picks the next speaker), Swarm (handoffs), MagenticOneGroupChat (an orchestrator with a plan)
terminationcombine with | (either) and & (both). Always keep a backstop.
model_clientOpenAI, Azure, Anthropic, Ollama and more, from autogen-ext

Part B · Beyond one framework

B1 · Custom agent loops

Sometimes the best framework is 15 lines of SDK code you fully understand. This is the whole loop from page ①, with no hidden prompts or retries and nothing to upgrade.

import anthropic
client = anthropic.Anthropic()
messages = [{"role": "user", "content": task}]

for _ in range(MAX_STEPS):          # backstop only, not the exit
    r = client.messages.create(model="claude-sonnet-5",
            max_tokens=1024, tools=TOOLS, messages=messages)
    messages.append({"role": "assistant", "content": r.content})
    if r.stop_reason != "tool_use":
        break                       # end_turn (handle the others)
    messages.append({"role": "user", "content": [
        {"type": "tool_result", "tool_use_id": b.id,
         "content": run(b.name, b.input)}
        for b in r.content if b.type == "tool_use"]})
you now own…a framework gives you
tool schemasgenerated from type hints and docstrings
retries, backoff, timeoutsbuilt in
state + resume after a crashcheckpointers and session services
pause for a humaninterrupt(), confirmation hooks
tracinga dev UI plus OpenTelemetry out of the box
multi-agent routingteams, handoffs, workflow agents
Custom wins when…
  • the flow is simple, like one agent with a few tools
  • you need exact control of prompts, caching and tokens
  • you can't afford dependency churn in production
  • you're learning, so build it once by hand to see what frameworks hide
A framework wins when…
  • you need durable state, pause/resume, or long-running jobs
  • many agents and routing patterns are involved
  • the team needs shared conventions and a dev UI
  • its integrations (RAG, vector stores, MCP) save you weeks

B2 · Framework integration

Real systems mix frameworks. Keep tools, prompts and evals framework-free, and let standard protocols do the joining.

patternuse it for
🔌 MCPwrite a tool once as an MCP server, and every framework can consume it: LangChain langchain-mcp-adapters, ADK MCPToolset, CrewAI MCPServerAdapter, LlamaIndex McpToolSpec, AutoGen McpWorkbench, SK MCP plugins
🤝 A2Aagent-to-agent over HTTP between services, teams or companies. Each agent publishes an agent card.
🧩 agent-as-toolwrap one agent or crew as a callable tool inside another framework, in the same process
🔭 OpenTelemetryone trace across frameworks, sent to Langfuse, LangSmith, Phoenix or Datadog
🔀 LiteLLMone model interface across providers (CrewAI uses it internally, and ADK has LiteLlm)
Integration traps
  • Loops inside loops: an agent inside another framework's agent doubles the retries, the memories and the costs.
  • Two sources of truth for state. Pick one owner.
  • Lock-in by stealth: prompts buried in framework classes. Keep them in files you version.
  • Version drift: pin versions, and re-run the eval suite on every upgrade.
