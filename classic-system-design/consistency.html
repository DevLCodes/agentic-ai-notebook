Consistency and CAP

When data lives on several machines, deciding what a reader is allowed to see, and what you give up when the network breaks.

Why it comes up

As soon as you replicate data, copies can disagree for a moment. Consistency models describe how big that moment is, and what a reader might see during it.

Example: Priya changes her display name. The write lands on one replica in Mumbai. A second later her friend in London reads from a London replica that hasn't received the change. Is that a bug? For a display name, no. For a bank balance or the last seat on a flight, yes. Choosing per piece of data is the real design skill.

CAP, said precisely

The CAP theorem says: during a network partition, a replicated system must choose between consistency (every read sees the latest write, or gets an error) and availability (every request gets a non-error answer). Partitions happen in any real network, so "CA" is not a real option for a distributed system.

PACELC adds the more everyday part: if Partitioned, choose Availability or Consistency; Else, choose Latency or Consistency. Even with a healthy network, waiting for replicas in other regions to confirm a write costs tens to hundreds of milliseconds. Most of the time, the latency trade is the one you actually feel.

Consistency models

ModelA reader seesTypical use
Strong (linearizable)The latest committed write, as if there were one copyBalances, inventory, unique usernames, leader election, locks
Read-your-writesAt least their own latest writesProfile edits, posting a comment and seeing it
Monotonic readsNever an older value after a newer oneAvoiding "the comment appeared, then vanished on refresh"
CausalEffects after their causes (a reply after the message it replies to)Chat, comment threads, collaborative apps
EventualSome value; all replicas converge if writes stopLike counts, view counts, feeds, recommendations, DNS

Most products mix them: strong consistency for money and inventory, read-your-writes for the user's own content, and eventual for everything else. Saying this out loud in an interview is worth more than reciting CAP.

Quorums

Leaderless stores such as Cassandra and DynamoDB write each item to N replicas. A write succeeds when W replicas confirm it; a read asks R replicas and takes the newest value. If R + W > N, every read set overlaps every write set in at least one replica, so a read sees the latest successful write (barring edge cases like concurrent writes and clock skew).

N = 3, W = 2, R = 2 → 2 + 2 > 3 → reads overlap the latest write; survives 1 replica down

Try it: tune a quorum

Pick a replication factor and quorum sizes. The lab shows which replicas confirmed the latest write, a sample read, and what the settings cost.

Simplified: the write reached exactly W replicas before the read; the others still hold the old value. In real systems, the rest catch up within milliseconds through background repair.

In practice

Leaders make strong consistency easier

With a single leader per piece of data (Postgres, or each range in Spanner and CockroachDB), reading from the leader is strongly consistent. Consensus protocols like Raft and Paxos keep a majority of replicas agreed on the log, so a leader can fail without losing committed writes. etcd and ZooKeeper use them to store small, critical state such as config and locks.

Conflicts

When two replicas accept different writes to the same item, something must pick. Last write wins by timestamp is simple but silently drops one write, and clocks drift. Alternatives: version numbers with compare-and-set, keep both versions and let the app merge, or CRDTs, data types such as counters and sets that merge automatically.

Across services

Two services with two databases can't share one transaction. Use a saga: a sequence of local steps, each with a compensating action if a later step fails (reserve stock, charge card; if the charge fails, release the stock). Pair it with the outbox pattern from Message queues.

Saying it in an interview

"Not everything needs the same guarantee. Seat inventory and payments need strong consistency, so they live in a single-leader database and go through transactions; during a partition we'd rather reject a booking than double-sell a seat. Users must always see their own reviews right after posting, so those reads go to the leader for a short window. Ratings, counts and recommendations are eventually consistent and served from replicas and caches, which keeps them fast and available."
