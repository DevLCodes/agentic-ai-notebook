Message queues and streams

Letting one part of a system hand work to another without waiting, so slow steps, bursts and failures don't spread.

Why queues

A queue sits between a producer and a consumer. The producer drops a message and moves on; consumers process messages at their own pace.

  • Decoupling. Producers don't need to know who consumes, or whether consumers are up right now.
  • Absorbing bursts. A flash sale produces 10× normal orders for ten minutes; the queue grows and workers drain it, instead of the database falling over.
  • Faster responses. Slow work (video encoding, emails, reports) leaves the request path.
  • Retries. A failed message can be retried later without the user retrying.

The cost: the work is now eventually done, not done when the request returns. The user interface has to show "processing", and you need monitoring for queue depth and age.

A third pattern, publish/subscribe (Amazon SNS, Google Pub/Sub), fans one message out to many subscribers, each often with its own queue.

Partitions and ordering

Kafka splits a topic into partitions. Messages with the same key (say order_id) go to the same partition and stay in order; different partitions are processed in parallel. You can run at most one consumer per partition in a group, so the partition count caps parallelism. Choose it with growth in mind.

Delivery guarantees

GuaranteeMeansWhen
At most onceNever redelivered; can be lostMetrics where losing a few is fine
At least onceNever lost; can be delivered twiceThe usual default
Exactly onceProcessed effectively onceOnly within a system that supports it end to end (Kafka transactions); across systems, build it from at-least-once plus idempotency

Duplicates happen: a worker finishes the work, then crashes before acknowledging, and the message is redelivered. So make consumers idempotent: processing a message twice has the same effect as once. Give each message a unique ID and record processed IDs (for example, a unique constraint on payment_id), or design writes as "set to X" rather than "add X".

A common bug: write to the database, then publish an event. If the process dies between the two, the event is lost. The outbox pattern writes the event to an outbox table in the same transaction as the data; a separate relay publishes rows from the outbox.

Try it: a burst

Orders normally arrive at 100 per second. At minute 2 a sale starts and traffic jumps for 5 minutes. Each worker handles 25 orders per second. How many workers keep the delay acceptable?

A simple fluid model, one step per second. Autoscaling adds workers when the backlog is older than 30 seconds, with 60 seconds of startup delay, up to 20 workers.

Failure handling

Retries and dead-letter queues

Retry transient failures with exponential backoff. After a few attempts (say 5), move the message to a dead-letter queue (DLQ) so one bad message ("poison pill") doesn't block or burn workers forever. Alert on DLQ size and give engineers a way to inspect and replay it.

Visibility timeout

In SQS-style queues, a received message is hidden for a timeout. If the worker doesn't delete it in time, it reappears for another worker. Set the timeout longer than the slowest normal processing time, or extend it while working.

Backpressure

A queue hides overload for a while, but if consumers are slower than producers for long enough, the backlog grows without limit. Watch the age of the oldest message, not just the count, scale consumers on it, and when you can't keep up, slow producers down or shed low-priority work.

Saying it in an interview

"Placing an order writes the order and an outbox row in one transaction and returns. A relay publishes to a Kafka topic partitioned by order_id, so events for one order stay in order. Payment, email and search each consume as their own group, at least once, and each is idempotent on the event ID. Failures retry with backoff and land in a dead-letter queue after five tries. Workers autoscale on consumer lag, and we alert when the oldest message is more than a minute old."
