Load balancing

Spreading requests across many servers so no single one is overloaded, and so one failing server does not take the service down.

What a load balancer does

A load balancer sits in front of a pool of identical servers. Clients talk to one address; the balancer picks a healthy server for each connection or request.

It gives you three things at once: scale (add servers to add capacity), availability (a dead server is skipped), and a single stable entry point where you can terminate TLS, apply rate limits and roll out new versions gradually.

For this to work, the servers behind it should be stateless: any server can handle any request because session data lives in a shared store such as Redis or the database, not in one server's memory.

Choosing a server

AlgorithmHow it picksGood forWatch out for
Round robinNext server in turnIdentical servers, similar requestsIgnores load; a slow server still gets its full share
Weighted round robinTurns in proportion to a weightMixed instance sizesWeights are static guesses
Least connectionsServer with the fewest open requestsRequests of very different lengthsNeeds a global view of counts; hard across many balancers
Power of two choicesPick two at random, send to the less busy oneMany balancers, large poolsSlightly worse than perfect least-connections, far better than random
Hashing (IP, user, key)Same key always goes to the same serverCaches and sticky sessionsPlain hash % N reshuffles almost everything when N changes; use consistent hashing

Power of two choices is worth remembering: checking just two random servers instead of one makes the worst queue dramatically shorter, without every balancer needing up-to-date counts for every server.

Health checks and failure

Health checks

The balancer calls something like GET /healthz every few seconds. After a few failures in a row the server is taken out; after a few successes it goes back in. A liveness check asks "is the process up?"; a readiness check asks "can it serve right now?" (database reachable, caches warm). Keep the readiness check cheap, or the checks themselves become load.

Connection draining

When you deploy or scale in, stop sending new requests to a server but let in-flight ones finish for a grace period, often 30 seconds. Without this, every deploy produces a burst of errors.

Sticky sessions

Pinning a user to one server with a cookie makes in-memory sessions work, but it fights the balancer: load becomes uneven and a server failure logs everyone on it out. Prefer stateless servers with a shared session store.

The balancer itself

A single balancer is a single point of failure. Run them in pairs or fleets, behind DNS with several addresses or an anycast IP, and spread servers across availability zones so losing one zone loses a fraction of capacity, not the service. Managed cloud balancers handle this for you.

Retries

Retrying a failed request on another server hides individual failures, but retries add load exactly when the system is struggling. Cap them (one retry, or a retry budget of about 10% of traffic), only retry safe or idempotent requests, and add jittered backoff.

Saying it in an interview

"Clients hit a managed L7 load balancer that terminates TLS and spreads requests across stateless app servers in three zones; sessions live in Redis so any server can take any request. I'd use least-outstanding-requests or power of two choices rather than round robin, so one slow instance doesn't build a queue. Health checks remove bad instances, deploys drain connections, and retries are capped to one, only for idempotent calls, so a partial outage doesn't turn into a retry storm."
