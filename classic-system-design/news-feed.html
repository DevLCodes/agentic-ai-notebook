Requirements

  • Clarify

The feed is read far more than it is written, and follower counts are wildly uneven. Those two facts drive the whole design.

Daily active users200M, each opening the feed ~10 times a daySets read load: billions of feed loads a day

Feed latencyp99 under 200 ms for the first pageThe feed is the first screen of the app
FreshnessA new post appears for followers within ~5 seconds; celebrities within ~1 minute is fineLets fan-out be asynchronous

Out of scope for v1: comments and likes as full features (we only show counts), direct messages, search and ads. Say so explicitly, so the interviewer knows you chose rather than forgot.

Estimates

  • Back of the envelope
  • Numbers
  • Posts: 100M ÷ 86,400 s ≈ 1,200 a second; peaks of about 3× are 3,500 a second.
  • Feed loads: 200M users × 10 opens = 2B a day ≈ 23,000 a second, about 70,000 at the evening peak. Each load wants a page of ~20 posts.
  • Fan-out: follower counts are skewed, so the average post reaches far more people than the average user has followers. With the distribution in the lab, pushing every post to every follower would be over 2 million timeline inserts a second. Pulling celebrities instead brings that to around 400,000.
  • Timeline cache: keep the newest 500 post IDs per user, at ~16 bytes each (8-byte ID plus a score): 8 KB a user, ≈ 1.6 TB for 200M users. That's a big Redis cluster (around 100 nodes with replicas), so keep timelines only for users active in the last few weeks and rebuild the rest on demand.
  • Posts: ~1 KB of text and metadata each is 100 GB a day, ~36 TB a year before replication. Media on 20% of posts at ~500 KB is ~10 TB a day, which belongs in object storage.

Cursors, not page numbers

New posts arrive at the top while you scroll, so ?page=2 would show duplicates or skip posts. The cursor encodes where the last page ended (the last post's ID for "latest", or a snapshot ID plus position for ranked), so the next page continues from exactly there. The idempotency_key on create stops a retried request on a flaky phone connection from posting twice.

Architecture

  • Whole system
  • Post API stores the post, then publishes a small "new post" event. It never touches followers' timelines itself, so posting stays fast even for a celebrity.
  • Fan-out workers consume those events, page through the author's followers in the follow graph, and push the post ID onto each follower's timeline. Celebrities are skipped.
  • Timeline cache holds, per user, a sorted list of the newest ~500 post IDs. It holds IDs only, never post bodies, so an edit or delete changes one row, not millions of copies.
  • Feed service reads the timeline, merges in recent posts from celebrities the reader follows, fetches post bodies and counts from the post cache, asks the ranker to order them, and returns a page.

Fan-out: push, pull or both

  • Deep dive 1
  • Queues

The central decision: do we build each feed when someone posts (push), when someone reads (pull), or mix the two?

ApproachHowProsCons
Pull (fan-out on read)On every feed load, look up everyone I follow, fetch their recent posts, merge and sortPosting is one write; no wasted work for people who never open the appA feed load touches ~200 accounts; at 70k loads a second that's 14M lookups a second on the hot path, and latency is set by the slowest one
Push (fan-out on write)When someone posts, append the post ID to every follower's timelineA feed load is one cache read plus hydration: fast and predictableOne post by an account with 50M followers is 50M writes; followers see it minutes late; work is wasted on inactive followers
HybridPush for ordinary accounts; for accounts above a follower threshold, skip the push and merge their recent posts at read timeFast reads, bounded write stormsTwo code paths; the read side must merge, dedupe and paginate across sources

I'd use the hybrid. Each account has a fanout_mode flag, flipped to pull when it crosses a threshold (say 10,000 followers). Celebrity posts go into a small per-author "recent posts" list that every feed service instance caches heavily, since millions of readers ask for the same few lists.

Making fan-out safe

  • Batch it. A worker reads followers 1,000 at a time and writes with Redis pipelines, then checkpoints its position, so a crash resumes instead of restarting.
  • Idempotent inserts. Timelines are sorted sets keyed by post ID, so a retried batch re-adds the same members and nothing duplicates.
  • Skip the inactive. Followers who haven't opened the app in 30 days have no cached timeline. Don't write to them; their feed is rebuilt by pull when they return.
  • Trim on write. After each insert, trim the timeline to 500 entries. Older posts come from the posts store if someone scrolls that far.
  • Separate queues by size. A 90,000-follower fan-out shouldn't sit in front of a thousand 200-follower ones. Route big jobs to their own partition so small posts stay within the 5-second freshness target.

Try it: where to draw the celebrity line

  • Lab

Move the threshold. Accounts at or below it are pushed into followers' timelines when they post; accounts above it are pulled when someone loads their feed. Watch the write rate, the extra work on every feed load, and how long the slowest push takes.

Storage

  • Databases
  • Sharding
posts            -- Cassandra / DynamoDB, partition by post_id
  post_id     bigint   PRIMARY KEY     -- Snowflake ID: time-sortable
  author_id   bigint
  text        string
  media       list<media_ref>
  created_at  timestamp
  status      enum      -- live | deleted | removed

posts_by_author  -- partition by author_id, cluster by post_id DESC
  author_id, post_id                  -- "recent posts by X", used for pull

follows          -- two tables, both directions
  followers(user_id, follower_id)     -- who to fan out to
  following(user_id, followee_id)     -- who I follow, for pull and rebuilds

timeline:{user_id}  -- Redis sorted set: member = post_id, score = post_id
  • Post IDs are time-sortable (Snowflake-style: timestamp, machine ID, sequence), so sorting by ID is sorting by time, timelines can use the ID as the score, and no central counter is needed.
  • The follow graph is stored twice, once per direction, because fan-out asks "who follows X?" and pull asks "who does Y follow?". Both are a single partition read. A celebrity's follower list is huge, so page through it in chunks.
  • Counts live elsewhere. Like and reply counts change constantly. Keep them in a separate counter service (sharded counters in Redis, flushed to a store) so hot posts don't hammer the posts table.

Reading a feed

  • Deep dive 2
  • Caching

Every feed load does four things inside a 200 ms budget: gather candidates, hydrate them, rank them, and return a page.

  1. Gather candidates (~10 ms). Read the top few hundred IDs from timeline:{me}, and in parallel fetch recent posts for each celebrity I follow from their cached "recent posts" lists. Merge and drop duplicates.
  2. Hydrate (~20 ms). Fetch post bodies, author names and avatars, and counts with one batched multi-get against the post cache (Redis or Memcached in front of the posts store). Drop posts that are deleted, removed, or by people I've since blocked or muted.
  3. Rank (~50 ms). Send a few hundred candidates with features to the ranker; keep the top ones.
  4. Return a page of 20, with a cursor. Store the ranked list briefly (a few minutes, keyed by a snapshot ID) so the next page continues the same order instead of re-ranking and reshuffling.

Rebuilding a cold timeline

A user who returns after two months has no cached timeline. The feed service falls back to pull for that one load: read following, fetch recent posts per followee (in parallel, capped), merge, then write the result back into the cache so the next load is fast. Do the same for a brand-new user, who also needs suggested accounts so their first feed isn't empty.

Deletes and edits

Because timelines hold IDs, a deleted post only needs its status set and its post-cache entry purged. It vanishes from every feed at hydration time, without hunting down millions of timeline entries.

Ranking

  • Relevance

Chronological order is a sort by post ID. A ranked feed scores each candidate with the predicted chance that this reader engages with it: like, reply, share, or dwell for a few seconds.

  • Features: how often I interact with the author, post age, the post's early engagement rate, media type, and whether people like me engaged.
  • Two stages. A cheap model or heuristic trims ~500 candidates to ~100; a heavier model (gradient-boosted trees or a small neural net) scores those. Precompute per-user and per-author features offline and keep them in a feature store, so ranking time is spent scoring, not fetching.
  • Rules after the model: no more than two posts in a row from one author, demote content flagged by trust and safety, and always include fresh posts from close friends.
  • Degrade gracefully. If the ranker is slow or down, serve the chronological timeline. A slightly worse feed beats an error screen.

Ranking quality is measured online with A/B tests on sessions and engagement, and guarded by metrics such as hides, reports and unfollows.

Photos and video

  • Media

Media never passes through the feed service. The app asks for an upload URL, uploads the file directly to object storage (S3 or GCS) with that pre-signed URL, then creates the post with the returned media_id. A background pipeline makes thumbnails and several sizes (and transcodes video into a few bitrates for adaptive streaming), and the feed returns CDN URLs. A post whose media is still processing shows a placeholder, or is held back from fan-out until the media is ready.

Deployment and regions

  • Production
  • Load balancing

Users are served from the nearest of several regions. Posts and the follow graph are replicated to every region (multi-region Cassandra or DynamoDB global tables). Kafka topics are mirrored between regions, and each region runs its own fan-out into its own timeline caches, so a feed load never crosses an ocean.

Timeline caches are rebuildable. They are derived data: if a Redis node or a whole region's cache is lost, timelines can be rebuilt from posts and follows. Make that rebuild path a tested, rate-limited job, because after an outage every user's first load is a cold miss, and a thundering herd of pull rebuilds can take down the posts store.

Services are stateless containers, autoscaled on request rate; fan-out workers autoscale on Kafka consumer lag. Roll out feed-service and ranker changes as canaries, watching latency, error rate and engagement before going wide.

"Feed loads outnumber posts about twenty to one, so I'd precompute feeds. A post is stored once and an event goes to Kafka; fan-out workers push the post ID into each active follower's Redis timeline. Accounts above about 10,000 followers are not pushed. Their posts are merged in at read time from a heavily cached recent-posts list, which caps the write storm; a reader merges a few dozen of those. A feed load reads the timeline, merges celebrity posts, hydrates bodies from the post cache, ranks a few hundred candidates and returns 20 with a cursor. Timelines hold IDs only, so deletes are instant, and they're rebuildable, so losing the cache costs latency, not data."
