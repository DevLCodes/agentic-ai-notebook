Chat Service

Design a messaging app: one-to-one and group chats up to 500 people, delivered in real time when people are online and as soon as they come back when they aren't, with sent, delivered and read receipts, on several devices per user. Plan for 100 million daily users.

Requirements

  • Clarify

Chat looks like "store a message, show it to the other person". The interview is about holding millions of open connections, never losing or reordering a message, and handling people who are offline.

Estimates

  • Back of the envelope
  • Numbers
  • Messages: 100M users × 50 = 5B a day ≈ 58,000 a second; the evening peak is about 3× that, 170,000 a second. Group messages are stored once but delivered to every member, so deliveries are several times higher.
  • Connections: 25% of 100M online at peak is 25M open WebSockets. A tuned server holds 100k–500k idle connections (memory, not CPU, is the limit), so at 200k each that's 125 servers, about 170 with headroom for a zone failure.
  • Control traffic: each message produces a delivered receipt, often a read receipt, and typing indicators before it. Presence heartbeats from 25M devices every 30 s add ~830,000 small events a second. These are cheap individually, but together they outnumber messages.
  • Storage: ~300 bytes a message (text, IDs, timestamps) is 1.5 TB a day, ~550 TB a year before replication. Keep recent months on fast storage and older history in cheaper tiers. Media goes to object storage.

API and protocol

  • Interface

Clients keep one WebSocket open while the app is in the foreground and exchange small JSON (or protobuf) frames over it. REST is used for everything that isn't real time.

// client → server
{ "type": "send", "client_msg_id": "c-7f3a…", "conv_id": "g_219", "text": "on my way" }
{ "type": "ack",  "conv_id": "g_219", "seq": 4182 }          // delivered to this device
{ "type": "read", "conv_id": "g_219", "seq": 4182 }          // read up to here
{ "type": "ping" }                                            // heartbeat every ~30 s

// server → client
{ "type": "sent",    "client_msg_id": "c-7f3a…", "seq": 4183 }  // stored: show one tick
{ "type": "message", "conv_id": "g_219", "seq": 4183, "from": "u_88", "text": "…" }
{ "type": "receipt", "conv_id": "g_219", "user": "u_12", "delivered_up_to": 4183 }

// REST
GET  /v1/conversations/{id}/messages?after_seq=4100&limit=100   // catch-up and history
POST /v1/media/uploads → { media_id, upload_url }                 // direct to object storage

Why WebSockets

Polling every few seconds wastes battery and adds latency; long polling works but re-opens a request after every message. A WebSocket is one TCP connection kept open, so the server can push a message the moment it arrives. On mobile, when the app goes to the background the OS kills the socket, and push notifications (APNs, FCM) take over.

Architecture

  • Whole system
  • Gateways terminate WebSockets and keep nothing but the open connections and which user each one belongs to. They are the only stateful tier, so they are kept dumb and are easy to replace.
  • Chat service handles each incoming frame: deduplicate by client_msg_id, assign the conversation's next sequence number, write the message, acknowledge the sender, then route it to recipients.
  • Session registry (Redis) maps each user's devices to the gateway they're connected to, written on connect and expired by TTL if heartbeats stop.
  • Messages store holds every message by conversation and sequence, which serves history, multi-device sync and catch-up after reconnects.
  • Kafka carries "message stored" events to slower consumers: push notifications for offline users, unread counters, search indexing later.

Ordering and delivery

  • Deep dive 1
  • Consistency

Two promises: everyone sees a conversation in the same order, and a message the sender saw as "sent" always arrives exactly once on screen.

A sequence number per conversation

Timestamps from phones can't order messages: clocks drift and two messages in the same millisecond tie. Instead the server gives each message in a conversation the next integer: 4182, 4183, 4184. Clients sort by it, and a gap (they have 4181 and 4184) tells them exactly what to fetch.

OptionHowTrade-off
Redis INCR conv:{id}Atomic counter per conversationSimple and fast; needs Redis persistence and care on failover so numbers never go backwards
Single owner per conversationConsistent-hash each conversation to one chat-service shard, which keeps the counter in memory and persists it with each message writeNo extra hop; ordering is local. Reassigning a shard must hand over the counter (read the last seq from the store)
Database conditional writeInsert with seq = last + 1 only if absentStrong, but a contended hot group retries a lot

Only order within a conversation matters, so there's no global sequence and no global bottleneck. A 500-person group at peak sends a few messages a second, nowhere near the limit of one counter.

At-least-once plus dedupe

  1. The client sends with a random client_msg_id and shows a clock icon.
  2. The chat service checks a short-lived dedupe set for that ID. A repeat gets the original sent reply again and nothing else happens.
  3. It assigns seq, writes the message durably, and only then replies sent (one tick). If the reply is lost, the client resends with the same ID, which is safe.
  4. Delivery to recipients is at-least-once: gateways may push the same seq twice after a reconnect, and clients ignore a seq they already have.
  5. Each device acks the highest seq it has stored. That ack becomes the delivered receipt (two ticks) and tells the server where this device's catch-up starts next time.

Sync by position, not by push. Pushing over the socket is the fast path, but it isn't what correctness rests on. Every time a device connects it asks "what's after seq N in each of my conversations?" and fills any gaps from the store. A missed push therefore delays a message but never loses it.

Millions of open connections

  • Deep dive 2
  • Load balancing

A gateway is cheap per connection, but there are 25 million connections, and they all reconnect at once when something goes wrong.

  • Event-driven servers. Gateways use non-blocking I/O (Netty, Go, Erlang/Elixir), so an idle connection costs a few KB of memory and no thread. Raise the OS file-descriptor limits and tune TCP buffers.
  • An L4 load balancer spreads new connections across gateways. Long-lived connections don't rebalance themselves, so new servers only fill as clients reconnect; plan for that when scaling out.
  • Heartbeats. Mobile networks silently drop idle connections, and NAT gateways forget them after a few minutes. A ping every ~30 s keeps the path open and lets both sides detect a dead connection quickly. The registry entry expires if pings stop.
  • Reconnect storms. When a gateway with 200k connections dies, 200k clients reconnect. If they all retry immediately they hit the remaining gateways and the registry at once, and the overload can spread. Clients use exponential backoff with random jitter spread over tens of seconds.
  • Deploys drain. A gateway being replaced stops accepting connections and closes existing ones gradually over minutes, with a "reconnect elsewhere" frame, instead of dropping them all at once.

Try it: size the gateway fleet

  • Lab

Change how many people use the app, how many are online at peak, how many sockets one gateway holds, and how far clients spread their reconnects. See the fleet size, heartbeat load, and what one crashed gateway does to the others.

Illustrative model: 30% headroom on top of peak connections, one heartbeat every 30 s per connection, and a gateway can accept about 5,000 new connections a second (TLS handshakes are the expensive part).

Group chats

  • Fan-out
  • Queues

A group message is stored once, with one sequence number, and delivered to every member's online devices. For a 500-member group that's up to 500 registry lookups and pushes for one message, so the chat service batches them: look up all members' gateways in one Redis pipeline, group recipients by gateway, and send one frame per gateway carrying the list of local recipients.

Members who are offline need nothing at send time; they catch up by sequence when they reconnect. Only those with notifications on get a push, and a busy group collapses many messages into one "12 new messages" notification.

Much larger rooms (Slack-style channels with 100,000 members) flip to a subscribe model: gateways subscribe to a per-channel topic only while one of their users has the channel open, and everyone else just sees an unread badge. That's the same push-vs-pull trade-off as the news feed.

Storage

  • Databases
  • Sharding
messages            -- Cassandra / ScyllaDB
  PRIMARY KEY ((conv_id, bucket), seq)      -- bucket = seq / 10,000
  sender_id, client_msg_id, body, media_ref, created_at, deleted

conversation_members  -- who is in each chat, and where each device has read to
  PRIMARY KEY (conv_id, user_id)  →  role, read_up_to, muted

user_conversations    -- the chat list on the home screen
  PRIMARY KEY (user_id, last_activity DESC, conv_id)  →  unread_count
  • Partition by conversation, cluster by seq: "messages after 4100 in this chat" is one contiguous range read. A bucket splits very long-lived chats so no partition grows without limit.
  • A wide-column store fits: huge write volume, simple key-range reads, no joins. Writes are append-only, which these stores handle well.
  • The chat list is its own table, updated on every message, so opening the app is one read rather than scanning every conversation.
  • Retention and tiering: recent months on SSD-backed nodes, older history compacted into cheaper storage; media in object storage behind a CDN with signed URLs.

Presence and receipts

  • Control traffic

Presence ("online", "last seen 5 min ago") is the noisiest signal and the least important one. Each heartbeat refreshes presence:{user} in Redis with a 60-second TTL, and "last seen" is the timestamp left behind when it expires.

Broadcasting every status change to every contact would cost far more than messages do. Instead, a client subscribes to presence only for the chats on screen right now, and the presence service pushes changes only to those subscribers. Status changes are also debounced, so flapping on a train doesn't spam anyone.

Receipts piggyback on acks. Devices ack the highest seq they have, not every message, so one "delivered up to 4183" covers a burst of messages. In groups, show "delivered" and "read" as counts, and send the per-member detail only when someone opens message info.

Typing indicators are fire-and-forget: they are never stored or retried, and are dropped first under load.

Offline and push notifications

  • Async

If the registry has no live device for a recipient, the "message stored" event on Kafka is picked up by the push notifier, which checks their notification settings and mute state and sends through APNs (iOS) or FCM (Android). The notification carries a preview, or with end-to-end encryption just "New message", and tapping it opens the app, which connects and syncs from its last seq.

Collapse notifications per conversation, respect quiet hours, and rate limit busy groups. Push providers throttle senders that spam, and users turn off apps that do.

Security and abuse

  • Governance
  • Rate limiting
  • Transport: TLS on every connection; the WebSocket is authenticated with a short-lived token at connect, and re-authenticated on expiry without dropping the socket.
  • Authorization on every send: the chat service checks membership of conv_id for each message. A client can't post into a chat by guessing its ID.
  • End-to-end encryption (Signal protocol) means the server stores and routes ciphertext it can't read. Routing, ordering and receipts all still work, because they use metadata. Server-side search and content moderation do not, so decide early.
  • Spam: rate limit sends per account and per new-conversation, require a message request before strangers can message you, and let users report and block.

Deployment and regions

  • Production

Users connect to the nearest region. Each conversation has a home region that owns its sequence counter. A message from a user connected elsewhere is forwarded to the conversation's home region to get its number, then replicated out. That costs one cross-region hop for a minority of messages, in exchange for one clear order per conversation.

Don't let two regions number the same conversation. If each region assigned sequences independently during a network split, two different messages would both be 4183 and devices would disagree for good. If the home region is unreachable, queue the message on the client ("sending…") rather than inventing a number elsewhere.

Gateways deploy by draining (see above); chat services deploy as canaries watching delivery latency and error rate. The registry and dedupe sets are in-region Redis clusters with replicas; the messages store replicates across regions.

"Clients hold a WebSocket to a gateway that only keeps connections. A stateless chat service handles each message: dedupe on the client's message ID, take the next sequence number for that conversation from its single owner, write it to Cassandra partitioned by conversation, then reply 'sent'. It looks up recipients' gateways in a Redis registry and pushes the message; devices ack the highest sequence they have, which becomes the delivered receipt. Offline users get a push notification from a Kafka consumer. Correctness never depends on the push: every reconnect syncs 'after sequence N' from the store, so a lost push is a delay, not a loss."
