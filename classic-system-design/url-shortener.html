URL Shortener

Design a service like a link shortener: users paste a long URL and get a short one such as sho.rt/aZ3k9Qx. Anyone who opens the short link is redirected to the original. Expect 100 million new links a month and a hundred times as many clicks.

Estimates

  • Back of the envelope
  • Numbers
  • Writes: 100M ÷ 30 days ÷ 86,400 s ≈ 40 per second; peaks of about 3× are about 120 per second. One database leader could take that.
  • Reads: 10B clicks a month ≈ 4,000 per second on average. Clicks are spiky (a link shared in a big newsletter), so plan for 20,000+ per second and burst beyond that at the edge.
  • Storage: 6B links × ~500 bytes (code, URL averaging ~200 bytes, owner, timestamps, flags) ≈ 3 TB, about 9 TB with three replicas. Too big to be comfortable on one node, easy for a partitioned key-value store.
  • Cache: if ~50M distinct links are clicked on a given day, caching all of them is 50M × 500 B ≈ 25 GB, which fits in a small Redis cluster.

API

GET /{code}
→ 302 Location: https://example.com/a/very/long/path?utm=…
→ 404 if unknown, 410 if expired or taken down

GET /api/links/{code}/stats?from=…&to=…   (owner only)
→ { "clicks": 18234, "by_day": […], "by_country": {…} }

301 or 302?

A 301 (permanent) is cached by browsers, which saves us traffic but means repeat clicks never reach us: no analytics, and no way to take down a phishing link for people who already opened it. A 302 (or 307) is temporary, so every click comes back. Use 302 with a short Cache-Control: max-age, so the CDN can still absorb bursts for a few seconds while we keep control.

Architecture

  • Whole system

Four pieces, each sized for its own load:

  • Link API creates links. Low volume, but it must never hand out the same code twice and must refuse dangerous URLs.
  • Redirect service turns a code into a 302. It is tiny, stateless and replicated widely; nearly all traffic is here.
  • Links table in a partitioned key-value store, keyed by code, with Redis in front for hot links and a CDN in front of that for bursts.
  • Analytics: click events go to Kafka without blocking, and a stream job aggregates them into a stats store.

Splitting create and redirect into separate services lets them scale, deploy and fail independently. A bad deploy of the dashboard should never break links printed on billboards.

Generating short codes

  • Deep dive 1
  • Keys and hashing

The core question: how do many API servers hand out codes that are short, never collide, and can't be guessed in order?

Codes use base62 (a–z, A–Z, 0–9). Seven characters give 62⁷ ≈ 3.5 trillion codes, nearly 600 times the 6 billion we need in five years.

ApproachHowProsCons
Hash the URLTake the first 7 base62 characters of a hash of the long URLSame URL gives the same code; no coordinationTruncated hashes collide, so you still need a check and a fallback; two users can't get separate links (and stats) for the same URL
CounterA global sequence, encoded in base62: 1 → b, 125 → cb …Never collides; shortest possible codesA single counter is a bottleneck and a single point of failure; codes are sequential, so anyone can enumerate every link
Counter rangesEach API server leases a block of 10,000 IDs from a coordinator (a database row or ZooKeeper), then scrambles each ID with a reversible permutation before encodingNo per-write coordination; never collidesMore moving parts; a crashed server wastes its unused block (fine)
Random + conditional writeGenerate 7 random base62 characters; insert with "only if this key doesn't exist"; on conflict, retry with a new codeStateless, unguessable, simpleA retry now and then, more often as the space fills (see the lab)

I'd pick random codes with a conditional write. Every key-value store supports "put if absent" (DynamoDB condition expressions, Cassandra lightweight transactions, INSERT … ON CONFLICT DO NOTHING in Postgres), so uniqueness is enforced by the database rather than by our own coordination. Random codes are also unguessable, which matters because a sequential scheme lets a scraper walk through every link anyone has ever made, including private documents shared by link.

Custom aliases go through the same conditional write, after checking a reserved list (api, login, admin, offensive words) and a minimum length so people can't squat the short random space.

Storage

  • Databases
links
  code         string   PRIMARY KEY      -- "aZ3k9Qx"
  long_url     string                    -- up to ~2 KB
  owner_id     string   NULL
  created_at   timestamp
  expires_at   timestamp NULL
  status       enum     -- active | expired | blocked

index: (owner_id, created_at)            -- "my links" page

Every redirect is a lookup by primary key, and there are no joins or multi-row transactions. That is exactly what a partitioned key-value store does best, so I'd use DynamoDB (or Cassandra/ScyllaDB if self-hosted), partitioned by code. Random codes spread evenly across partitions with no hot spots from creation order.

Postgres also works if the team knows it well: 9 TB means sharding by a hash of code (for example with Citus), and the "my links" query becomes a scatter-gather unless you keep a separate per-owner table. The key-value store makes that per-owner index a built-in secondary index.

Back it up: point-in-time recovery plus daily snapshots to another account. Losing the mapping breaks every link ever printed, and that can't be fixed.

The redirect path and caching

  • Deep dive 2
  • Caching

Three layers keep the hot path fast: the CDN edge, Redis, then the database. Each one absorbs most of what reaches it.

  1. CDN edge. The redirect response carries Cache-Control: public, max-age=60. A viral link is answered at the edge, so a million clicks a minute become one request per edge location per minute.
  2. Redis. Cache-aside, keyed by code, with a TTL of a day plus jitter. Unknown codes are cached as "not found" for a minute, so scrapers guessing random codes don't hammer the database.
  3. Database. Only misses arrive here, usually links that haven't been clicked today.

The redirect service itself does almost nothing: parse the code, look it up, check status and expires_at, emit a click event into an in-memory buffer, and return the 302. It runs in several regions and zones behind a load balancer; see Load balancing.

Changing or removing a link

Caching makes changes slow to take effect. When a link is blocked or expires, the API writes the new status, deletes the Redis key and sends a purge to the CDN for that path. Keep the CDN TTL short (about a minute) so even a missed purge heals quickly.

Click analytics

  • Queues and streams

The redirect must not wait for analytics. Each redirect server appends a small event (code, time, country from the edge, referrer, user agent hash) to a local buffer and a background thread sends batches to a Kafka topic. If Kafka is unreachable the buffer fills and old events are dropped: losing a few clicks is better than slowing redirects.

A stream job (Flink, or Kafka Streams) filters obvious bots, deduplicates rapid repeats from the same client, and adds counts per code per minute into a column store such as ClickHouse or BigQuery. The stats API reads those pre-aggregated rows, so a dashboard for a link with 10 million clicks is still one small query.

Clicks served by the CDN never reach the redirect service, so edge clicks come from CDN logs instead, streamed into the same topic. That's an extra pipeline, but it's the price of edge caching; mention it before the interviewer does.

Abuse and safety

  • Governance
  • Rate limiting
  • Check destinations. On create, check the URL against threat lists such as Google Safe Browsing and our own blocklist; rescan new links again after an hour and every link periodically, because pages turn malicious after they're shared.
  • Rate limit creation. A token bucket per account and per IP; anonymous users get low limits and must pass a challenge at volume.
  • Fast takedown. A reported or flagged link flips to blocked, its caches are purged, and visitors see a warning page instead of a redirect.
  • Protect the domain. If email providers or browsers flag sho.rt itself, every customer's links break. Track the domain's reputation and keep abuse response in hours, not days.
  • Private links. Codes are unguessable, but not secret. Tell users that anyone with the link can open it, and cache "not found" so scraping is cheap for us and slow for them.

Deployment and regions

  • Production

Redirects are served from at least two regions, with users routed to the nearest healthy one by DNS latency routing or anycast. The links table is replicated to every region (DynamoDB global tables or a multi-region Cassandra cluster), so a redirect never crosses an ocean.

A subtle trap: a conditional write only checks the local region's copy. If two regions both accept creates, they could each hand out the same random code within the replication delay, and last-writer-wins would silently overwrite one link. At 40 writes a second, the simple fix is to send all creates to one home region, failing over if it goes down. The alternative is to give each region its own slice of the code space (a region character in the code).

Services are stateless containers behind load balancers, autoscaled on CPU and request rate. Deploy the redirect service with canaries: send 1% of traffic to the new version, watch error rate and p99, then roll forward. Keep the redirect service's dependencies minimal so a failure elsewhere (dashboard, analytics, even the API) can't take redirects down.
