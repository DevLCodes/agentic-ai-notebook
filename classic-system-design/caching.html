Caching

Keeping a copy of hot data somewhere faster, so most reads never reach the slow system behind it.

What a cache does

A cache trades memory for speed. A read from Redis takes well under a millisecond; the same read from a database that has to touch disk or run a join can take 5 to 50 ms.

Caching works because real traffic is skewed: a small share of keys (today's popular posts, the logged-in user's profile, the home page) gets most of the reads. Cache those and the database only sees the long tail.

Caching is a good fit when data is read much more than written, when it is expensive to compute, and when a slightly stale answer is acceptable. It is a bad fit for data that must always be exact, like an account balance at the moment of a payment.

Read and write patterns

PatternHow it worksProsCons
Cache-asideApp reads cache; on a miss reads the DB and fills the cache. Writes go to the DB and delete the cache key.Simple; cache only holds what is read; cache outage only slows things downFirst read is slow; small window for stale data
Read-throughThe cache library loads from the DB on a missLess app codeSame staleness as cache-aside
Write-throughEvery write goes to the cache and the DB togetherCache is always freshSlower writes; caches data nobody reads
Write-back (write-behind)Write to the cache; flush to the DB later in batchesVery fast writes; absorbs burstsData loss if the cache dies before flushing

On a write, delete the cache key rather than updating it. Two concurrent writers that each update the cache can leave the older value in place; deleting forces the next reader to load the current value.

Try it: hit ratio and cache size

A catalogue of 100,000 items gets 200,000 reads. Popularity follows a power law, as in real traffic. Change how big the cache is, how skewed traffic is, and the eviction policy.

Eviction

Assumes 0.5 ms for a cache hit and 15 ms for a database read. Sizes map to a 0.5% to 12% scale; the first step is 0.5%.

Eviction and expiry

PolicyEvictsUse when
LRULeast recently used keyThe default; recent use predicts future use
LFULeast frequently used keyStable popularity; resists a one-off scan flushing the cache
TTLAnything older than its time to liveAlways set one, so stale data heals itself even if an invalidation is missed

Redis approximates LRU and LFU by sampling a few keys rather than keeping an exact order, which is cheap and close enough. Add a little random jitter to TTLs so keys written together do not all expire together.

How caches fail

Stale data

The hardest part of caching is invalidation. Delete on write, set a TTL as a safety net, and for data that must be fresh, either skip the cache or listen to the database change stream (change data capture) to invalidate keys.

Cache stampede

A hot key expires and thousands of requests miss at once, all hitting the database for the same value. Fixes: let only one request rebuild the key (a short lock or request coalescing) while others wait or get the stale value, or refresh popular keys a little before they expire.

Hot keys

One key, like a celebrity's profile, can get more traffic than one cache node can serve. Keep a small in-process copy on each app server for a few seconds, or replicate the key under several names (key#1 to key#8) and read one at random.

Cold start and cache loss

If the cache tier restarts empty, the full read load lands on the database at once. Size the database to survive a cold cache at reduced traffic, warm the cache before shifting traffic, and replicate the cache so one node failing is not a full flush.

Penetration

Requests for keys that do not exist always miss. Cache the "not found" result with a short TTL, or check a Bloom filter first.

Saying it in an interview

"Reads outnumber writes about 100 to 1, so I'd put a Redis cluster in front of the database with cache-aside: read from Redis, on a miss read the database and set the key with a TTL of a few minutes plus jitter. Writes go to the database and delete the key. How much a cache helps depends on how skewed the traffic is, so I'd size it from the real key distribution: with typical skew, caching the hottest 5 to 10% of items takes half or more of the reads off the database, and far more for very skewed traffic. For hot keys I'd add a short in-process cache, and I'd use request coalescing so one expiry doesn't stampede the database."
