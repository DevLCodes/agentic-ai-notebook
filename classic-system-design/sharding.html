What sharding is

Replication copies the same data to more machines. Sharding (partitioning) splits the data so each machine holds only part of it. You shard when writes or total data outgrow what one machine can handle.

Sharding is a big step. Cross-shard joins and transactions become hard, and operations get heavier. Before sharding, try: a bigger machine, read replicas, a cache, archiving old data, and splitting unrelated tables into separate databases. A single well-tuned Postgres node handles more than most people expect.

Choosing the shard key

The shard key is the most important decision, and the hardest to change later. A good key:

  • Has many distinct values spread evenly, so no shard gets too much.
  • Matches the main access pattern, so most queries hit one shard. For a chat app, shard messages by conversation_id; for a SaaS app, by tenant_id.
  • Keeps things that change together on one shard, so transactions stay local.

Bad keys: a timestamp (all writes go to the newest shard), country (one country dominates), or a boolean.

Consistent hashing

The obvious way to hash is shard = hash(key) % N. The problem appears when N changes: going from 4 to 5 shards changes the answer for about 80% of keys, so almost all data has to move, or almost every cache entry misses at once.

Hot partitions and resharding

Hot partitions

Even with a good hash, one key can be hot: a celebrity's timeline, a viral post, a huge tenant. Options: split that key with a suffix (post:123#0 to post:123#9) and merge on read; give big tenants their own shard via a directory; or put a cache in front.

Resharding

Plan for growth from day one. Common approaches:

  • Many logical shards, few machines. Create 1,024 logical shards at the start and place many on each machine. Growing means moving whole logical shards to new machines, never re-splitting keys.
  • Automatic splitting. Distributed SQL and stores like DynamoDB, Bigtable and Spanner split busy or large ranges automatically.
  • Online migration. Double-write to old and new locations, backfill, verify, then switch reads, the same playbook as any big data migration.

Queries across shards

A query without the shard key must "scatter-gather" to every shard and merge results, which gets slower as shards are added. Keep a secondary index keyed the other way (for example, a table from email to user_id) or a separate search system for those queries.

Saying it in an interview

"At 50,000 writes a second and 40 TB, one Postgres leader won't fit, so I'd shard by user_id, because almost every query is scoped to one user and that keeps their data and transactions on one shard. I'd hash the key over 1,024 logical shards mapped onto 16 physical clusters, each a leader plus two replicas, so growth means moving logical shards, not rehashing. Lookups by email go through a small email-to-user table. For celebrity accounts I'd watch for hot shards and cache aggressively."
