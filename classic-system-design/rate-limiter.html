Distributed Rate Limiter

Design the rate limiter for a public API platform. Every request is checked against limits per API key, per user and per IP, with different limits per pricing plan (for example 100 requests a minute on Free and 5,000 on Pro, plus a daily quota). The API serves a million requests a second from hundreds of servers in several regions.

Requirements

  • Clarify
  • Rate limiting block

The algorithms are covered in the rate limiting building block. This design is about running them for real: shared state across hundreds of servers, a tiny latency budget, and deciding what happens when the limiter itself breaks.

Out of scope for v1: DDoS protection at the network edge (that belongs to the CDN or a scrubbing service), and cost-based limits that weigh calls by how expensive they are. Say so explicitly, so the interviewer knows you chose rather than forgot.

Estimates

  • Back of the envelope
  • Numbers
  • Checks: 1M requests a second × ~2.5 limits each (key, user or IP, sometimes endpoint) = 2.5M counter operations a second if every check goes to shared storage.
  • State: 10M active identities with ~2.5 buckets each, at ~100 bytes per bucket (tokens, last refill time, key name, overhead), is ~3 GB. It fits in memory several times over.
  • Redis: a shard comfortably runs ~100k small Lua scripts a second, so 2.5M a second needs ~25 primary shards, plus replicas. That works, but each check is a network round trip (~0.3–1 ms in-zone), which is why the scale section cuts most of them out.
  • Decisions log: logging every decision at 1M/s × 100 B is 100 MB/s. Log every rejection and a sample of allows, and keep exact quota counts separately.

API

  • Interface

The limiter is a library inside the API gateway (or a sidecar next to it), not a separate network hop. Its interface is one call per request:

decision = limiter.check(
    keys   = ["key:ak_29f1", "user:u_812", "ip:203.0.113.7"],
    route  = "POST /v1/search",
    cost   = 1)                      // expensive endpoints can cost more
→ { allowed: false, rule: "pro.per_minute", limit: 5000,
    remaining: 0, reset_after_ms: 12400 }

What clients see when they're limited:

HTTP/1.1 429 Too Many Requests
Retry-After: 13
RateLimit-Limit: 5000
RateLimit-Remaining: 0
RateLimit-Reset: 13
{ "error": "rate_limited", "message": "Pro plan allows 5,000 requests per minute." }

Send the RateLimit-* headers on every response, not only on 429s, so clients can slow down before they hit the wall. Admin APIs manage plans, per-customer overrides and emergency blocks.

Architecture

  • Whole system
  • Limiter library in every gateway. No extra service hop: the check is a function call plus, sometimes, one Redis round trip. Rejected requests never reach the backend.
  • Redis cluster holds the shared counters, sharded by key. Each check is one atomic Lua script, so concurrent gateways can't double-spend a token.
  • Config service keeps plans, overrides and blocks in a database and pushes changes to every gateway (a watch on etcd or a pub/sub channel), which keeps the full rule set in memory.
  • Kafka receives rejections and sampled allows for dashboards, abuse detection and customer-facing usage pages; daily quota totals feed billing.

Atomic counters in Redis

  • Deep dive 1
  • Algorithms

Many gateways check the same key at the same moment. The read-modify-write has to be atomic, or two gateways both see one token left and both spend it.

Use a token bucket for rates (it allows short bursts up to the bucket size, then a steady refill) and a plain counter with a TTL for daily quotas. The bucket is two fields per key, and a Lua script runs atomically inside Redis:

-- KEYS[1] = "rl:{ak_29f1}:pro.per_minute"
-- ARGV: capacity, refill_per_ms, now_ms, cost
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or capacity
local ts     = tonumber(b[2]) or now_ms
tokens = math.min(capacity, tokens + (now_ms - ts) * refill_per_ms)
local allowed = tokens >= cost
if allowed then tokens = tokens - cost end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now_ms)
redis.call('PEXPIRE', KEYS[1], ttl_ms)          -- idle keys disappear
return { allowed and 1 or 0, tokens }
  • Why a script: GET then SET from the gateway leaves a race between them. INCR alone is atomic but can't express refill. The script runs as one step on the shard that owns the key.
  • Whose clock? Gateways' clocks drift. Use Redis server time (TIME inside the script) or keep gateway clocks NTP-synced and tolerate a few ms of skew.
  • Several limits per request: wrap them in a hash tag (rl:{ak_29f1}:…) so all of one key's buckets live on one shard and one script checks them together, refusing all if any refuses. That way a rejected request doesn't consume from the others.
  • GCRA (generic cell rate algorithm) is an equivalent that stores a single timestamp instead of two fields, used by several production limiters. Same behaviour, smaller state.

A million checks a second

  • Deep dive 2
  • Caching

Calling Redis on every request works, but it adds a round trip to every request and needs a big cluster. Most requests are nowhere near their limit, so most of that work is wasted.

  1. Local leases. A gateway takes a small batch of tokens from Redis in one script call (say 10% of the bucket, or 20 tokens) and spends them locally from memory. It only goes back to Redis when the batch runs out. A customer spread across 300 gateways costs a Redis call per batch, not per request.
  2. The accuracy cost: tokens leased to a gateway that then sees no traffic are stranded, and in the worst case every gateway holds a full lease at once. Overshoot is bounded by gateways × lease size, so size leases from the limit: big limits get big leases, small limits (10 a minute) go straight to Redis every time.
  3. Local deny cache. Once a key is refused, remember that locally until its reset time. An abusive client hammering at 50,000 requests a second gets 429s from memory and never touches Redis.
  4. Batch and pipeline. Lease refills from one gateway to one shard go in a pipeline, a few ms at a time.
  5. Hot keys. One giant customer can make one shard hot. Split its bucket into N sub-buckets on different shards (rl:{ak_29f1#3}) with 1/N of the rate each, chosen at random per lease.

Try it: local leases vs accuracy

  • Lab

One customer has a limit and sends traffic through many gateways. Choose how many tokens a gateway leases at a time. Bigger leases mean fewer Redis calls, but more tokens can sit stranded or be overspent.

Illustrative model: the customer sends exactly at their limit, spread evenly across gateways; one Redis round trip ~0.5 ms. Worst-case overshoot assumes every gateway holds a full unused lease at the moment the shared bucket empties.

Rules and plans

  • Configuration
plans:
  free:       { per_minute: 100,  burst: 20,  per_day: 10_000 }
  pro:        { per_minute: 5000, burst: 500, per_day: 2_000_000 }
routes:
  "POST /v1/search":   { cost: 5 }                 # expensive endpoint
overrides:
  ak_29f1:             { per_minute: 20000 }        # enterprise contract
blocks:
  ip:198.51.100.0/24:  { until: "2026-11-04T00:00Z", reason: "abuse" }

Rules live in a database with an admin UI and an audit log. The config service versions the whole rule set and pushes it to gateways; each gateway swaps it in atomically and reports the version it's running, so you can see a rollout finish. A plan upgrade simply changes which rule a key maps to, and the bucket's capacity changes on its next check.

Keep a static fallback rule set baked into the gateway image, so a gateway that starts while the config service is down still enforces sane defaults.

When the limiter fails

  • Failure modes

The limiter exists to protect the backend. It must never become the reason the API is down.

FailureBehaviour
Redis slow (> 5 ms) or a shard downA circuit breaker trips and the gateway switches to local-only limits: each gateway enforces limit ÷ number of gateways from memory. Approximate, but abusive traffic is still capped.
Config service downGateways keep their last rule set; new gateways use the baked-in defaults.
Kafka downDecisions are buffered then dropped; enforcement is unaffected. Quota counts come from Redis, so billing isn't lost.
Whole limiter disabled by mistakeBackends keep their own coarse protection: concurrency limits and load shedding.

Fail open or closed? For a public API, fail open (with local limits): a few minutes of over-serving is better than rejecting every customer. For limits that guard money or security, such as login attempts, password resets or SMS sends, fail closed. Decide per rule, and write it down.

Multiple regions

  • Production
  • Consistency

A global Redis that every region calls would add 70–150 ms to every request. Instead each region keeps its own counters, and you choose how to split a customer's global limit:

  • Static split: each region gets a share of the limit (for example by its share of that customer's traffic last week). Simple, but a customer whose traffic moves between regions gets limited early.
  • Async sync: regions enforce locally and gossip their usage every second or so, adjusting their local budget. Overshoot is bounded by about one sync interval of traffic.
  • Daily quotas don't need real-time accuracy: count per region, sum asynchronously, and block once the total crosses the quota (a minute late is fine).

Risks and v2

  • Wrap-up
RiskHow you detect itMitigation
Limiter adds latency to every requestOverhead p99In-process library, leases, local deny cache
Redis outage makes the API failError rate during shard failoverCircuit breaker, local-only fallback, fail open by default
Overshoot from big leasesCompare allowed totals with limitsLease size scaled to the limit; direct checks for small limits
One customer melts one shardPer-shard CPU, hot keysSplit buckets, local deny cache
Bad rule blocks everyone429 spike right after a config pushStaged rule rollouts, dry-run mode that logs without enforcing, instant rollback

v2 ideas: cost-based limits (weigh calls by CPU or tokens used), adaptive limits that tighten automatically when backends are under strain, per-tenant concurrency limits, and self-serve limit increases.

"The limiter is a library in every API gateway, so there's no extra hop. Rules per plan are pushed from a config service and held in memory. Shared state is token buckets in a Redis cluster, updated by one atomic Lua script per check, with a hash tag so all of a key's limits are checked together. To avoid a round trip per request, gateways lease small batches of tokens and spend them locally; overshoot is bounded by gateways times lease size, so leases scale with the limit. Refusals are cached locally until reset. If Redis is slow, a circuit breaker drops to local-only limits: we fail open for the public API and closed for login and SMS limits. Regions keep their own counters and sync usage asynchronously."
