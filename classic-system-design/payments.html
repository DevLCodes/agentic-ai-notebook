Payments

Design the payment system for a large online marketplace. Buyers pay by card at checkout through an external payment processor, sellers are paid out later, refunds must work, and finance must be able to prove where every cent went. Expect 10 million payments a day, with ten times the usual traffic during big sales.

Requirements

  • Clarify

Payments is a low-traffic, high-stakes system. The interview is about correctness: never charging twice, never losing a charge, and proving it afterwards, while relying on an external processor that is slow and sometimes silent.

Estimates

  • Back of the envelope
  • Numbers
  • Payments: 10M ÷ 86,400 ≈ 115 a second; a sale peak of 10× is ~1,200 a second. One well-tuned Postgres primary can do this; the challenge is correctness, not scale.
  • Processor calls: each takes 1–3 s, sometimes far longer. At 1,200 a second with 3 s each, that's ~3,600 calls in flight, so the calls must be asynchronous or on a large connection pool.
  • Ledger: ~4 rows per payment (authorise, capture, fees, seller balance) ≈ 40M rows a day at ~200 bytes ≈ 8 GB a day, ~15 TB over five years. Financial records are kept 7–10 years, so plan partitioning and archiving.
  • Edge cases: timeouts, duplicate webhooks, partial refunds and currency rounding each happen thousands of times a day at this volume.

Architecture

  • Whole system
  • Payment service owns each payment's state machine and its idempotency keys, in a relational database with transactions (Postgres).
  • PSP adapter wraps each processor behind one interface, with timeouts, retries and circuit breakers, so a second processor can be added for failover or lower fees.
  • Ledger is an append-only, double-entry record of every money movement. Balances are derived from it, never stored separately as editable numbers.
  • Kafka carries payment events to the order service (confirm the order), the payout service (seller balances) and analytics, using an outbox so events are never lost or invented.
  • Reconciliation compares our records with the processor's daily settlement files and flags every difference.

Idempotency and the unknown state

  • Deep dive 1
  • Exactly-once

The most dangerous moment in payments: you asked the processor to charge a card, and the connection timed out. Did it charge or not?

A timeout doesn't mean failure. The request may have succeeded with only the response lost. Retrying blindly can charge twice, and giving up can leave a charge with no order. Three tools handle it:

  1. Idempotency keys end to end. The client sends an Idempotency-Key per checkout attempt. The payment service stores it with a unique constraint in the same transaction that creates the payment row. A repeat with the same key returns the stored result instead of acting again; a repeat while the first is still running gets 409 in progress. The service passes its own key (the payment_id) to the processor, which supports idempotency keys too, so a retry to the processor is safe.
  2. Record intent before acting. The row is written as PENDING before calling the processor. If the service crashes mid-call, a recovery job finds payments stuck in PENDING and asks the processor what happened.
  3. Treat "unknown" as a state. After a timeout, mark the payment UNKNOWN, tell the buyer "we're confirming your payment", and resolve it by retrying with the same key, querying the processor's API, or waiting for the webhook. Never guess.
BEGIN;
  INSERT INTO idempotency_keys (key, request_hash, status) VALUES ($1, $2, 'started');
  -- unique violation → another request owns this key: return its stored response
  INSERT INTO payments (id, order_id, amount, currency, status) VALUES (…, 'PENDING');
COMMIT;
-- call the processor with idempotency key = payment id (outside the transaction)
-- then, in a second transaction: update status, write ledger rows, store the response

Don't hold a database transaction open across the network call. A 3-second processor call inside a transaction holds row locks and connections; at 1,200 a second the pool runs out. Write intent, commit, call, then record the outcome in a new transaction.

The payment state machine

  • Correctness

Transitions are explicit and guarded: UPDATE payments SET status='CAPTURED' WHERE id=$1 AND status='AUTHORIZED'. If zero rows change, someone else moved it first, so read and decide again; never overwrite. Each transition and its ledger entries commit in one transaction, and every change is kept in a payment_events history table for audits and debugging.

Webhooks and API responses can arrive in any order and more than once. Handlers check the current state and ignore transitions that are already done or no longer valid (a late "authorised" webhook for a payment already captured).

The double-entry ledger

  • Money
  • Databases

Every movement of money is recorded as entries that sum to zero: money leaves one account and arrives in another. If the books don't balance, there's a bug, and you'll know.

-- invariant, checked on every insert batch and nightly:
--   SUM(debits) = SUM(credits) for every txn_id and every currency
  • Append-only: mistakes are fixed with new reversing entries, never edits, so the history is a complete audit trail.
  • Balances are derived: a seller's balance is the sum of their account's entries. For speed, keep a running balance table updated in the same transaction, and check it against the sum nightly.
  • One currency per entry: FX conversions are explicit transactions through an FX account at a recorded rate, so rounding differences have somewhere to go.
  • 40M rows a day is fine for a partitioned Postgres (by month) or a purpose-built ledger database; archive closed periods to cheaper storage.

Checkout as a saga

  • Distributed transactions
  • Consistency

Checkout spans services that can't share one database transaction: reserve stock, authorise payment, confirm order. Use a saga: a sequence of local steps, each with a compensating action if a later step fails.

  1. Order service creates the order PENDING_PAYMENT and reserves stock (compensation: release the reservation).
  2. Payment service authorises the card (compensation: void the authorisation).
  3. Order service confirms the order when it sees payment.authorized; capture happens later, at shipping.

Events between services go through a transactional outbox: the payment service writes the event into an outbox table in the same transaction as the state change, and a relay publishes it to Kafka. Consumers dedupe by event ID. The order service therefore never misses a successful payment, and never sees one that was rolled back.

A reservation that expires (the buyer abandoned 3-D Secure) triggers the compensation path: void any authorisation and release the stock.

Reconciliation

  • Proof

Your records, the processor's records and the bank's records must agree. Reconciliation finds out, every day, where they don't.

  • Inputs: the processor's settlement report (every captured, refunded and charged-back transaction with fees) and bank statements for payouts.
  • Matching: join on the processor's transaction ID, then compare amount, currency and status. Typical results: matched; in the processor's file but not ours (a charge we never recorded, usually an unresolved UNKNOWN); in ours but not theirs (we think we captured, they don't); amount mismatch (fees, FX, partial captures).
  • Resolution: known patterns are fixed automatically with correcting ledger entries (and refunding orphan charges); the rest go to a finance operations queue with an age SLA.
  • Run it daily for settlements, and continuously for the critical cases: any payment in PENDING or UNKNOWN for more than a few minutes is queried against the processor straight away.

Refunds and payouts

  • Money out
  • Refunds are their own records with their own idempotency keys, linked to the payment. The sum of refunds can never exceed the captured amount, enforced in the same guarded update. Ledger entries reverse the seller payable and the fee as the policy says.
  • Payouts run as a weekly batch: for each seller, sum their payable balance, hold back a reserve for expected refunds and chargebacks, and send a bank transfer through a payout provider. Each payout has an idempotency key per seller per period, so a rerun of the batch can't pay twice.
  • Chargebacks arrive by webhook days or weeks later; they debit the seller's balance (or the marketplace's), and open a dispute case with evidence from the order.

Security, PCI and fraud

  • Governance
  • Rate limiting
  • Never touch card numbers. The processor's hosted fields or SDK collect the card in the browser and return a token; our servers only ever see the token. That keeps most of our systems out of PCI DSS scope.
  • Verify webhooks: check the processor's signature and timestamp, and fetch the object from the processor's API before acting on anything surprising.
  • Fraud checks before authorising: velocity rules (cards and accounts per device, attempts per minute), a risk model score, and 3-D Secure for risky or regulated transactions. Card-testing attacks (thousands of small attempts) are stopped by rate limits per account, IP and card fingerprint.
  • Access: refunds and manual ledger corrections need two-person approval and are audited; secrets live in a vault; encrypt data at rest and in transit.

Deployment and regions

  • Production

Run active-passive across regions for the payments database: a single primary with synchronous replication to a standby in another zone and asynchronous replication to another region. A ledger split across two active writers is hard to keep balanced, and 1,200 payments a second fits on one primary.

Two processors are a feature, not a luxury. When your processor has an outage during a sale, a second one keeps checkout working. The adapter routes by health, cost and card type, and each payment records which processor handled it, so refunds go back the same way.

Deploy payment-service changes behind feature flags with canaries, watching authorisation rate by processor and card brand. A silent drop in approvals costs as much as an outage.

"Throughput is small, so this is about correctness. Every create carries an idempotency key, stored with a unique constraint in the same transaction as a PENDING payment row; we then call the processor with our payment ID as its idempotency key, outside the transaction. A timeout becomes UNKNOWN and is resolved by retrying with the same key, querying, or the webhook, never by guessing. Each state change is a guarded update that writes balanced double-entry rows to an append-only ledger and an outbox event in the same transaction. Checkout is a saga with compensations. A daily reconciliation matches our ledger with the processor's settlement file, and anything that doesn't match is fixed or escalated."
