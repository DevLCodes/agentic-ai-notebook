Kinds of database

Start with a relational database unless you have a specific reason not to. Most "why not Postgres?" answers in an interview should name an access pattern or a scale number.

FamilyData modelStrong atExamples
Relational (SQL)Tables, rows, joins, schemasTransactions, flexible queries, constraints; the safe defaultPostgreSQL, MySQL, Aurora, Cloud SQL
Distributed SQLSame SQL, partitioned across nodesSQL and transactions beyond one machine, multi-regionSpanner, CockroachDB, YugabyteDB, TiDB
Key-valueA key maps to a valueVery high throughput lookups by key, predictable latencyDynamoDB, Redis, etcd
DocumentJSON-like documentsNested objects read and written together, evolving schemasMongoDB, Firestore, Couchbase
Wide-columnRows keyed by partition, sorted by a clustering keyHuge write volumes, time-ordered data per key (messages, events)Cassandra, ScyllaDB, Bigtable, HBase
SearchInverted index over textFull-text search, filters, facets, relevance rankingElasticsearch, OpenSearch
Time seriesTimestamped pointsMetrics, downsampling, range queries over timePrometheus, InfluxDB, TimescaleDB
GraphNodes and edgesMany-hop relationship queriesNeo4j, Amazon Neptune
Object storageFiles (blobs) by keyImages, video, backups, data lake files; cheap and nearly unlimitedAmazon S3, Google Cloud Storage, Azure Blob

Real systems combine them: Postgres as the source of truth, Redis as a cache, S3 for media, and Elasticsearch fed from Postgres for search. Each extra store is another thing to keep in sync, so add them only when an access pattern demands it.

Indexes

Without an index, finding rows means reading the whole table. An index is a separate sorted structure that points to rows, so the database can jump straight to the ones it needs.

StructureHow writes workReadsUsed by
B-treeUpdate pages in placeFast point and range readsPostgreSQL, MySQL InnoDB, most relational databases
LSM treeAppend to memory, flush sorted files, merge them in the background (compaction)May check several files; Bloom filters skip mostCassandra, RocksDB, ScyllaDB, Bigtable

Indexes are not free. Every index is updated on every write and takes disk and memory. Index the columns your frequent queries filter and sort by, and use a composite index (for example (user_id, created_at)) when a query filters on one column and sorts by another.

Try it: with and without an index

A query looks up one user's orders: SELECT * FROM orders WHERE user_id = ?. Change the table size and see what an index changes.

Rough model: a full scan reads about 1 million rows per second per core from cache-warm storage; a B-tree with 300 keys per page; each user has about 20 orders; each index adds roughly 15% to insert cost. Real numbers vary widely, but the shape does not.

Transactions

A transaction groups several writes so they all happen or none do. Relational databases give you ACID: atomic (all or nothing), consistent (constraints hold), isolated (concurrent transactions do not see each other's half-done work) and durable (committed means on disk).

Use them whenever two writes must agree, such as moving money between accounts or decrementing stock while creating an order. Isolation levels trade safety for speed: read committed is the usual default, while serializable prevents every anomaly at the cost of more aborted transactions. Many NoSQL stores only offer atomic writes to a single item or partition, which pushes that logic into your application.

Replication

Replication keeps copies of the data on several machines for durability (a disk dies, the data survives), availability (a follower is promoted if the leader fails) and read scale (spread reads over followers).

ModeCommit waits forTrade-off
SynchronousAt least one follower to confirmNo data loss on failover; slower writes; a slow follower slows the leader
AsynchronousOnly the leaderFast writes; a failover can lose the last few changes
Semi-synchronousOne of several followersThe common middle ground

Replication lag

Followers are usually milliseconds behind, but under load it can be seconds. A user who updates their profile and immediately reloads might read an old copy from a follower. Fixes, in order of simplicity: read your own recent writes from the leader for a few seconds; route all of one user's reads to the same follower; or wait until the follower has caught up to the write's position in the log.

Other topologies

Multi-leader lets each region accept writes, but two regions can change the same row at once and you must resolve the conflict. Leaderless stores such as Cassandra and DynamoDB write to several replicas and read from several, using quorums; see Consistency.

Saying it in an interview

"Users, orders and payments are relational and need transactions, so they live in Postgres. I'd index the queries we actually run, like (user_id, created_at) for 'my recent orders'. The leader replicates semi-synchronously to a follower in another zone for failover, and async read replicas handle reads, except a user's own reads right after a write, which go to the leader. Images go to S3. If writes outgrow one leader, I'd shard by user ID."
