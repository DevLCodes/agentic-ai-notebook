Rate limiting

Capping how many requests a client can make in a period, so one noisy user or a bug can't take the service down for everyone.

Why limit

Without limits, the heaviest client decides how the service performs for everyone else.

  • Protect capacity. A retry loop in one customer's script can send 10,000 requests a second.
  • Fairness. Each user or API key gets its share, often tied to a pricing plan.
  • Abuse and cost. Slow down password guessing, scraping and sign-up spam; cap spend on expensive calls such as SMS or LLM requests.

When a client is over its limit, return 429 Too Many Requests with a Retry-After header, and ideally headers that show the limit and how much remains, so well-behaved clients can slow down on their own.

Where to enforce

Limiting across many servers

With 50 gateway instances, a limit kept in each instance's memory lets a client get 50 times the limit. Keep counters in a shared store: Redis is the standard choice, with the check-and-increment done atomically in one Lua script or a single INCR plus EXPIRE per window.

That adds a network hop to every request. At very high volume, servers keep local counts and sync with Redis every few hundred milliseconds, accepting a small overshoot in exchange for speed.

If the limiter fails

Decide up front: fail open (allow traffic if Redis is down; usual for general API limits) or fail closed (reject; right for login attempts and expensive operations).

Rate limits are not load shedding

A per-client limit doesn't help if the total of all well-behaved clients exceeds capacity. Pair limits with load shedding: when the service itself is overloaded, reject low-priority traffic first, regardless of whose it is.

Saying it in an interview

"I'd enforce per-API-key limits at the gateway with a token bucket: a refill rate from the customer's plan and a capacity that allows short bursts. State lives in Redis, keyed by API key, updated atomically with a Lua script, so all gateway instances share one count. Over-limit requests get a 429 with Retry-After. Coarse per-IP limits at the CDN stop floods earlier. If Redis is unreachable we fail open for normal endpoints and closed for login."
