1.1 Agentic loops

Your code runs the loop: send → check stop_reason → run the tools → append the results → send again. stop_reason is the only reliable signal that the model has finished.

Four ways to get "done" wrong
  • parsing text ("I've finished the first file…" doesn't mean it's done)
  • content[0] is text (text often comes before a tool_use)
  • for _ in range(5) (acceptable as a safety net, not as the main stop)
  • tool_choice: "any" (never reaches end_turn, so it loops forever)

1.2 Multi-agent orchestration

The exam tests one shape: hub-and-spoke. All communication goes through the coordinator. Subagents never talk to each other. That gives you observability, consistent error handling, and control over what context each subagent receives.

The coordinator's 4 jobs
  1. Pick subagents dynamically (not every query needs the full pipeline)
  2. Partition scope so subagents don't duplicate each other
  3. Refine in a loop: find gaps → re-delegate → repeat
  4. Route all communication through itself
Isolation: a subagent does not inherit the coordinator's system prompt, history, or other subagents' results. It only knows what is written into its prompt.

1.5 Agent SDK hooks

  
PreToolUse enforces policy before a tool runs. PostToolUse transforms data after it runs.
    PostToolUse can't undo a side effect, because by then the tool has already run.

1.6 Task decomposition

  

    

      🛤 Fixed pipeline (prompt chaining)

      Steps planned in advance, each feeding the next. Consistent and easy to debug, but it
        can't adapt to surprises.
e.g. multi-file code review, document processing, compliance checks
    

    

      🧭 Dynamic decomposition

      Subtasks are created from what gets discovered. It adapts, but runtime is less
        predictable and it's harder to debug.
e.g. security audits, debugging an unfamiliar legacy system
    

  


  
✎ Try it: review 14 files

  
Attention dilution: do 14 files in one pass and the early files get deep feedback, the later ones get
    shallow feedback, and the same pattern gets flagged in one file (≠) but approved in another.

1.7 Session state & resumption

  
Resume to continue. Fork to explore alternatives. Start fresh with a summary when the old tool results are stale.

  
  

    

      The contradictory-advice bug

      An agent analyses 50 files and finds 3 auth issues. You fix them overnight, then --resume the next day.
      The agent recommends fixing the issues you already fixed, because the old tool results showing the unfixed
      code are still in its history. Re-reading the files doesn't fully cure this.
    

    

      Targeted re-analysis

      Start a fresh session and inject: "Prior findings X, Y, Z. Modified: auth.ts, session.ts, middleware.ts."
      The agent re-reads only those 3 files, not all 50. Forking won't help, because a fork inherits the stale results.
    

  

  
CLI: name a session with -n/--name, resume with --resume <name>, or use -c/--continue for the most recent one. fork_session is used together with resume.
