LLM Observability

Evals tell you an agent worked on your test set. Observability tells you what it is doing right now, for real users, and what that costs. Three jobs: tracing & logging, cost/latency monitoring, and production monitoring. Four common tools do them.

0 · Why LLM apps need their own kind of monitoring

classic web serviceLLM app / agent
a failure looks likea 500, an exception, a timeouta 200 OK with a wrong answer: made-up facts, the wrong tool, an off-topic reply
same input twicesame outputcan give different outputs, and can take a different number of steps
cost per requestroughly fixedvaries 100× with tokens, number of loop steps and model
latencymilliseconds, mostly your codeseconds, mostly the model and tools, and it grows with output length
what you must logstatus, duration, stack tracethe prompt, output, tool calls, tokens, model and prompt version — the whole story
The three questions
  1. What happened? → tracing & logging
  2. What did it cost, and how long did it take? → cost/latency monitoring
  3. Is it still working well, for everyone? → production monitoring
Where it fits
  • Offline evals (previous page): fixed test set, before you ship.
  • Observability (this page): real traffic, after you ship.
  • The two feed each other: bad production traces become new eval cases.

1 · Tracing & logging

A trace is one request, end to end. It is a tree of spans: timed steps, each with a parent. In an agent, the root span is the agent run, and the children are model calls and tool calls. A trace is the agentic loop, written down.

span kindrecordsOpenTelemetry GenAI name / attributes
🤖 agent runuser input, final answer, session and user id, total stepsinvoke_agent · gen_ai.agent.name
💬 model callmodel, messages in, output, stop reason, input/output tokens, latency chat {model} · gen_ai.request.model, gen_ai.usage.input_tokens, gen_ai.usage.output_tokens
🔧 tool calltool name, arguments, result or error, latencyexecute_tool {name} · gen_ai.tool.name
📚 retrievalquery, top-k document ids and scoresoften a custom span, e.g. retrieve

The OpenTelemetry GenAI semantic conventions are still evolving, but most tools can read them. Emitting OTel keeps you free to switch tools.

# the same trace, created by hand with OpenTelemetry (any tool below can ingest it)
from opentelemetry import trace
tracer = trace.get_tracer("support-agent")

with tracer.start_as_current_span("invoke_agent support") as run:
    run.set_attribute("session.id", session_id)
    with tracer.start_as_current_span("chat claude-sonnet") as span:
        resp = client.messages.create(model=MODEL, messages=msgs, tools=TOOLS, max_tokens=1024)
        span.set_attribute("gen_ai.usage.input_tokens", resp.usage.input_tokens)
        span.set_attribute("gen_ai.usage.output_tokens", resp.usage.output_tokens)
    with tracer.start_as_current_span("execute_tool issue_refund"):
        result = issue_refund(**args)
# in practice: one decorator or an auto-instrumentation package does all of this (see section 4)
What to log on every model call
  • model id, prompt version, temperature, max tokens
  • full input messages and output (or a pointer to them)
  • input, output and cached tokens; latency; stop reason
  • tool calls: name, arguments, result, error
  • session id and user id, so you can find "that one bad chat"
  • user feedback (👍/👎), attached to the trace later
Logging gotchas
  • Prompts contain PII. Redact or mask before export, set a retention period, and restrict who can read traces.
  • Log the prompt version, not just the text, or you can't tell which change caused a regression.
  • High traffic? Sample the full payloads (e.g. 10%), but keep token and latency metrics for 100%.
  • Never let a logging failure break the request: export asynchronously.

2 · Cost & latency monitoring

Cost is just token arithmetic:

cost = input_tokens  × input_price
     + output_tokens × output_price
     + cached_tokens × cache_read_price   # often ~10% of input

Output tokens usually cost several times more than input. An agent pays for its whole history again on every step, so step count is the hidden multiplier.

Latency has three numbers:

  • TTFT (time to first token): what the user feels with streaming
  • output tokens / second: how fast the answer then appears
  • end-to-end: all model and tool steps. This is what an agent's user waits for.

Track p50, p95 and p99, not the average.

Levers to cut cost
  • Prompt caching for the long, stable prefix (system prompt, tools, docs)
  • Model routing: a small model for easy requests, a large one only when needed
  • Trim context: summarise old turns, drop stale tool results
  • Cap max_tokens and the number of agent steps
  • Batch anything that isn't interactive
Levers to cut latency
  • Stream the answer: TTFT drops, total time doesn't
  • Run independent tool calls in parallel
  • Fewer steps: a better tool design beats a faster model
  • Smaller model, shorter output, cached prefix
  • Set timeouts on every tool, and alert on the p95

4 · Observability tools

All four do tracing, cost tracking and some evals. The real differences are how you plug them in and where your data lives.

# LangSmith                                   # export LANGSMITH_TRACING=true  LANGSMITH_API_KEY=…
from langsmith import traceable
@traceable
def answer(q): ...

# Langfuse                                    # LANGFUSE_PUBLIC_KEY / SECRET_KEY / HOST
from langfuse import observe
@observe()
def answer(q): ...

# Helicone: no decorator, just route calls through the proxy
client = Anthropic(base_url="https://anthropic.helicone.ai",
                   default_headers={"Helicone-Auth": f"Bearer {HELICONE_KEY}"})

# Arize Phoenix: OpenTelemetry + auto-instrument installed SDKs
from phoenix.otel import register
register(project_name="support-agent", auto_instrument=True)
Three ways to plug in
  • SDK / decorator (LangSmith, Langfuse): richest traces, including your own functions and tools. Needs code changes.
  • Proxy / gateway (Helicone): one line, sees every model call. Can't see tool calls or your code between calls, and adds a network hop.
  • OpenTelemetry (Phoenix, Langfuse, and others): vendor-neutral; send the same spans anywhere.
Choosing well
  • Is trace data allowed to leave your cloud? If not, self-host.
  • Do you need to see tool calls and agent steps, or just model calls?
  • Will one tool do evals and prompts too, or do you already have those?
  • Prefer OTel, so switching tools later is a config change.
