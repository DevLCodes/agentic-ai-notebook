Reranking with Cross-Encoders

Vector search finds fifty chunks that look like the question. A cross-encoder reads each one together with the question and decides which actually answers it. Retrieve wide for recall, rerank narrow for precision. The reranking topic page has the short version; this notebook opens the model up.

See it in 3D: from fifty lookalikes to five answers

1 · Two ways to score a pair

Both models start from the same kind of transformer. The difference is when the question and the chunk meet.

bi-encodercross-encoder
Inputquery and chunk separatelyquery and chunk concatenated
Outputtwo vectors, compared by cosine or dot productone relevance score (a logit)
Interactionnone until the very end: the whole chunk is squeezed into ~384–1,024 numbers firsttoken-level: “2023” in the question can attend to “2022” in the chunk and notice they differ
Precomputeyes: embed the corpus once, then ANN search in millisecondsno: the score depends on the query, so the model runs at query time
Cost per queryone forward pass (the query) plus an index lookupone forward pass per candidate: O(N)
Jobrecall: find the 50–100 plausible chunks among millionsprecision: put the right 5 at the top

The cross-encoder is more accurate for the same reason it is expensive: it never compresses the chunk before seeing the question. A bi-encoder must decide what a chunk is “about” without knowing what will be asked, so two chunks that share vocabulary (“operating margin”, “gross margin”, a table-of-contents line that says “Operating Margin … page 21”) land close together. Scoring a whole corpus that way is out of the question: FinSight has about 50,000 chunks, so one question would mean 50,000 transformer passes.

    3 · The budget: why only the top 50–100

    A reranker is a fixed price per pair. The price grows with the number of candidates and the tokens in each pair, and the whole call sits on the critical path before the LLM can start. Do the math before picking a model.

    Presets:

    Throughput presets are rough planning numbers, not benchmarks: measure on your own hardware, batch size and chunk length. The model assumes cost grows linearly with tokens; attention is quadratic, so long pairs are worse than this shows. A hosted API (Cohere, Voyage, Jina) replaces this math with one network call, typically on the order of 100–300 ms for ~100 short documents.

    Ways to stay inside the budget

    • Rerank fewer. Measure recall@k of the first stage. If recall@50 ≈ recall@100, send 50.
    • Shorter pairs. Rerank the chunk, not the parent section. Truncate to the model’s trained length (often 512).
    • Batch on a GPU. All pairs for one query go in one or a few batches; padding to similar lengths helps.
    • Smaller model or distilled model. A 22M-parameter MiniLM is many times cheaper than a 568M-parameter bge-reranker-v2-m3.
    • Skip when easy. If the first stage is confident (an exact ID match, one dominant hit), don’t rerank at all; see routing.

    4 · Scores, thresholds and the middle grounds

    A score is not a probability

    A cross-encoder outputs a raw logit. Libraries often pass it through a sigmoid so it lands in 0–1, but that number was trained to order chunks for one query, not to mean “73% likely to be relevant” across queries. Easy questions produce high scores for everything; hard or oddly phrased ones produce low scores even for the right chunk. A fixed cut-off like “drop below 0.7” therefore behaves differently per query type, model and chunk length. If you need a threshold (to say “I couldn’t find this”), pick it on your own labelled set, and re-pick it whenever the model changes. Confidence Scoring goes further.

    Late interaction: ColBERT’s MaxSim

    ColBERT keeps one small vector per token instead of one per chunk. Chunk token vectors are precomputed like a bi-encoder; at query time each query token finds its best-matching chunk token, and the score is the sum of those maxima. You get token-level matching without a transformer pass per pair, at the cost of a much larger index (ColBERTv2 compresses it with residuals).

    LLM rerankers

    stylehow it workstrade-off
    PointwiseScore each (query, chunk) alone: “relevant? yes/no” or 0–3. monoT5 is the classic fine-tuned version.Parallel and simple; scores drift between calls, same calibration problem.
    Pairwise“Which of these two answers the question better?” Aggregate the wins (duoT5, pairwise ranking prompting).Robust judgements, but O(N²) comparisons unless you sort cleverly.
    ListwiseShow the model 20 passages and ask for a ranked list of IDs; slide a window over 100 (RankGPT).Sees candidates side by side; long prompts, sensitive to input order, slowest.

    An LLM reranker can follow instructions (“prefer the audited financial statements over press releases”) that a cross-encoder can’t. It is also 10–100× the latency and cost. Treat it as a candidate to beat, not the default.

    How they are trained

    • MS MARCO: Bing queries with ~8.8 million passages and human-clicked positives. Most open cross-encoders (the ms-marco MiniLM family) start here.
    • Hard negatives: the training negatives are chunks the retriever ranked highly but are wrong (the gross-margin chunk above). Random negatives teach nothing.
    • Distillation: a big teacher (a large cross-encoder or an LLM) labels pairs; a small student learns its scores. The same trick trains better bi-encoders from cross-encoder scores.
    • Domain fine-tuning: a few thousand (question, good chunk, hard negative) triples from your own logs or evals often beat a bigger general model on filings, contracts or code.

    How to tell if it helped

    Run the same golden set twice, with and without the reranker, and compare NDCG@10 and MRR (see evals and Testing & Evals). Also log first-stage recall@k: if the right chunk isn’t in the 100 candidates, no reranker can rescue it, as the lab’s “never retrieved” box shows. Fix recall with hybrid search, better embeddings or chunking, then rerank.

    Remember
    • Bi-encoder: fast, precomputed, recall. Cross-encoder: slow, query-time, precision.
    • Rerank the top 50–100, keep 5–10. Cost is one model pass per candidate.
    • Reranker scores order chunks for one query. They are not calibrated probabilities.
    • Measure NDCG@10 / MRR with and without it, plus first-stage recall.
    Pitfalls
    1. One global threshold copied from a blog post
    2. Reranking 1,000 candidates and blowing the p95 budget
    3. Expecting the reranker to fix recall: it can only reorder what it’s given
    4. Pairs longer than the model’s trained length, silently truncated
    5. Shipping it without an A/B on the golden set
